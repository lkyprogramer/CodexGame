# B29 Baseline 成本与有效性复审

日期：2026-10-21。状态：**REVIEW / PROPOSAL，尚未替换现行执行合同。** 本文只形成审查结论与精简方案；未停止远端任务、改变采样或模型参数、实施优化，也未修改既有结果。09:54（上海）观察到远端仍在运行。

## 结论

当前首次 Baseline 过重，应精简。主要错误是将完整声明矩阵、探索测量、正式统计验收一次展开，并把真实 Pi 闭环排在全部合成性能请求之后。14,420 次核心请求主要消耗在重复长上下文 cold prefill，不能按比例增加编程质量证据。

这不是必须接受的项目成本，也不应该每阶段重跑。建议改为：**首次全长度薄覆盖 → 每阶段相关合同与小集对照 → H5/H8 发布时集中资格验收。** 当前运行结果全部保留；缺少统计资格的项保留未资格状态，不能将减少数量解释为原完整矩阵已经通过。

此前由本轮审查引入的“20 Java × 3 seed 是工程下限”没有给出风险覆盖或功效计算依据，应撤回其通用必选地位。已有题目、实际缺陷和适用阶段应决定集合；3 seed 也不能自动证明 3 个百分点非劣。

## 2. 主要 findings

### R1 · P1：首次测量过早承担发布级重复，真实行为反馈被推迟

`runner.py:766–828` 对所有可表示组合无差别重复。现行 [design/07](ninfer-hyperqwen-v3-md-20261019/design/07-metrics-and-acceptance.md) 第 42 行已经区分 T0/T1/T2，并说明 672 是声明覆盖；[design/09](ninfer-hyperqwen-v3-md-20261019/design/09-test-and-evidence-contract.md) 第 5 行要求 Task 最小定向、Phase 做本阶段验收。执行器却直接全量 T2 化，首批异常/Pi/任务结果可能几天后才出现。

建议：先完成全 P 薄覆盖和真实行为检查。将阶段性能集合显式绑定所修改路径。第一次 B29 参考数据就绪不等于未来候选发布合格；身份/语料可长期复用，候选比较仍需同期 A/B 小集以控制漂移。

### R2 · P1：重复次数多，但编程任务代表性与验收仍弱

`runner.py:160–205` 的四类 workload 共享相同 record 结构，只改变随机标识与末尾指令；`runner.py:738` 明确写 `NOT_JUDGED_PERFORMANCE_OBSERVATION_ONLY`。09:54 快照 O128 **148/148** 为 `finish=length`；O512 为 **118/150**，O2048 为 **44/80**。这可用于预算/解码压力测试，不能用来认定请求完成了代码任务，更不能用其短 wall 宣称编程变快。

现有 20 题中的新增小 fixture 也不等于真实框架/数据库运行。更高价值的补充是已有隐藏测试题、真实仓库补丁，以及 Pi 多轮上下文的 append、compaction、context_edit、异常耗尽行为。

建议：合成请求仅报告性能；任务 wall 必须以独立测试通过为条件，并同时保留失败/超时成本。不能为了提速将 Pi 的 O32768 降至 512，或强制结束 reasoning。已冻结 44 个 Pi 请求包含 15 个经过 compaction 的请求、11 个经过 context_edit 的请求及 2 个必测耗尽异常，先每个执行一次比盲目重复五遍更有信息。

### R3 · P1：p95 桶与需要声明的结论未完全对应

`runner.py:768,816` 和 `analyze.py:255–271` 将固定 P/O512/track/cache 的四负载混合桶凑到 100；每一负载通常只有 25 个样本。混合桶 p95 不能变成每类 Java/中文/tools 的 p95，而 [design/07](ninfer-hyperqwen-v3-md-20261019/design/07-metrics-and-acceptance.md) 第 56–57 行又要求长上下文 warm TTFT p95 和非 copy 类负载尾部回归。

当前分析器主要聚合 elapsed/部分 decode 统计（`analyze.py:82–116`）；采集到 TTFT 原始字段并不等于已实现其候选比率 CI 门禁。它本来也始终拒绝宣布优化资格，但不能靠继续凑满旧次数弥补最终门禁映射。

建议：未来测量前冻结每个 gate 的 metric、桶、权重和比较对象。p95≥100 是本项目最低可估条件，不是“有 100 次即可确认 5% 差异”。CI 跨门槛就是 INCONCLUSIVE；预登记一次追加预算仍不明确，则停止采用，不无限采样到显著。

### R4 · P2：某些缺口需要实现或认证，增加旧版本请求无效

B29 缺 round wall、真实逐 token ITL、可靠 reasoning token 分项及 allocator 高水位；来源重建 BO 也尚未认证。这些与采样数量无关。B29 E8/schema20、B6 rk4v4/schema24、同 codec 的 Cn 对照必须继续分开。

建议：B29 缺值保留原因，阻断相应声明；未来 H0 补计量后做最小负例/开销校验。不要把 H0 尚不存在的字段作为本次 B29 永远无法完成的重复任务。

全局权威仍是 [design/07](ninfer-hyperqwen-v3-md-20261019/design/07-metrics-and-acceptance.md) 的原业务 TTFT/prepare、decode、长上下文和质量门槛。精简的是**何时、对哪些案例估计什么结论**，不是取消数值/状态安全测试或把 INCONCLUSIVE 当 PASS。

### 阶段筛选配额

推荐最多6个P：1024/32768/98304/131072/196608/253952，2类与改动最相关的负载，cold/warm，一个相关采样 profile，每版本5次配对观察：A+B 共 **240请求**。按至少3个时间block交错，short/long的具体顺序在执行前固定；此处是建议修订的统一筛选配额，不能冒称原正式T2已满足。另带2个固定 Pi/代码任务哨兵，数值测试按实际改动独立运行。

明显错误或无收益路线在此停止；达到探索目标才进入更强资格。若CI跨线，先检查效果量和噪声；一次预登记追加仍不清楚，标INCONCLUSIVE/不采用，不能反复加样本直到看起来赢。失败的调试重跑全部留档，发布用未参与调参的冻结集。

### 发布资格与尾延迟预算

H5/H8 才对**实际发布的 profile**做正式关键 case≥10配对/5block与p95资格；首版greedy功能不能靠混入production sampling的统计冲淡退化，也不能宣称production sampling提速。未改变的原sampling路径仍需其合同与工程回归。

一个可审查的预算示例：P32768/131072/196608/253952 × 3类非copy负载 × 35次warm / variant（5block各7次），共420次warm；各自保留cold前置，A+B共**1680请求**。事前登记三种长P各105个固定普通负载混合样本，以及每类非copy负载跨四P各140个样本。这样一份数据可以支持已命名的多个桶；仍需处理同case/block相关性与多个gate，不得称每一个P×每一个workload均有100次，也不以copy收益冲淡普通负载的退化。

此示例限定O512的请求级TTFT/E2E回归，**不能替代完整生成任务wall**。copy完整补丁另做至少10配对/5block，真实Pi任务继续保留32768预算和独立成功判定。如果最终要求每类、每个P、O32768完整任务p95均有资格，成本会更高，须明确扩大预算，而不能用这个示例偷换范围。100样本也不保证5% CI足够窄，是否采用继续fail-closed。

## 5. 题目与长程编程：复用已有，新增只填真实缺口

已有 [QCB-4090 v1.0.0题库](qwen38-coding-benchmark-4090-v1.0.0/docs/03-task-catalog.md) 包含48题、隐藏验证、工具/仓库/长上下文类别；[统计规范](qwen38-coding-benchmark-4090-v1.0.0/docs/05-scoring-and-statistics.md) 已要求完整task/seed配对、失败类型分列、质量通过后比较效率。它是可复用资产，不是当前B29已经通过的证据。

推荐初始8个工程闭环：

| 来源 | 选择 | 作用 |
|---|---|---|
| 已有 Pi 三题 | idempotency、retry-contract、reconnect-loop | 保留可追溯历史锚点；过去medium NInfer为32/23/31秒，但不能外推当前版本 |
| QCB Java | BF009 缓存失败污染；RE003 事务与Outbox；RE007 稳定游标；AT005 SQL分句；LC003 长仓库税额舍入 | 五个不同合同，包含定位、修改、测试、较长上下文 |

这些QCB题仍是JDK小工程，不声明真实Spring/数据库集成覆盖。QCB原runner不是Pi，复用应是冻结题面、workspace和隐藏verifier，接入同一个Pi scaffold；适配与评分环境要先验证，不能把两种agent的成绩直接混合。现有新造17题保留，不必删除，但不再因“凑20题”全部作为每阶段必选。

初始8题各1次用于可运行性与工程参考；正式发布全8题×3固定seed，并在原版/候选间按task/seed配对。60变24并不是统计充分性的证明：8题中1题占12.5%，3次相同任务也不是3个独立业务场景。报告逐题通过、失败、耗尽、分歧与总成本，不以pass@3掩盖稳定性。

再增加**最多2个真实Java仓库holdout**即可，不整套引入外部榜单：SWE-bench Multilingual有43个Java任务，来自Gson、Druid、Lombok、Lucene、RxJava、JavaParser。按任务机制、仓库和构建成本选2题，冻结instance ID/commit/image；正式选择前先确认空patch失败、gold patch通过，模型成绩不可参与选题。此自定义Pi子集只报内部结果，不能报官方SWE-bench分数。[官方数据与评分协议](https://swe-agent-bench.github.io/multilingual.html)

借用SWE-bench Pro V2的**新环境重放补丁评分**：agent结束后只导出允许路径的patch，应用到干净同版本仓库，再注入未修改测试。agent工作区里的测试全绿仅是调试结果。固定失败修复测试与原有通过测试、依赖和资源；保存轨迹、patch、测试exit与日志。[官方锁定协议](https://github.com/scaleapi/SWE-bench_Pro-os/blob/main/v2/README.md)

“长程”要测试持续上下文、跨文件、多次工具与测试反馈，不是强制耗满时长。METR的时间范围用人类专家完成任务的时间定义，不能把“人类8小时题”理解为必须让本机模型跑8小时。[METR定义](https://metr.org/time-horizons/)

两道repo题可先固定每题50分钟上限作内部预算参照，提前完成立即评分；若要测compaction/rewrite，用冻结Pi轨迹或明确的阶段任务触发它，不靠让任务空转。公开基准的更多取舍、版本和限制见[一手资料报告](ninfer-baseline-benchmark-sources-20261021.md)。

外部2题的环境准备不阻塞先交付全P与已有题的参考数据；未就绪就明确真实repo资格NOT_RUN。最终建议为8题×3seed加2个repo题各1次，每个variant共26次闭环；它仍是工程回归集，不是总体能力的统计无退化证明。

| 发布示例1680请求 | 当前混合均值约20.44 GPU小时，仅一个相关profile | 预留约1天性能窗口，再加copy完整任务和Pi闭环；两个profile分别资格约翻倍；CI不足不得自动延长到通过 |

所以合理目标是**首次参考集按一个工作日量级安排并由Pi试点修正；常规阶段性能按小时；发布节点约1–2天量级**。这些是预算目标，未跑过的新任务和正式tail合同可能突破它。不能承诺“全部肯定几小时”，也不应默认“每阶段都必须6–8天”。总改造工期还取决于BO/P6资格、GPU实现与DFlash资产，不能由bench次数单独推断。
