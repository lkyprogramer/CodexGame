# NInfer性能改造复盘：计划选择和执行验证都需要纠正

截至2026-10-24，本轮已完成5个性能方向的筛选，H3/W6只完成部分实机数值验证。局部CPU和算子确有收益，但**尚无可归因、可复现的整体Chat推理加速结果**。因此问题同时出在方向选择和执行；不能用“还有很多方向没做”代替对这两项问题的解释。

本文只读复用现有源码见证、报告和原始JSON，没有SSH、GPU、模型、HTTP、构建或旧测试执行。当前主机状态以本轮主代理的新读回为准，本文不把历史STOPPED快照冒充实时检查。全部旧原件、失败、18处G1差异和C1缺口保持。

## 2. 计划的主要错误：没有先量化“可省多少整轮时间”

[K0原始metrics](../output/ninfer-v4-k0-20261023/metrics.json)中，`GPU_op_durations`、`GPU_critical_path`、`per_round_timeline`均为null；K0报告当时已经明确这一缺口。后续norm、correction、卷积先后进入实现，选择依据主要是源码中存在可优化机制、改动能隔离，而非它们占真实请求关键路径的已测份额。它们适合廉价研究筛选，但不应连续被包装成“下一项最值得做的推理加速”。

Amdahl关系为：局部段占整轮串行关键路径比例为f，局部耗时减少比例为g，且其余路径完全不变，则整轮耗时减少为f×g。若一个局部段减少36.48%，要获得10%整轮降耗，该段原先必须占至少约27.4%；若局部段只占1%，同样优化只贡献约0.365%。这是条件算术，不是对NInfer各算子份额的测量。

K2-T05正好体现这一问题：原始局部段排除输入投影、GDN递推和其余模型层；真正完整Prefill只观察到0.314%改善。[整链原始配对](../output/ninfer-v4-k2-t05-chat-remaining-20261024/analysis.json)为5/5更快，但均为有序instrumented cohort。不能把局部和整链两个不同样本的百分比反推成精确实测热点占比，更不能认为门槛从1%降到0.3%就解决了“用户感觉不快”的问题。

C0的错位不同：优化对象是后台发布而非持续decode。微基准节省约0.94秒是真实的，但首个深前缀可能在整个publication job完成前已可恢复。C0补测中P4命中stable_prefix，C0命中routed_session，两个控制假设未先按源码厘清。日志queue字段又包含restore/准入，不能与restore时间简单相加或直接当纯竞争等待。该设计导致实机即使功能通过，也回答不了预定TTFT因果问题。

H1则缺少接受上界的事前筛查。两个原正例的raw每轮正式提交3.880/3.944，K3上限为4。在相同token轨迹、相同整轮成本等强假设下，只靠提高接受量，节时上界为`1-3.880/4≈3.01%`及`1-3.944/4≈1.39%`，已经低于原5%信号目标。源码又明确首版Lookup不跳过mandatory MTP对齐/下一轮proposal，所以命中本身不省当前轮计算。此类正例不适合用于证明显著加速。真实Pi较低接受率仍可能有空间，但不能由这个失败样本直接证明。

原先把完整上游整合、接口/UI/媒体能力与性能研发串成统一前置，也确实增加了与纯Chat加速不直接相关的工作。这部分后来已按用户要求剥离。它说明早期计划目标过宽，但不能否定P3 small-T等实际性能代码的价值；这些尚欠相对原版的性能量化。

## 3. 执行的主要错误：大量合同覆盖了控制器，却没有先覆盖真实失败边界

下表是**已明确记载的不同缺陷类别/例子**，不是完整失败次数统计。一个类别可有多次窗口，一个窗口也可有多个缺陷，不能把行数当失败总数。

| 类别 | 真实例子 | 影响与责任 |
|---|---|---|
| 请求身份关联 | K2-T05用client operation标签查服务端，而实际权威ID由响应头产生；P2也保留关联失败 | 请求已经结束仍被采集器判成缺少终态，增加修复/接续成本；属于执行工具缺陷 |
| 进程身份登记 | P4读取短暂空cmdline并登记错误owner | CPU只验证理想身份不足以覆盖真实spawn/register边界；服务未测完就被安全合同中止 |
| Graph见证 | K1从探针实例化模板取地址，未取真实launch TU地址 | 正确kernel也可能被错误见证拒绝；属于驱动/诊断问题，不是correction数学失败 |
| 宏/观测接线 | K2-T05诊断宏未进入实际模型消费TU，首轮缺真实logits | 只看测试target编译通过不够；应先检查实际consumer TU和对象符号 |
| 夹具与协议合同冲突 | C0具名tool_choice/HTTP400终态、P3严格增量/历史夹具 | 测试输入没有先对齐产品支持范围，实机预算被无效夹具消耗 |
| 夹具与运行保护冲突 | H1要求重复行/重复对象，命中原repetition guard；K2-T05 `Reply OK.`与精确OK断言歧义 | 质量正例和性能分母被污染，不能靠保留FAIL后继续累加文档来补救实验有效性 |
| 真实初始化未覆盖 | H3 record workspace合法返回0，但新驱动构造非零Arena | 16个具名CPU合同和构建PASS没覆盖这个实际调用约束，首个链场景在Op前失败 |
| 失败出口审计遗漏 | H3 catch只写stderr，没有落audit；K2-T05最早native也缺最终资源总数 | 原失败虽然保留，但完整成本无法复算，造成永久证据缺口；应在现有异常出口最小修复 |

来源：[P2关联/取消补测](ninfer-v4-p2-http-remaining-20261022.md)、[P4登记修复](ninfer-v4-p4-chat-recheck-20261023.md)、[K1 Graph修复](ninfer-v4-k1-graph-r2-20261023.md)、[K2-T05请求ID修复](ninfer-v4-k2-t05-chat-remaining-20261024.md)、[C0 HTTP与L2前置诊断](ninfer-v4-c0-l2-preflight-20261023.md)、[H1原始失败解释](ninfer-v4-h1-hardware-20261024.md)、[H3精确stderr与源码](ninfer-v4-h3-w6-hardware-20261024.md)。

这些问题不是“严格预算自然会导致”，也不应归咎于用户禁止重跑或要求保留失败。预算和不可重发保护是合理边界；执行者应在花模型/GPU额度前，使夹具、进程登记、ID和真实初始化合同闭合。保全失败是必要善后，不是性能交付。

反复为每个小方向建立新的controller/ledger/probe/归档/文档入口，扩大了容易出错的代码面。已有owner、响应ID、deadline、Graph采集修复应选择性复用到同一窄驱动；不能因为新任务名不同就再建一套。下一轮需要减少新工具代码，而不是继续增加没有覆盖真实消费路径的CPU场景数。

现有资料没有覆盖所有分析、修改、审查和传输的统一工时账本，因此不能可靠宣称“多少小时/多少比例都浪费在工具上”。GPU窗口本身有原始耗时，工程文档中的8–16小时等是预估，不应当成实际已花工时。

## 4. 已有证据支持的下一步，而非再列一长串方向

**目前没有证据能给任何尚未实施候选授予“最大热点”的事实称号。** 应先准备一个覆盖真实持续decode的窄成本归因，将一次完整round分为Target主体、Target head/采样、MTP alignment、后续AR/proposal head、许可/host间隙。使用同一现有raw基点和既有观察入口；不重跑旧Baseline，不创建新的业务接口，不把Profiler本身扩成一个工程阶段。

已有源码提供的高性价比候选是**draft-only成本降低**：进一步核对现有optimized proposal head的词表/投影与可省计算，优先审查只影响proposal head/映射的窄变化。理由是它在每轮固定多次执行、不会靠局部norm的几微秒赌整链收益，也可保持完整Target分布权威。证据为[现有MTP执行链](../output/ninfer-v4-k0-20261023/source-witnesses/src/targets/qwen3_8/impl/runtime/mtp_impl.h)，以及[W6选型实际源码核对](ninfer-v4-post-h1-selection-20261024.md)：现有proposal head已经是131072，而Target为248320，不能把已有裁剪或greedy proposal重新算作新优化。

该候选只具有机制上的潜力，**不是已经确认的大收益**。缺少proposal head独立耗时、实际draft argmax覆盖和进一步裁剪后的接受变化；若head占整轮很小，或新shortlist降低接受量，整轮仍可能更慢。词表尺寸比例不能直接当吞吐改善比例。任何draft裁剪保持Target全词表、processor顺序、RNG、accept/residual/bonus、状态许可不变，且必须在完整decode口径判断代价和接受损失。

并列的较小产品改动是已有W6配置：已有K≤5和T6路径，产品扩宽工作少，但已有驱动准备成本并不小；本轮实机未取得完整状态和性能，不能继续把“配置已存在”当收益证据。修复H3驱动可以解除其技术阻断，但不应自动追加补测或成为所有新方向的前置。

较大潜在收益的proposal-skip/DFlash2/全局检索仍有研究价值，但前者涉及Graph拆分和MTP状态/回退时机，后两者涉及资产、索引/草稿质量及更多资格。它们不符合“本轮先找范围小”的首选条件。workspace复用只有在真实内存/Graph开销限制吞吐时才有直接性能收益，现有172.57MiB容量与短场景45.45MiB峰值不能证明这一点。Utility scheduler需要混合负载队列证据，也不解决当前C1持续decode单轮成本。

## 5. 下一轮如何更快得到有用答案

1. 先用已有数据或一个未来获准的窄trace确定占比和上界；进入实现的候选必须写出“省哪段、该段当前花多少、增加什么成本”。份额未知就记未知，不能替换成方向列表或外部引擎百分比。
2. 首次性能实验选择真实Java/中文Chat片段与一个工具场景，避免重复保护/语义歧义；Target采样、Pi预算、上下文不变。为归因计算的固定token轨迹与真实采样质量分别解释，不混成一个PASS。
3. 同一驱动先验证一个正常路径、一个会失败的真实入口、一个集成边界；优先补实际Arena、response ID、异常audit等已暴露缺陷，不追求CPU合同数量。
4. 对未改变的数学、state、codec、旧Graph直接复用证据；新的局部首筛若没有足够整轮上界就停止，不再支付“完整产品接入→Chat”成本。
5. 交付只报告三件事：真实关键路径是否变短、完整decode/token或TTFT是否改善、哪些质量/状态缺口仍在。构建数、合同数、文档数和review通过不能列为性能成果。

本文没有执行新性能测量，收益预测、p95、置信区间和optimization qualification均未新增。具体新候选与只读准备结果由主代理结合当前源码和外部一手研究统一选择。
