## 1. 对方向调整的判断

### 1.1 这次收缩范围是正确的

你现在的目标是研究 Inkling 的计算机制，并能亲自控制其执行细节。Astral 的 Rust 主机侧和手写 CUDA，配合同一 GGUF 的 llama.cpp 参考，能把模型语义、执行策略和硬件实现拆开观察。相较之前 v2 的广泛整合，v3 减少了无助于回答研究问题的工程依赖。[S01] [S02]

我的判断是：

- **底座选择继续沿用 Astral。** 本次发现的关键问题多数是验证、代码地图和实验设计问题，没有形成必须换引擎的证据。
- **研究成果优先于达成某个 tok/s 数字。** 能清楚解释第二遍、第三遍的作用，比先实现一个生产服务器更符合目标。
- **保留参考实现，但不让参考框架决定实验结构。** llama.cpp 用于同资产数值对照；官方模型配置和 Transformers 用于语义核查。
- **项目论文按“能否形成一个可证伪实验”筛选。** 借鉴一个内核、状态更新约束或测量方法即可，不需要迁移对应项目的完整架构。

v3 已经写明 G3 性能不通过不阻止 P5 研究，这一点应该落实到任务依赖，而不只是留在总计划文字中。[S02]

### 1.2 建议冻结的研究边界

| 项目 | 当前主线 |
|---|---|
| 模型 | Inkling-2-Mini 固定三遍；varloop 作为对照研究模型 |
| 硬件 | 单张 RTX 4090，24 GB 级显存；既有主机与用户目录工具链 |
| 执行 | 单请求优先；prefill、单 token decode、小批验证分别测量 |
| 引擎 | Astral 固定上游版本加本地补丁 |
| 资产 | 既有 A1 GGUF、A3 原生 DSpark、小文件与已下载的 A4 varloop |
| 目标 | 解释模型行为、找到可复现的质量—延迟—显存关系 |
| 暂不推进 | 生产替换、多模型框架、通用分布式服务、专家 SSD 系统、通用内核编译平台 |

这里没有否定那些系统研究的价值，只是它们当前不能直接回答“这个循环模型为什么有效、哪里能省、如何在 4090 上更快”。

## 3. 优先修正的评估问题

### 3.1 V7 的政策调整有理由，但两端没有计算同一个量

用户批准以参考实现自身差异替代固定 1.0 阈值，这个方向合理。本次审查不撤销这项历史批准；需要修复的是它的可执行定义。[S04]

源码存在三层差别：

| 比较项 | `nearcmp.py` 对参考的测量 | Astral patch0003 的测量 |
|---|---|---|
| 数值 | 归一化 log-prob | 原始 logits |
| 窗口 | 两边均满足 log p > −16 的交集 | step 一侧距其最大 logit 小于 16 |
| KL | reference 截断求和，且来自 u16 编码文件 | float64 全词表求和 |

因此，记录中的 **1.18 ≤ 3.15 不属于同一统计量的直接比较**。这不说明真实结果一定不通过，只说明目前不能用该比较完成严格复判。[S05] [S06] [S07]

两个简单例子可以说明原因：

- logits 整体加 3，softmax 分布不变；原始 logit 差是 3，log-prob 差是 0。
- 一个 token 从 logit −15 降到 −17，若两侧都必须进入窗口，变化最大的 token 反而可能被排除。

**建议：两端共用一个离线计算器。** 对相同 token 前缀、相同位置导出 logits；使用同一种 log-softmax、同一种词表范围、同一种窗口和 KL 定义。历史阈值保留为历史值，新计算口径的阈值重新校准，不能直接继承数值 3.15 和 0.0284。

### 3.2 文档已经改判，判定脚本仍按旧规则运行

`tools/w2/v567.py` 仍用“argmax 相同且全词表最大差 ≤1.0”计算 V7；near/KL 只解析到诊断文本，没有参与判定。它也只打印 JSON，没有将失败映射成非零进程退出状态。[S08]

本次对判定器做了本地合成诊断：

| 合成输入 | 实际行为 | 意义 |
|---|---|---|
| full max=3.6、near=1.18、KL=0.0147 | V7=False，进程仍退出 0 | 当前脚本不能复现文档的新 PASS |
| 空 score 日志 | V5=True、V6=True、n_gen_checked=0 | 缺失数据可能被错误视为通过 |

这些是判定器的确定性问题，**不是这台 4090 真实运行缺少数据的证据**。修复成本很小：要求样本与位置完整、唯一、有限；缺项直接失败；判定策略版本写入报告；总体 verdict 对应清晰退出状态。

### 3.3 PASS 的覆盖范围比标题所暗示的小

对上游命令和脚本的读取显示：[S09] [S07]

- **V3** 的 verify-model 使用固定 5 token，并比较每行首尾各 3 个已打印值。应叫“逐算子采样对照”，不能叫全张量逐元素证明。
- **V4** 的 c512×8 实际评分 `8×(512−1−256)=2040` 个位置，不是 4096 个独立测点。
- **V5** 的 W2 使用全 step 的 teacher-forced score，不能单独覆盖默认 `prefill→generate` 路径。
- **V7** 每条序列只比较最终位置，因此是 **16 个 logits 向量**，不是 16×500 个位置。
- **V8** 已经允许非零 token 分歧，名称应使用“容差内目标一致性”，另报严格 token 一致率。

不用因此增加一套大型评测框架。补查 prompt 末位、prefill/decode 交接、小批长度变化和几个边界位置，就能显著提高证据质量。

### 3.4 “参考噪声底”应进一步分解

`ub512` 对 `ub1` 的差异主要反映不同执行形状、累加顺序和内核路径。它不是同配置重复运行产生的随机噪声，也不一定是不可降低的误差下限。

建议把三个对照分别保存：

1. **重复性对照**：同一引擎、同一形状、同一输入重复。
2. **形状对照**：同一引擎，prefill、step、不同 verify batch。
3. **跨引擎对照**：同一资产、同一前缀，Astral 对 llama.cpp。

候选 KL 小于形状对照的 KL，表示它落在一个已观察到的工程误差尺度内，不表示候选比参考更正确。

此外，2040 个相关 token 只有 8 个 chunk；p99 受约二十个尾部值决定。后续扩大测点时，不能继续机械地要求“候选所有位置的最大值小于参考 p99”。应事先选定配对分位数、超阈率或实际 winner-gap 规则，并按文档/题目聚类统计。

### 3.5 缺少助手生成前缀，应影响补测范围

T13 已记录样本缺少 `<|message_model|>` 生成提示。因为 W2 多项实验沿用了 V2 的 token IDs，这不只影响后续 T14 的速度和接受率，也影响 V5–V8 对真实助手生成场景的代表性。[S03]

旧结果仍证明“两个实现处理同一输入时的接近程度”。建议保留它们作为回归样本，再用正确模板补跑，而不是删除或改写旧数据。

要记录的不只是 prompt 文本，还包括：

`template_hash、rendered_token_ids_hash、add_generation_prompt、special_token_policy、EOS_policy、reasoning_mode`。

### 3.6 当前可审阅证据还不够独立重算

本次取得的是执行摘要、脚本和补丁，没有取得 T12 的逐位置数组、原始结果 JSON、完整 logits 或可取回它们的索引。准确说法是“本次未取得”，不能推断它们在 4090 上不存在。

最小补充只需：

- 小型逐位置结果 JSONL/NPZ；

不用把数百 MB 的中间文件塞进 Git，更不需要新建通用证据服务。

`VALIDATION.md` 仍写“4090 未执行、全部 NOT_RUN”；T04 的原 FAIL 已由 T11 修复，但任务表没有清楚表示该失败已关闭。建议保留历史记录，加明确时间和版本边界，链接当前执行表。[S03] [S11]

## 4. 两项必须纠正的 Astral 代码地图

### 4.1 Inkling 预填当前走 mma3，不是 mma5

固定版本的 `model/inkling.rs` 通过 `Exec::mm / Gemv::launch_mma` 执行相关矩阵乘。`QAct::with_f16` 在满足形状条件且未启用 INT8 覆盖时，使路径进入 **mma3**。Inkling 模型路径没有构建 `add_frag`，也没有调用 `launch_mma5`。[S12] [S13]

所以：

- `04_astral_fork.md` 中“4090 的预填走 mma5”需要更正。
- 调优先针对实际 mma3、小批 INT8/dp4a、MoE 分组路径。
- 将其他模型已有的 fragment/mma5 路径移到 Inkling，是**新的布局与内核实验**，涉及额外权重表示、工作区和数值差异，不能当作现成开关。

### 4.2 默认解码已有 split-K online softmax

`logit[MAX_CTX]` 是 simple/reference attention 的实现。默认 Inkling 形状会走 `attn_decode_split`，已有 split1 / 循环 split 和 merge，使用分块 online softmax。[S12] [S14] [S15]

8192 限制仍然真实存在，但分别出现在：

- Rust 启动参数检查；
- CUDA 中多个 `min(capacity, MAX_CTX)` 限制；
- 个别参考路径的静态共享内存布局；
- Session 的缓存分配与位置管理。

因此 P4 应改写为：**扩展已有 split attention，解除各处上限，分离逻辑位置与物理容量，加入 SWA 环形缓存及正确回滚。**

只删除 Rust 检查会留下 CUDA 截断；只增大 MAX_CTX 又可能撑大 simple 路径的共享内存。两个做法都不足以完成长上下文支持。

### 4.3 “330 tok/s 上限”和“已经 launch-bound”只能作为假设

3.1B 个权重乘 4.5 bpw 本身约为 1.744 GB。实际每 token 字节数还取决于循环回访、NVFP4/Q8_0 混合类型、专家路由、LM head、KV、工作区及缓存复用。

如果实际每输出 token 恰好读取 3.0 GB DRAM，且达到 1008 GB/s，才得到约 336 tok/s 的理想带宽推算。这个条件尚未被本机 profile 证实。5745 次 kernel 来自 llama.cpp 的特定实现，CUDA Graph 中的节点数也不等于 CPU enqueue 次数。[S16] [S17] [S58]

把当前结论写成：

> 短上下文存在融合与 launch 调度优化的可能；长上下文可能转向 KV 带宽受限。需要对当前 Astral fork 分阶段测量。

这样既保留方向，也避免把推测当成已经找到的瓶颈。

### 4.4 外部速度数字不能当统一上界

| 来源 | 需要补上的条件 | 对当前项目的用途 |
|---|---|---|
| atlas-ingine 的 236.7 tok/s | atlas-12g、推测解码、不同 dense/KV 精度等条件 | 机制研究参照；不是无草稿上界 |
| Xolotl 的 113–127 tok/s | 主要对应其 14 GB XQ/不同权重；parent NVFP4 另有数据 | 对照具体内核与回滚语义 |
| tqllm 的 exact 模式 | exact 是项目模式名；代码 pin 与镜像 tag 还需分别固定 | 可选独立实现对照 |
| 本地 Astral 143 对 llama 66.7 | 单次记录，llama 当时未开 `-fa` | 首次运行观察；不能替代 T14 |

固定版本的 tqllm README 已写 1.8.0，而模型指南仍示例 1.7.0，进一步说明“源码 commit”和“实际镜像 digest”应分别记录。[S18] [S19] [S20]

## 5. 研究所需的最小语义合同

### 5.1 必须分清三个坐标

后续探针统一使用：

`(token_position, physical_layer, pass, logical_visit, stage)`

物理层表示共享的参数，pass 表示循环遍次，logical visit 表示执行顺序，token position 表示序列时间。这些坐标不能互相替代。固定三遍时：

- prelude：物理层 0–5；
- core：物理层 6–17，执行三遍；
- coda：物理层 18–23；
- 总访问数：`6+12×3+6=48`。

每遍 core 都从 prelude 的输出与本遍块状态开始；第二遍及之后才通过控制器读取上一遍的消息；它不是简单把上一遍末尾的一个 residual vector原样继续向下跑。每个 core pass 的历史 KV 与 conv 状态也分别存在。[S21] [S22]

~~~mermaid
flowchart TD
    A["同一 token 的 Prelude"] --> B["Core 第 1 遍"]
    A --> C["Core 第 2 遍"]
    A --> D["Core 第 3 遍"]
    B -->|"块消息与控制器"| C
    C -->|"块消息与控制器"| D
    D --> E["Coda 与输出"]
    F["第 1 遍历史 KV / conv"] --> B
    G["第 2 遍历史 KV / conv"] --> C
    H["第 3 遍历史 KV / conv"] --> D
~~~

图只说明依赖关系；Attention Residuals 还需要各块累计状态，不能把图中的一条连线实现成单一张量拷贝。

### 5.2 最小状态表

| 对象 | 参数是否共享 | 状态是否自然共享 | 实验时必须记录 |
|---|---|---|---|
| core 投影与专家权重 | 同物理层跨遍共享 | 不适用 | 物理张量身份、量化格式 |
| core Attention KV | 不适用 | 默认按 pass 独立 | 读历史哪一遍、当前 token 写哪一遍 |
| K/V/attention/FFN 短卷积 | 卷积参数可共享 | 历史按 visit/pass 独立 | ring 指针、有效长度、回滚版本 |
| Attention Residuals | 读出参数按定义使用 | 当前块和跨遍消息分别管理 | 块编号、归一化前后状态 |
| controller | 同物理层参数复用 | 输入来自不同 pass | 输入、消息、gain、forget |
| DSpark 特征 | 特定访问处读取 | 不能只按物理层取值 | feature slot 约定、读出位置 |
| CUDA Graph | 可复用固定执行结构 | 依赖稳定地址与形状 | pass 数、capacity、verify 长度、指针纪元 |

### 5.3 区分四类变化

| 类别 | 例子 | 正确的评价 |
|---|---|---|
| 表示/状态等价变换 | 无损打包、同值布局重排 | 位级往返与状态不变量 |
| 同数学计算的实现变化 | 融合、不同 reduction、不同 MMA | 数值误差、局部与端到端回归 |
| 推理策略变化 | KV 跨遍共享、LoopCD、提前退出 | 新策略的质量—成本权衡 |
| 模型变化 | 不同 checkpoint、额外训练、改 controller 参数 | 新模型对照，不能归为原模型无损加速 |

同专家被多遍选中，只说明参数重用；输入改变，专家输出仍需重算。KV 历史相似也不等于它们可以直接别名共享。

## 6. 一个足够小、但可信的实验协议

### 6.1 固定两套样本，避免边看结果边改门槛

沿用现有 prompts A/B：

- A 用于故障定位与校准，标明哪些已经看过。
- B 仅在确认未用于选择阈值后作为保留集；若已使用，另外冻结一个小的 C 集。
- 研究语料覆盖代码、中文/英文、数字/精确字符串、结构化输出与长依赖。
- 长上下文另取小样本，不把所有组合立即扩成全量矩阵。

建议首先完成 16–32 个 case 的小实验，再决定是否扩大。几千相关 token 的细粒度测量用于定位机制；不能替代足够多独立题目的质量结论。

### 6.2 统一数值比较的具体定义

建议新口径使用 float64 的离线 log-softmax：

`lp = log_softmax(z_reference)`，`lq = log_softmax(z_candidate)`。

选参考单边窗口：

`S = {i : lp_i >= max(lp)-16}`。

然后记录：

- `max_near = max_{i∈S}|lp_i-lq_i|`；
- `KL(p||q)`，明确全量或截断求和；若截断，另记被排除的概率质量；
- 参考/候选 argmax、双方 top-2 margin；
- `gap_ref = z_ref(argmax_ref)-z_ref(argmax_candidate)`；
- `gap_candidate = z_candidate(argmax_candidate)-z_candidate(argmax_ref)`；
- top-k 重叠、非有限值数量、词表 mask 和 token 位置。

也可以选择并集窗口，但必须在校准前冻结，不能用候选是否进入窗口来隐藏差异。采用 u16 KLD 格式时，再抽少量 FP32 logits 核查编码/截断误差。

**原 G2 继续作为历史工程门槛；统一后的复核生成新的策略版本。** 不以修改公式为理由自行放宽或收紧用户已经批准的标准。若新公式需要新的数值阈值，先由参考对照给出依据，在候选保留集结果揭晓前固定。

### 6.3 检查点比单纯加长生成更有效

短期优先取：

| 维度 | 建议检查 |
|---|---|
| prefill/step | prompt 末位；生成第 1、2、8、32、128 个位置 |
| prefill chunk | 实际 chunk 边界前一位、边界位、后一位 |
| 小批验证 | batch 1/2/4/8；条件允许再测其余中间长度 |
| conv | 初始 0–4 token；截断恢复；接受前缀与回滚 |
| SWA | 1023/1024/1025 及真正发生 wrap 的位置 |
| 容量 | 当前 8191/8192；支持扩展后再加入 8193 |
| Graph | 同输入 graph/eager；探针开/关 |

表中边界数默认表示序列长度，实际 trace 另存零基 token_position；执行时不可把长度与下一个写入下标混用。8192 长度的 prefill 可以单测，但持续生成和投机必须预留剩余容量。

这是按风险挑选的有限覆盖，不要求一开始执行所有维度的笛卡尔积。

### 6.4 数值、质量、性能分别回答问题

- **数值**：当前实现是否按预期计算同一策略？
- **质量**：策略改动是否影响答案、代码运行、精确检索、工具参数或长生成稳定性？
- **性能**：变化是否降低 TTFT、每个提交 token 的延迟和显存峰值？

研究任务可以得到“没有质量改善”或“没有性能收益”的有效结论。内核调优沿用两轮有数据支撑、收益不足即结束的纪律；机制研究不能因为没有 tok/s 提升就判失败。

### 6.5 输出只保留最小必要结构

建议每次实验采用一个目录，不新增后台平台：

~~~text
run.json
metrics.json
positions.jsonl
trace-summary.jsonl
stdout.log
stderr.log
evidence.sha256
~~~

`run.json` 至少包含模型/模板/语料 hash、Astral 基线与补丁身份、参考 commit、构建 flags、运行参数、pass/cache 策略、测量模式和证据路径。计划状态继续使用原项目约定，实验的科学结论另写“支持 / 不支持 / 不确定”。

## 7. 先做真正有解释力的观测

### 7.1 T15 的探针应观察完整的块消息结构

目前计划中的 RMS、余弦、gain/forget、路由统计是好的起点，但还不足以判断哪条信息通路在起作用。建议第一版只在选定 token 和块边界记录：

| 探针 | 主要问题 | 推荐记录 |
|---|---|---|
| prelude / core block / coda 输出 | 信息在哪个阶段改变 | RMS、最大值、分位数、前若干异常坐标能量占比 |
| Attention Residuals | 当前输入读取哪些块 | softmax 权重、reader score、来源块身份 |
| 跨遍 message | 上一遍哪些信息传到下一遍 | message norm、reader 权重、输入与消息的相关性 |
| controller | 信息放大、抵消还是保留 | gain、forget、keep=1−forget 的分布及输出贡献 |
| MoE router | 是否沿不同专家路径计算 | top-8、选择分数、第 8/9 名差距、实际专家权重 |
| Attention | 是否从近邻或远处取信息 | near/far/sink 概率质量，抽样熵 |
| 读出 | 中间信息能否用于预测 | raw/coda/native-depth 三种读出分别标记 |

gain 与 forget 使用 tanh，不是概率；keep 可以大于 1，gain 也可以为负。把 gate 值当成“保留百分比”会产生错误解释。[S22]

避免全词表、全层、全 token 无限制落盘。先记录标量、少量向量及异常位置；完整 logits 只为重新计算 KL、分歧定位或读出校准而保存。**top-k 日志不能替代完整归一化的 KL。**

### 7.2 Goodfire 是此次最值得加入主线的直接研究

Goodfire 的原创工作直接研究 Inkling-2-Mini，观察到异常激活与跨遍块选择相关，并比较了 raw、tuned、coda 三类 lens。它提供了比“每遍余弦相似度”更有针对性的复现方向。[S23]

建议做两步，而不是直接接受解释：

1. **复现分布。** 在自己的 checkpoint、量化与输入上重新找异常坐标及块读取行为；论文提到的坐标 2027 只作为检查线索。
2. **小范围干预。** 对一个 token、一个 block、一个 pass 的消息或坐标进行替换，观察正确答案概率和最终行为是否按预测改变；增加同范数随机方向作为对照。

若相关性在 A1 上消失，应先检查采样位置和量化影响；不能为了复现图形去强制寻找某个坐标。若相关性存在但干预无作用，也应记录为因果解释尚不成立。

### 7.3 raw lens、coda lens 和真正浅深度模型必须分开

直接对 core-end 状态应用 output norm/head，是一个低成本探针，但不是“模型做完这一遍后的正常答案”。

完整 coda lens 还包括尾部六层、块混合、norm、head 与 softcap；这些层本身有序列注意力和 conv 历史。对一个 token 复用最终深度的 coda 缓存，与整个前缀都按浅深度重新计算，不是同一个实验。[S22] [S23] [S24]

建议明确三个标签：

| 名称 | 定义 | 用途 |
|---|---|---|
| raw lens | 直接读出指定中间表示 | 快速定位变化 |
| coda lens | 对指定深度的完整块状态运行 coda，注明历史策略 | 测量中间表示的可读出性 |
| native-r | 整个 prefill/decode 都执行 r 遍 | 比较实际 r 遍模型 |

第一轮可以只对很少的位置做 coda lens；按深度独立维护或重新计算其状态，避免一次性复制多套长上下文缓存。输出 head 词表很大，coda lens 也有真实成本，不能在估计 early-exit 收益时忽略。

### 7.4 探针不应改变被研究的行为

T15 至少交付三项对照：

- 探针关闭与原基线的同路径输出；
- 探针开启与关闭的数值差异；
- graph/eager 的独立差异。

性能结果来自关闭探针的正式模式；机制 trace 来自单独记录的观测模式。尽量按选定位置批量取回小型数据，不在每个算子后做同步拷贝。补丁已经修复过跨 stream 时序，不能在加探针时顺手删除同步，再把“开 trace 时通过”当作原路径正确。

## 8. 对 R1–R7 的逐项完善

### 8.1 R1：测“额外循环解决什么问题”，不只测与三遍有多像

**主要对象：同一个 varloop checkpoint。** 官方说明其后段训练按 1:2:6:2:1 抽样 1–5 遍，之后在三遍做 post-training；它与固定 Mini 的后期训练不同。6 遍、10 遍应单列为训练外探索。[S25]

最小设计：

| 实验臂 | 深度 | 解释 |
|---|---|---|
| varloop 主实验 | 1、2、3、4、5 | 同 checkpoint 的训练内深度曲线 |
| fixed Mini 对照 | 3；少量 1、2 | 观察固定三遍模型对截断的敏感性 |
| varloop 外推 | 6；有迹象再到 10 | 训练外外推，不混入主表 |

每个深度从同一 token 前缀重建自己的历史，不能跨深度复用缓存。先统一或明确两类 checkpoint 的加载与计算精度，避免把 A1 GGUF 对 A4 原生格式的差异归因于循环。

增加三个小任务：

- 可生成、答案确定的 N-hop 查找，按 hop 数和干扰程度分桶；
- 有确定结果的代码/数学题；
- 多位置、多干扰的长依赖查找。

同时报告 NLL/PPL、任务正确率、生成长度、截断率、整题用时和正确任务/秒。**与三遍的 KL 变大不必然表示变差**：四遍可能改变分布并解决更多题。官方报告过特定任务在更多循环下改善，这只能作为待复现假设。[S26]

### 8.2 R2：每一遍在做什么

先把 raw/coda/native-r 的读出区别落实，再观察：

- 正确 token 的 log-prob 是否按遍次改善；
- 哪些位置最后一遍才发生关键修正；
- block-message 权重和异常激活是否提前预示这种修正；
- 高余弦、低 norm 变化是否仍伴随路由翻转或答案变化。

“相邻遍相似”不等于“后一遍无用”。可以专门寻找高相似度但最终答案变化的反例，它们往往比均值更能暴露模型机制。

### 8.3 R3：专家重合度要与路由稳定性和复用距离一起看

Jaccard 可以保留，但应增加：

- top-8 集合及选择分数；
- 第 8 名与第 9 名的 margin；
- 同专家输入的变化；
- 对应专家的实际计算耗时与权重读取估计；
- 同一个物理专家的访问距离。

同一物理层在下一遍被访问之前，中间经过多层计算；不能因为专家重复就认为其权重必然还在 L2。A1 已全驻留显存，这里首先研究的是显存 DRAM（GDDR6X）/L2 局部性与小批分组，而不是 CPU 专家卸载。

若要复用专家输出，必须作为新的近似推理策略，单独评估误差与质量；它不能被描述为普通缓存优化。

### 8.4 R4：不要再把不同的“共享 KV”混成一个实验

建议首轮只做三臂：

| 实验臂 | 过去 token 的 KV | 当前 token 的 KV | conv | 性质 |
|---|---|---|---|---|
| A：per-pass | 每遍各自历史 | 每遍自己计算 | 每遍独立 | 原始基准 |
| B：global last-history | 核心全局层读取末遍历史 | 当前遍自己计算 | 每遍独立 | 仿 PR51161 的受控变体 |
| C：first current+past | 核心全局层读取首遍历史 | 后遍复用首遍当前 KV | 按被复现补丁语义处理 | 复现 prototux 的更激进策略 |

prototux 的实际补丁还跳过后续 pass 的相关 K/V projection、conv 等计算；它与 PR51161 只改变过去历史读法不是同一干预。其长生成重复现象不能直接否定 B；PR 的短样本 token 一致也不能保证 B 普遍无损。[S27] [S28]

B 若只做 global-only，应注明这是借鉴 PR 的新实验臂，不是假称已原样复现整个 PR。

每个模式必须有清晰签名：

`scope、history_source_pass、current_token_source、write_pass、conv_policy、prefill_chunk_policy`。

先在现有 8K 内研究输出变化；**研究 R4 的语义不必等待 T17 的长上下文改造。** 只有测 32K/128K 容量收益时，才依赖长上下文基础。

### 8.5 R5：把 controller 消融做成可解释的因果实验

“gain=0”会去掉消息加法，但仍保留 forget 对原输入的缩放；“forget=0”保留全部原输入，但消息仍然存在。因此建议分开比较：

1. 原始 controller；
2. 仅去掉 gain 项；
3. 仅去掉 forget 项；
4. gain=forget=0 的恒等合并；
5. 替换消息内容，但保留 reader/gate；
6. 恢复某个 block 或 pass 的正确消息。

从单点干预开始，再考虑整遍或全模型消融。大范围置零会使表示离开训练分布，结果可以说明依赖性，但不能直接给出“该模块贡献占比”。

评价使用正确答案概率、局部 winner-gap、后续路由与任务结果。仅看 PPL 增加多少，难以区分消息通道、幅度标定和路由改变。

### 8.6 R6：先证明早停值得做，再解决缺失历史

逐 token 提前退出意味着之后 token 可能缺少深层 KV、四路 conv 和相应 coda 历史。varloop 学过不同固定遍数，不代表任意 token 都能独立选择深度而无状态问题。[S22] [S24]

建议分三步：

**第一步：离线 oracle。** 在完整深度 trace 上计算“如果提前读出且不计部署代价，哪些位置可以停止”。这只给接受率/质量的乐观上界。

**第二步：计入真实开销。** 包括 coda/head、探针、状态保存和补算。如果上界收益都不足以覆盖这些成本，就停止这一方向。

**第三步：明确历史策略。** 只选择一种实现：

| 策略 | 优点 | 必须支付的代价 |
|---|---|---|
| 整段/整请求固定深度 | 状态语义最清楚 | 不能按 token 细调 |
| 提交前补齐深层历史 | 历史完整 | 省下的串行计算可能很少 |
| 延后补齐并调度重叠 | 有潜在吞吐收益 | 明确依赖、排程和回滚 |
| 近似历史 | 可减少计算 | 新目标分布，必须测质量 |

第一版可先做“按请求选择固定 1–5 遍”，得到质量—延迟曲线；逐 token 的动态深度放到后面。不要直接把 R2 的 raw-lens KL 阈值写成循环 break。

### 8.7 R7：先优化原生 DSpark，再评估新 drafter

原生 DSpark、incoai DFlash2、2DSD 的 loop-conditioned drafter，应分别建立身份与契约。

至少固定：

- 目标权重与量化 hash；
- loop 数和 cache 策略；
- feature tap 到具体 stash 位置的映射；
- embedding 归一化、输出 head、softcap 和 correction 顺序；
- 词表范围、mask、anchor 与 block 长度约定；
- 接受、拒绝及状态恢复规则。

已有 `[5,23,41,48]` 不能只按“第几个物理层”理解；必须从代码的实际 feature stash 位置解释输入/输出边界。[S22] [S29]

原生 DSpark 先扫少量已经支持的 draft 长度，例如 2/4/6；8 只有在 anchor/block 约定允许时才加入。记录：

`draft_ms、verify_ms、rollback_ms、committed_tokens、accepted_prefix、bonus_tokens、expert_union_size`。

收益按：

\[
\mathrm{effective\ throughput}=
\frac{\mathrm{committed\ tokens}}
{\mathrm{draft+verify+rollback+other\ elapsed\ time}}
\]

如果各部分发生重叠，分母应直接取真实轮次 wall time，不能把重叠段重复相加。

平均接受长度提高不保证加速：验证批次可能访问更多专家、采用不同矩阵路径，或付出较大的快照成本。R7 首轮只需回答“哪种 block 在哪些负载下有净收益”。

## 9. 建议新增的三条研究线

### 9.1 R8：量化误差如何通过循环被放大或修正

这是现计划最值得补的一条主线。

A1 的名字含 Q4，不代表所有张量都是同一种四位量化。记录中存在 NVFP4、Q8_0、BF16、F32；官方原始模型本身又有原生低精度训练与部署设计。把 NVFP4 解码成 BF16，不能恢复原始文件中从未保存的更多权重信息。[S03] [S26]

建议分开研究：

| 问题 | 最小干预 | 避免的混淆 |
|---|---|---|
| 权重表示误差 | 同一原始资产的转换前后，按物理层比较 | 不同 checkpoint 不能互当精度基准 |
| 算术误差 | 固定解码权重，切换局部累加/舍入路径 | 不把低精度 GEMM 与权重量化混为一谈 |
| 路由不连续 | 对路由临界位置测第 8/9 名 margin 与专家集合变化 | 小张量误差可能改变整条专家路径 |
| 跨遍误差传播 | 只在一个 pass 的一个算子注入或恢复局部误差 | 不同时改多个 pass |
| coda 敏感性 | 检查尾部六层、head 与最终块混合；原生后四层的混合精度影响另列 | 不把输出差全归于 core |

**共享权重的约束：**“只给第二遍升 Q8”通常需要第二份表示或运行时转换，既改变显存也改变访存。先做局部小张量或同表示算术实验，证明某一阶段确实敏感，再考虑双格式常驻。

R8 与 R2/R3/R5 可以共用探针。尤其关注 high-margin token、异常激活坐标、块选择和专家选择变化，不只汇总平均 KL。

### 9.2 R9：收益来自当前 token 的深度，还是历史上下文的深度

做一个明确标为反事实的 2×2 实验：

| 历史深度 | 当前 token 浅算 | 当前 token 深算 |
|---|---|---|
| 浅历史 | A | B |
| 深历史 | C | D |

关键是定义浅/深历史如何映射：第一遍是否锚定、后续 pass 如何读源缓存、conv 边界如何接续。不得悄悄把缺失 cache 当零或复用最后一个 slot。

LoopBridge、Late Entry、Loop Behind 提供了这个问题的不同研究方法，但并非都以 Inkling 为实验对象，也并非都无需训练。[S30] [S31] [S32]

建议首先只在固定 teacher-forced 前缀的少量位置做离线实验，观察正确 token 概率、coda 输出和路由，再决定是否实现在线排程。若 C 接近 D，才有理由继续研究“深历史、浅当前 token”；若差距仍大，就说明当前 token 的额外循环不可轻易省略。

### 9.3 R10：局部稳定性与误差传播

高余弦相似度不足以判断迭代稳定。可以增加一个很小的有限差分实验：

- 固定输入、历史与路由策略；
- 在一个消息或 block 状态上施加若干方向的小扰动；
- 比较下一遍及最终读出的变化；
- 分“路由未改变”和“路由改变”两组；
- 使用多个扰动幅度，排除量化舍入把扰动直接吞掉的情况。

记录局部增益 `||δoutput||/||δinput||`，但不把有限样本的局部增益称为全局收敛证明。Inkling 的状态不止一个 hidden vector，top-k 路由也不连续，普通固定点理论不能直接套用。

这条线是研究建议，不是已有论文已经证明的 Inkling 性质。若 R8 显示多数误差会在后续 pass 被修正，R10 可以帮助解释；若少数位置被放大，也能指导精度预算。

## 10. 4090 优化应围绕当前真实热路径

### 10.1 硬件能力、存储格式、实现路径要分开

Ada 支持 FP16/BF16、INT8 和 FP8 Tensor Core；4090 没有可直接照搬 Hopper/Blackwell 的 TMA、wgmma、TMEM 或原生 block-scaled FP4 路径。每 SM 共享内存约 100 KiB；单 block 最大动态共享内存与默认静态上限还需分别处理。[S17]

| 现有对象 | 当前可研究方向 | 不成立的推断 |
|---|---|---|
| NVFP4 权重 | 小块解码、scale 布局、dp4a/MMA、减少重复访存 | “四位存储所以用原生 FP4 Tensor Core” |
| Q8_0 权重 | INT8 MMA 与 dp4a 对照；分 batch 选择 | “Ada 支持 FP8，所以 Q8_0 可直接喂给 FP8 MMA” |
| MXFP4 selftest | 保留已修复的正确性回归 | “修好 MXFP4 就提升了 Inkling 热路径” |
| BF16/FP16 GEMM | 保持同一解码权重语义，比较计算路径 | “永久展开全模型仍能维持原显存预算” |
| CUDA Graph | 优化现有 graph、形状和空节点工作 | “需要从头新增 Graph 才能加速” |

A1 的主要低位类型是 NVFP4 与 Q8_0。按格式计算，NVFP4 约 4.5 bpw，Q8_0 约 8.5 bpw，均还需考虑相应元数据。把所有专家常驻展开成 BF16 会显著放大容量，通常不符合这个 24 GB 实验的前提。[S03] [S13]

### 10.2 T14：先得到可信的分阶段基线

建议先用正确模板、固定 A1 和固定补丁完成：

| 阶段 | 初始测量点 | 需要解释 |
|---|---|---|
| prefill | 512、2K、8K，固定 chunk | GEMM、attention、conv 与临时空间 |
| plain decode | 已有 1K、4K、约 7K 历史，8K 为当前总容量预算 | 热 kernel、图间隙、每 token 延迟 |
| verify | 支持的小批长度 1–8 | 每新增验证 token 的边际成本 |
| DSpark | 与 plain 相同输入、生成预算 | 草稿、验证、状态成本后的净收益 |

不要混用 score、CLI generate、server 的计时范围。温态 TTFT 定义为请求/输入就绪至第一个对外提交 token，模板、tokenize、排队是否计入要明确；另存 prefill GPU 时间、首 token 额外开销、后续 TPOT 和请求总时间。生成步数、EOS 与 ignore_eos 策略相同。当前 capacity≤8192，不能把 8192 个已消费 token 再接长 decode 当作有效测点；必须给生成、未提交 verify 以及相关 bonus/anchor 约定留出容量，并从实际 Session 的 pos 检查可评估位置。

现有 CUDA events、kbench、Nsight Systems 足够开始。若性能计数器权限本来就可用，再补实际 DRAM/L2 指标；**权限不足则记为 N/A，不为 profile 修改驱动配置**。编译器的寄存器/静态资源报告和源代码字节估计可以用于筛选，但不能伪装为硬件计数器实测。

### 10.3 建议的内核实验顺序

| 顺序 | 候选 | 首个实验 | 继续条件 |
|---|---|---|---|
| K1 | NVFP4 GEMV 软件解码与访存 | 真实热点形状，现有行数/展开参数小范围扫描 | 原算子通过且端到端有收益 |
| K2 | Q8_0 小形状路径 | T=1 与 T=2–8 分别比较 MMA/dp4a | 不靠 dtype 改动换取隐藏误差 |
| K3 | controller / mix / conv | 只融合时间线中仍独立且可安全合并的操作 | 状态更新顺序与数值门不回退 |
| K4 | attention split 数 | 按有效长度与 capacity 测空 CTA、split/merge 成本 | 多个长度均无明显退化 |
| K5 | verify 的数值一致性 | 相同 token 在不同小批形状中的结果 | 能解释并控制接受率变化 |
| K6 | 新 fragment / Tensor Core 路径 | 一种真实 MoE 形状，显式计入新布局成本 | 值得扩到整模型 |
| K7 | FP8 重编码 | 只对已证实有算力瓶颈的局部 Q8_0 部分 | 同时得到质量与时间收益 |

K1–K5 优先利用已存在机制。K6/K7 是后续候选，不应为了“底层先进”提前重写整个执行器。

### 10.4 自动化调优可以很小

当前只需要一个有限候选列表、一个可重复运行器和一张结果表：

`op、shape、dtype、pass、batch、context、candidate、registers、shared_bytes、latency、error、peak_bytes`。

流程为：

1. 从真实 profile 提取一个热点；
2. 为这个热点定义少量合法候选；
3. 先正确性，再资源约束，再计时；
4. 在代表形状上筛选；
5. 回到完整 forward 测净收益；
6. 保留基线，失败可直接回退。

停止条件继续沿用原项目纪律。只有某个候选跨多形状持续有效，才把它整理为稳定实现。不必建设通用自动编译器、在线调优服务或多硬件后端。

### 10.5 循环模型特有的硬件研究

可在 R3 数据基础上试三类小问题：

- 同一 token 不同 pass 的专家集合是否导致可预测的访问热度？
- 小批 verify 的 expert union 是否让高接受率策略反而更慢？
- 第一遍与后两遍的 controller/message 工作量不同，是否值得分别选择固定执行形状？

固定深度 R=1–5 可以各自拥有明确的执行图。逐 token 动态深度涉及缺失状态和分支，应等 R6/R9 的数据支持后再做。不能为改善权重复用而改变有依赖的层/遍顺序。

## 11. 长上下文：先修结构，再研究压缩

### 11.1 先拿到无需近似的容量收益

每个 visit 的 FP16 KV 每 token 为：

\[
2 \times 8\ \mathrm{KV\ heads}\times128\ \mathrm{dims}\times2\ \mathrm{bytes}
=4096\ \mathrm{bytes}.
\]

固定三遍时有 40 个 SWA visits、8 个全局 visits。若 SWA 保留 1024 token：

\[
M_{\mathrm{KV}}(T)
=40\times1024\times4096+8\times T\times4096.
\]

按该结构推算：

| 上下文 T | 所有 48 visits 都分配完整 T | SWA 环形、全局完整 | 备注 |
|---:|---:|---:|---|
| 8K | 1.500 GiB | 0.406 GiB | 可先在当前范围验证结构收益 |
| 32K | 6.000 GiB | 1.156 GiB | 不含草稿和临时缓冲 |
| 64K | 12.000 GiB | 2.156 GiB | 同上 |
| 128K | 24.000 GiB | 4.156 GiB | 同上 |
| 256K | 48.000 GiB | 8.156 GiB | A1 常驻时需重新预算 |

这是由已知形状计算的理想稳态容量，不是分配器实测。批次可见窗口暂存、回滚余量、对齐、coda lens 副本、graph、工作区、草稿及 CUDA context 另计。第一列超过 8K 的数字只是同布局外推，不表示当前实现已经支持。

### 11.2 遍数增加也会增加状态，不能只改算力预算

保持同样层结构时：

`visits=12+12R；global_visits=2+2R；SWA_visits=10+10R`。

| R | visits | global | SWA | 128K 时理想 FP16 KV |
|---:|---:|---:|---:|---:|
| 1 | 24 | 4 | 20 | 2.078 GiB |
| 2 | 36 | 6 | 30 | 3.117 GiB |
| 3 | 48 | 8 | 40 | 4.156 GiB |
| 4 | 60 | 10 | 50 | 5.195 GiB |
| 5 | 72 | 12 | 60 | 6.234 GiB |
| 6 | 84 | 14 | 70 | 7.273 GiB |

所以 R1 的深度研究与 128K 研究应先独立开展。不能从三遍 128K 可能容纳，推出五遍/六遍和多套读出缓存也能容纳。

### 11.3 T17 的正确拆分

**第一段：SWA ring。** 在当前上下文范围内实现，验证绝对位置、实际窗口包含关系与回滚。保存写指针不足以恢复被覆盖的旧值；要根据最大未提交长度设计余量或撤销数据。

还要处理批量写入覆盖：当前层会先为整批写 K/V，再运行该层 attention。连续 C 个 query 的长度 W 窗口，并集最多有 W+C−1 行；单纯 W 行 modulo ring 会覆盖同批早期 query 仍需的数据，即使 C≤W 也不安全。应选定额外 staging/容量，或按依赖交错写读的 tile 方案，并用逐 token 完整缓存作为对照。以 W=1024、C=512 为例，40 个 SWA visits 的窗口并集比稳态多约 79.84 MiB；这只是该方案的额外可见数据量，投机回滚保护还要另外核算。[S12]

**第二段：扩展已有 split attention。** 将有效长度、物理 capacity、绝对 token position 分开；逐处检查 MAX_CTX clamp、索引类型、scratch 大小和 graph 捕获。

**第三段：长 prefill 与参考。** 分块产生缓存，并验证不同 chunk 的模式内一致性；重点检查 relative bias、全局位置缩放、sink、门控和短卷积。

**第四段：16K→32K→64K→128K。** 每一步记录峰值显存和时间；外部参考无法执行的范围，明确标成参考受限，不能把“可以分配”写成“已验证能力”。

当前 llama.cpp 的 indexed-bias CUDA PR #33063 有望帮助参考路径，仍须按具体提交单独验证，不能自动升级当前固定 oracle。[S33]

### 11.4 边界测试应针对真实状态风险

最值得保留的小集合：

- 窗口边界 1023/1024/1025；
- 完整绕环前后；
- prefill 分块大小 1、一个非整齐值、常规值；整批先写后读时，专门验证同批最早 query 的历史未被覆盖；
- verify 接受 0、部分、全部；
- 环形覆盖发生之后的拒绝与回滚；
- 相同前缀 reset 后重算；
- 相同前缀但不同有效长度，检查旧状态是否泄漏；
- 全局 near/far 拆分时，sink 只参与一次归一化。

新实现的 attention 应与当前相同 KV 上的参考计算比较。不同内容的 KV 或不同 cache 策略，不能用同一个“实现一致性”测试掩盖。

## 12. KV 压缩的新取舍

### 12.1 LoomKV 从核心系统方案降为局部参考

LoomKV 对无损编码布局、压缩态 attention 和真实分配收益有启发。但它的重点是 GPU/DRAM/SSD 多级服务缓存；这不应成为当前 Inkling 单模型实验室的主线。[S34]

更关键的是：**Astral 当前 KV 是 F16；LoomKV 的主要统计与编码设计针对 BF16/FP8。** 二者不能互换。将 F16 先转 BF16 再无损压缩，对原始 F16 已经是有损变换。

当前只值得先做一个小实验：

1. 从实际 attention 写入点采样 K/V；
2. 按物理层、pass、head、K/V 分别统计位模式；
3. 对 F16 的符号/指数/尾数以及跨 token、跨 pass 的 XOR delta 测熵；
4. 编码后逐 bit 往返；
5. 计入 metadata、fallback、工作区和分配粒度；
6. 只有净显存收益与恢复成本值得，才研究 fused decode。

不要直接继承 0.71 的压缩比例，更不要借它推算当前 4090 一定获得 40% 容量提升。

GAAC、SplitZip、ZipFusion 可作为 codec 与融合设计参照；现有后端对 dtype、SWA、sink、scale、投机 batch 的限制需要逐项核对。当前不引入 RAM/SSD cache tier。[S35] [S36] [S37]

### 12.2 新增 SRFT 论文：更贴近 Inkling，但不是无损结论

新检索到的 `arXiv:2611.29092v1` 及作者仓库 `aminems/inkling-1m-mlx`，直接针对 Inkling 的 NoPE、有限 relative-bias 范围和 V 归一化设计低位 KV。值得借鉴的重点是“远历史压缩、近窗口保真、同一 KV 服务三个 query head”。[S38] [S39]

需要保留四个限制：

- 实验平台是 Apple M6/Metal，不是 4090/CUDA。
- 低位 SRFT/Lloyd–Max 是**有损量化**；PPL 没下降不构成位级无损证明。
- 256K–1M 的计时使用直接填充 cache；作者 benchmark 的代码确实生成并重复填入合成 K/V。
- 质量实验主要是短语料 PPL 和到 32K 的少数 passkey，不能证明 1M 真实长提示的质量。[S38] [S40]

所以它应进入“模型特定 KV 量化研究”，不应直接变成下一版的默认缓存格式。

### 12.3 在 Astral 上迁移的第一步已有源码依据

本次独立核对了 V 的真实写入路径：

`short conv → per-head RMSNorm（无 learned gain）→ F16 cache store`。[S15]

这支持研究 scale-free V 量化。但有 epsilon 和 F16 舍入，缓存中的 RMS 不严格等于 1。要先测实际 stored-F16 的范数分布，不能把理想公式当成精确事实。

建议先在离线固定 KV 上比较：

| 方案 | 目的 |
|---|---|
| F16 原始 | 真正的表示基准 |
| 简单 K8/V8 或已有可解释低位方案 | 建立普通量化对照 |
| K3/V3、K3/V2 的旋转量化 | 测 K 与 V 的不同敏感性 |
| K2/V2 | 仅作为激进候选，后测 |

旋转前后需验证内积保持的数值误差；量化后的 attention 与“解码回同一组量化 K/V 再做参考 attention”比较，判断内核误差；再与原 F16 比较，判断量化误差。**这两种误差必须分开。**

### 12.4 远近分段的可迁移机制

若确认当前模型的 relative bias 在远处为零，可以把全局层拆成远 prefix 与近窗口，各自产生 softmax 归一化统计，再合并输出。近窗口负责 relative bias 与 sink，注意 sink 只计算一次。

这只是计算分解；原始 KV 时可验证同数学语义。远 prefix 再量化后，则是新的有损模式。对三个共享 KV 的 query heads，解码一次后复用 K/V 的思路值得做 SM89 实验，但寄存器压力、shuffle 和 tile 形状需要重新测量。

### 12.5 KV 压缩的停止条件

满足以下任一情况就暂缓工程化：

- 结构性 SWA ring 已经解决目标上下文容量，压缩没有实际需要；
- 包含工作区后净节省很小；
- 原始模式并非 KV 带宽受限，解压反而增加延迟；
- 真实代码/中文/长依赖上的质量损失不可接受；
- 需要额外复制整套长缓存才能读出或回滚，抵消收益。

先得到“当前不值得”的结论，同样能减少后续无效工作。

最先借鉴的是 reference readout 和 cache 结构。只有早读出的可用率与 coda 成本实测支持时，才值得继续 2D 调度。不能把其他模型、H100/L40S/A100 上的峰值收益套到 A1+4090。

### 13.3 PR51161 仍不是“免费提速”的证据

作者的 A100 短测试中，缓存明显下降，但动态缓存速度相同，静态缓存更慢。这个 PR 主要提供一种缓存语义与容量实验，不能直接证明 4090 decode 加速，也不能从一个 token 一致样本推出一般无损。[S27]

对本项目最有价值的是精确定义“读末遍历史、当前遍自己写”的变体，并测试 prefill chunk、长生成与局部误差。

### 13.4 LoopCD、ARLoop 与新的推测研究

| 研究 | 迁移价值 | 不能省略的条件 |
|---|---|---|
| LoopCD，2610.02185 | 早晚循环表示的质量引导 | 它改变目标分布；Inkling 需完整 coda 读出 |
| ARLoop，2611.05234 | 深度残差/窗口及训练对照 | 属于独立训练架构证据，不能原样改现有模型 |
| LoopSpec，2609.17184 | 早深度自投机和最终验证 | Inkling 额外 coda 成本、proposal 与回滚 |
| LoopCache，2611.24301 | draft 可近似、target 验证保持正确历史 | 不把 draft 的近似 cache 用作最终 target |
| Late Entry，2611.24576 | 当前深度和历史深度解耦 | 部分方案需要训练，greedy 与 sampling 保证分开 |
| PackLoop，2611.30205 | 在已读取的 KV 行中组织多个位置 | 主要面向并发；当前先借测量方法 |
| Loop Behind，作者研究 | 2×2 因果分析和延后计算 | 其他模型的发现，需 Inkling 复现 |

优先级应由 R2/R7/R9 的小实验决定。没有必要为追逐这些论文的峰值数字，提前实现复杂并发调度。[S31] [S32] [S44] [S45] [S46] [S47] [S48]

### 13.5 CUDA Rust 和“可证明安全内核”应如何保留

此前的代码快照结论需要更新。2026-11-26 查询到 CUDA Rust main 已为：

`97f61aef627d3dcdfb60214f1b287d3256a2e2a0`。

当前 proof preview 已扩展到共享内存阶段、竞争、uniform barriers，以及部分 cluster/TMEM 生命周期等内容；“只验证一维写入”已经不准确。但浮点数学没有包含在该安全证明中，编译器与运行时仍有可信边界。[S49]

对当前实验室的合理用途是：选一个小型布局/索引/codec 内核，试验边界、别名和状态安全约束。**不建议把 Astral 全部 CUDA 重写成 Rust kernel。** B200 上的性能、Blackwell 指令和安全证明都不能替代 SM89 的数值与速度测量。原来的可证明 GPU 内核文章可保留为方法背景。[S50]

### 13.6 当前不应恢复的范围

| 方向 | 暂缓原因 | 重新考虑的触发条件 |
|---|---|---|
| 全套 GPU/RAM/SSD KV tier | 当前目标是单模型研究，尚未证明复用/驱逐是核心瓶颈 | 明确的多轮重复 prefill 实验需要 |
| 动态专家 offload 平台 | A1 已能全权重驻留 | 新模型或新精度确实超出显存 |
| 多模型统一接口与调度 | 不回答当前循环机制问题 | 第二个模型有明确共享实验需求 |
| 通用自动内核生成平台 | 小型热点候选足以开始 | 已有多个重复的稳定优化模式 |
| 生产业务全量验收 | 用户未要求生产替换 | 用户重新启动部署目标 |
| 无条件扩到 1M | 容量、prefill 时间和质量都需证据 | 128K 的具体研究显示必须继续 |

ZipServ 的权重卸载/解码机制也属于容量压力出现后的候选；它不能因为有消费级 GPU 实验就自动进入当前全驻留 A1 的主线。[S51]

## 16. 下一轮可直接交给 AI 的小任务

下列 RV 编号只是本评审建议的执行顺序，正式采纳后映射回 `07_tasks.md`。不需要另建系统。每个任务只交付输入指纹、最小变更、原始证据、结论和后续建议。

### RV-01：让现有验证能够可靠复判

**目标：** 修复验证代码的确定性缺口，不改变模型实现。

**输入：** 当前 v3 固定快照、原始 T12 结果与现有门槛。

**工作：**

1. 明确 raw logits / log-prob、窗口、KL 截断的统一定义。
2. 新旧口径分别保留；记录为什么数值不能直接复用。
3. 将批准的策略落实到实际判定，避免文档和脚本分叉。
4. 检查预期 case 数、位置数、唯一性、完整性与 finite。
5. 明确总体失败退出状态。
6. 为通过、门槛失败、空日志、截断日志添加最小离线回归。

**完成条件：** 同输入可重复得到同 verdict；空/缺失数据不能通过；新旧策略可追溯；缺少原始 logits 的部分标为待补导出，而不是猜测结果。

**不必做：** GPU 重装、引擎重构、扩大所有 benchmark。

### RV-02：补齐真实助手生成路径的短验证

**依赖：** RV-01。

**工作：** 使用正确 generation prompt、固定 EOS/词表处理，复跑现有小样本；分别走默认 prefill→decode 与全 step；在少量边界保存完整 logits。

**交付：** V5/V6/V7/V8 的覆盖范围、strict token agreement、winner-vs-chosen gap、数值摘要和原始结果。

**完成条件：** 能明确回答“同一策略在已覆盖形状上数值接近到什么程度”，不再用一个 PASS 同时表示严格序列等价和工程容差。

**注意：** 保留旧模板样本和旧结果，不以删除历史数据实现通过。

### RV-03：实现固定三遍的只读探针

**依赖：** 足以支撑固定三遍研究的 RV-02 结果。

**工作：** 按第 7 章输出 block/message/controller/router 的稀疏 trace；先不加可变遍数，不改 cache 策略。

**交付：** trace schema、少量可复现样例、开/关探针对照、graph/eager 对照。

**完成条件：** 关闭探针保持原执行行为；开启探针的数值影响可解释；性能和观测数据分开。

**停止条件：** 探针需要保存所有 token 的全状态才能工作。此时先缩小选点和统计，不扩大平台。

### RV-04：完成第一轮模型机制实验

**依赖：** RV-03。

**只选一个主要问题开始：**

- 最后一遍在什么位置修正答案？
- 异常激活是否影响跨遍 block 读取？
- 路由临界点是否放大量化/算术误差？

先做观察，再选少量位置做可控干预。R2/R3/R5/R8 共用同一批 trace，但每次干预只改变一个因素。

**完成条件：** 给出能被原始数据支持的支持/不支持/不确定结论，包含反例与失败情况。没有性能提升不算失败。

### RV-05：得到正式性能基线，再选一个热点

**依赖：** RV-02；可与 RV-03 的代码准备并行。

**工作：** 完成 T14，分 prefill/plain/verify/DSpark 计时，固定对照条件。先用已有工具，计数器不可用就保留限制。

**交付：** 一张按阶段/形状列出的热点表、一项最值得尝试的 K1–K5 候选。

**完成条件：** 可以说明候选为何可能节省实际时间，并有同 GGUF、同模板、同预算的基线。

**停止条件：** 两轮有 profiler 或计时依据的优化仍达不到项目既定收益要求；记录 NO_BENEFIT，不继续盲扫参数。

### RV-06：使 varloop 的固定深度扫描可信

**依赖：** RV-02 与已下载 A4；按需要复用 RV-03。

**工作：**

1. 核对 A4 配置、张量类型和实际加载后的形状。
2. 明确 R 如何影响 visits、KV、conv、block/message、coda。
3. 先建立 A4 自己的三遍基线，不能借 A1 的 G2 作为它的通过证明。
4. 用局部算子参考与状态不变量核验新映射；独立参考不足时写清限制。
5. 修改循环控制后，原 A1 默认 R=3 路径仍须满足原 T18 的逐位不变回归；不能用 A4 自身基线替代。若提出不同数值合同，单独说明并按原项目规则确认。
6. 扫描 1–5 遍；每个深度重建历史。
7. 以小型确定答案任务形成质量—时间曲线。

**完成条件：** 深度变化可解释，资源与读出均一致；6/10 遍放在独立外推表。

**停止条件：** 新模型加载/状态映射尚不可信，先定位这些问题，不直接用输出质量解释循环机制。

### RV-07：先完成 SWA ring，再扩上下文

**依赖：** RV-02。

**工作：** 在现有范围验证 ring、批次窗口并集和回滚；随后扩展已有 split attention；按 16K、32K 逐步验证。

**交付：** state invariant、边界用例、峰值显存实测、同 KV 的 attention 对照、参考可用范围。

**完成条件：** 容量收益来自真正释放分配，越界和回滚场景正确，完整峰值与预算有解释。

**停止条件：** 只是改常量后能生成几个 token；这不算完成。

### RV-08：用成本模型优化原生 DSpark

**依赖：** RV-02、RV-05；使用 ring 时再依赖 RV-07 的相关回滚结果。

**工作：** 少量合法草稿长度，分代码/自然语言和两个上下文长度；记录真实提交 token、专家 union、draft/verify/回滚成本。

**交付：** 哪些负载启用、哪些关闭；严格/容差一致性的独立结果；保留集上的净收益。

**停止条件：** 接受率提高但总时间没有改善；此时不因为论文更强就继续移植 DFlash2 或 2DSD。

### 第一轮结束时应拥有的成果

不是“所有路线都实现”，而是以下六个明确答案：

1. 现有数值对齐结论是否能按同一口径复判？
2. 正确助手模板下，真实生成与投机路径是什么表现？
3. 哪些 block/message/router 现象在当前 A1 上稳定出现？
4. 第一项因果干预是否支持对循环作用的解释？
5. 真实 4090 热点在哪里？
6. 下一个投入应选深度、内核、KV 还是草稿器？

## 17. 后续 Inkling 系列探索的原则

### 17.1 可迁移的是实验方法，未必是循环优化本身

“同一系列”不意味着所有模型都具有 Mini 的三遍结构。以模型配置和实际 forward 为准，区分可共享算子与模型特定 schedule。

未来模型首先核对：

- 是否存在 core 重复、重复范围和训练深度；
- Attention Residuals 的块定义与 message 来源；
- KV/conv 的状态身份；
- MoE router、激活、scale 和 softcap；
- 原生精度与资产转换；
- coda/readout、草稿器和多模态入口。

这些字段可以是一个小的模型实验记录，不必上升成多模型插件系统。

### 17.2 值得保留的中长期问题

| 方向 | 先做的小实验 | 进入下一阶段的证据 |
|---|---|---|
| 请求级深度选择 | 用现有任务特征预测固定 R 的收益 | 保留集质量—总时间改善 |
| 学习早读出 | 小型 tuned lens 或读出校准 | 比完整 coda 便宜且足够校准 |
| controller/reader 轻量训练 | 先用 R5 找关键通道 | 有明确缺陷、数据与资源预算 |
| pass-aware 精度 | R8 找敏感层/遍次 | 局部高精度的收益大于额外字节与转换 |
| 分层历史深度 | R9 的反事实实验 | 深历史/浅当前有稳定优势 |
| 低位远 KV | 第 12 章固定 KV 对照 | 真实长前缀质量与净收益都成立 |
| 多模态循环机制 | 少量图片输入，固定视觉前处理 | 文本路径稳定且视觉资产受支持 |
| 新规模模型 | 先复核配置、局部形状与容量 | 4090 可开展有意义的小实验 |

涉及学习或微调时，它就成为新的模型研究。量化前后数据、训练数据、目标分布和评估需重新说明；不能继续称为固定 checkpoint 的无损实现优化。

### 17.3 允许组合，但先测交互

在每个独立改动有证据以后，才组合。例如：

- loop 深度 × KV 量化；
- loop 深度 × draft 长度；
- controller 精度 × 路由稳定性；
- attention split × 上下文长度；
- last-history × prefill chunk。

用最小 2×2 对照检查交互，再扩大范围。不要一次把 LoopCD、KV 共享、FP8 路径和新 drafter 全开，然后把总变化归因给某个项目。

### 17.4 本次最终建议

保留当前引擎和资产，先完成 **验证复判 → 固定三遍观测 → 一个机制干预 → 正式性能基线**。之后由数据决定继续 varloop、内核、长上下文还是 DSpark。

R1–R7 的选题值得继续；真正缺少的是足以分离“模型本身、历史状态、数值实现、读出方式”这四个因素的实验设计。把这一点补齐，v3 就能产出有解释力、可重复、后续模型也可借鉴的研究结论。

### 18.4 本次验证做了什么

- 对照固定代码检查验证计算、执行路径和部分状态语义。
- 对判定器做本地合成输入检查，验证空数据假通过、旧 V7 门槛与退出状态。
- 对内存公式做独立计算。
- 核对本次取得的文档包 SHA256 清单。
- 在本地审阅副本运行原包的 17 项工具测试，全部通过；结构检查通过。这些检查不包含 W2 判定的科学有效性，也不等于 GPU 测试。
- 检查本报告的来源链接定义、章节、代码块和任务依赖。
- 没有复跑 4090 的性能、质量、数值测试；本报告中的新增实验均待执行。
- 没有把搜索未发现官方代码表述为“代码一定不存在”；未完整审计的第三方实现只列为研究入口。

关于 stream 补丁：本次阅读的 CUDA 同步语义支持其修复方向；没有形成要求撤回补丁的证据。后续如优化这类同步，应单独测原竞争场景，不能把初始化/上传的时序保证当作可随意删除的性能开销。[S57] [S59]
