# v0.2.16 · 100K decode 顺序依赖与关闭周期快照（PCE0）复测（2026-11-20）

接 [V0216-DECODE100K-NSYS-QUALITY](V0216-DECODE100K-NSYS-QUALITY-20261120.md)。在 4090、端口 18089 上共启动 18 次，生产保持停机。

> **更正（2026-11-20，见 [V0217-MIGRATION-TAILSKIP](V0217-MIGRATION-TAILSKIP-20261120.md)）**：下文"全新服务上 greedy 输出可复现"只对前 400 字符成立。全文比较后，同版本两次全新启动的公共前缀只有 1045～1233 字符，之后仍会分叉。所以重启服务不能代替 teacher forcing 来固定文本。顺序依赖来自文本轨迹的结论不变。

## 结论

1. **顺序依赖的直接原因是生成文本的轨迹，不是草稿策略，也不是 GPU。**
   - **全新服务上 greedy 输出可复现**：A0-F 的 6 次 c100k 前 400 字符全部相同（轨迹 0）；B0-F 的 6 次和 PCE0-F 的 3 次全部相同（轨迹 1）。
   - **跑过 d3k→c32k→f10k 之后，轨迹分散**：42 次序列运行共出现 20 种开头，两版都是如此。
   - **轨迹决定可草稿性**：不同轨迹的草稿接受率在 0.65～0.80 之间。所以上一份报告里"全新服务 B0 快约 8%"只是两条固定文本之间的比较，不代表版本差异。
   - **推断（未直接验证）**：前序请求改变了专家缓存和自适应层的状态，同一专家在 VRAM、CPU 或 PCIe 上计算会有细微数值差异，从而改变 greedy 路径。要证实，需要做 logit 级对照。
2. **lookup 草稿策略不是原因。** v0.2.16 的 serve 默认开启 suffix/lookup 草稿，策略对象跨请求学习。但逐窗口追踪显示，c100k 中 lookup 窗口只占 3.9%～7.4%。关闭它（SD0 = B0 + `--suffix-draft 0`）后，序列下 c100k 的 avg T 和速度与 B0 同档。
3. **"B0 在序列下慢约 5%"只算弱结论。**
   - 合并所有序列运行的 c100k：A0 中位 133.2 tok/s（n=14），B0 中位 126.5 tok/s（n=18）。
   - 本轮 3 对中 B0 反而更快：中位 136.2 对 132.8。
   - 因为两版文本不同，无法排除文本可草稿性的影响。所有运行中单窗口的 GPU-reach（8.6～9.4 ms）两版相同。
   - 要得到可信的版本速度差，需要固定文本（teacher forcing）或每臂 ≥20 条不同轨迹。
4. **不采用 PCE0（`--prompt-cache-every 0`）。**
   - 序列下 c100k 无收益：本轮 PCE0 127.4/133.2/141.7 对 B0 129.6/136.2/139.4；screen 的 3 次也无收益。
   - 只有全新服务第一段有收益（同为轨迹 1：148 对 135 tok/s），预热后消失。
   - 代价确定而且很大：中途分叉无法复用前缀（见第 3 节）。

## 1. 方法

`seqtrace.py`，计划顺序：

```
A0:S B0:S PCE0:S SD0:S B0:F A0:F | A0:F B0:F SD0:S PCE0:S B0:S A0:S | A0:S B0:S PCE0:S SD0:S B0:F A0:F
```

- **S 段**：campaign 的 d3k(1536) → c32k(256) → f10k(512，复用 31472) → c100k(1024)，接着两个分叉请求 fork60 和 fork90。分叉请求取 c100k 用户内容的前 60% / 90%，换一个短问题，max 64。
- **F 段**：只跑 c100k。
- **采集**：每段都开 `STRATA_SPEC_TRACE`，逐窗口记录位置、T、接受数、是否 lookup、草稿概率和已提交 token。v0.2.3 的 serve 路径不支持该追踪，A0 只有 decode timing 汇总。`STRATA_TRACE_ADAPT` 在 serve 路径下没有输出。
- **轨迹分析**：合并本轮和此前 campaign、proto 的所有 c100k SSE 文本（57 条），按前 400 字符分组（`TRAJECTORY.json`）。

### 2.3 轨迹（c100k，前 400 字符分组）

| 条件 | 运行数 | 轨迹 |
|---|---|---|
| A0 全新服务（proto + 本轮 F） | 6 | 全部为 0 |
| B0 / PCE0 全新服务 | 9 | 全部为 1 |

两两公共前缀的中位数只有 38 字符，即固定前导之后很快分叉。按轨迹分组后，同一轨迹内不同臂之间仍有差异，但每组样本太少（1～5），不做版本结论。

## 3. 关闭周期快照的分叉复用代价

| 臂 | fork60 复用 / 重读 token | fork60 读入 ms | fork90 复用 / 重读 token | fork90 读入 ms |
|---|---|---|---|---|
| A0 | 49152 / 10954 | 4562～5173 | 81920 / 6506 | 4666～5158 |
| B0 | 48891 / 11215 | 4267～4309 | 81485 / 6941 | 4285～4391 |
| SD0 | 48891 / 11215 | 4266～4284 | 81485 / 6941 | 4305～4334 |
| PCE0 | 0 / 60106 | 13355～13422 | 0 / 88426 | 19803～19932 |

- 3 次完全一致。
- 关闭周期 checkpoint 后，Qwen Next 的 GDN 循环状态无法截断，在 prompt 中途分叉就只能从头重读：60% 处多花约 9.1 s，90% 处多花约 15.5 s。
- 在 Pi/agent 场景中，编辑或压缩历史、重新生成都会在中途分叉，这个代价是确定的；而 PCE0 的收益只在全新服务、固定文本下出现。
