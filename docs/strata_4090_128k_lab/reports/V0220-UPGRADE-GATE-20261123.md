# v0.2.20 升级评估（2026-11-23）

接 [v0.2.19 评估](V0219-UPGRADE-GATE-20261122.md)。上游 11-22 发布 v0.2.20（engine 0.1.66）。按当时定的低成本方案在 4090 上执行：prepare（不停机）加 40 题测速；同题端到端速度比 B2 快 4% 以上，才进入 KL 门和完整任务门。

## 结论

1. **不升级，也不进入完整门。** 采样方式与 B2 对齐后，v0.2.20 在同样 40 题上端到端 117.7 tok/s，B2 为 130.6，慢 9.9%；引擎 decode 为 122.0 tok/s。
2. **第一次测得的"快 4.4%"是采样方式变化造成的，不是引擎变快。**
   - v0.2.20 的服务端改动 #6536：模型带 MTP、请求又没给采样参数时，不再套用模型卡片的采样（thinking：temperature 1.0 / top_p 0.95 / top_k 20 / presence 1.5），改为 greedy。
   - gate 的请求不带采样参数，所以第一次测速全部走了 greedy。<4K 段草稿接受率从 0.643 升到 0.775，每窗口产出的 token 增加 32%。
   - 对齐采样后接受率回到 0.643，与 v0.2.19 相同；速度优势随之消失。
3. **变慢的部位是 GPU 侧。**（数字来自 prodlog，同 40 题，均为卡片采样）
   - CPU 侧确实改善：4K–32K 段每窗口 CPU 条目从 4.0 降到 2.59，命中率从 88.7% 升到 93.0%，方向与上游 #4870 声称的"命中率 +8%"一致。
   - 但 GPU 部分（reach）从 8.02 ms 升到 9.41 ms（+17%），<4K 段从 7.88 升到 8.41（+7%）。每窗口总时间两段分别 +4% 和 +12%。
   - 推断（未验证）：#4870 把这类缓存覆盖率（40%）下的自适应参数从"每 4 窗口换 96 个、衰减 0.70"改为"每 2 窗口换 192 个、衰减 0.92"，单位时间换入的专家字节约为原来的 4 倍。这些拷贝与 PCIe 分担共用链路，而且一层要等自己的拷贝到齐。
4. **以后任何升级都要注意 #6536。** 如果真实 Pi 请求同样不带采样参数，直接升级会把生产的采样方式悄悄改成 greedy。Pi 是否带采样参数未核实：服务端不记录请求体。v0220 补丁加了开关 `STRATA_MTP_GREEDY_DEFAULT=0`，可恢复 v0.2.17 的行为。

## 结果（同样 40 题，端到端 completion tok/s）

| 臂 | 采样 | 端到端 tok/s | 引擎 decode tok/s | 首次 / 最终通过 |
|---|---|---|---|---|
| B2（v0.2.17，生产） | 卡片 | **130.6** | —（整臂 134.7） | 15 / 34 |
| v0.2.19，VDH=0 | 卡片 | 129.9 | 134.6 | 16 / 31 |
| v0.2.20，VDH=0，LAG=1（#6536 生效） | greedy | 136.4 | 142.4 | 21 / 33 |
| **v0.2.20，VDH=0，LAG=1，卡片采样** | 卡片 | **117.7** | 122.0 | 16 / 36 |
| v0.2.19 默认（参考） | 卡片 | 115.7 | — | — |
| 精确路由 ts0（参考） | 卡片 | 115.0 | — | — |

VDH 即 `STRATA_VERIFY_DEVICE_HITS`，LAG 即 `STRATA_ADAPT_LAG`。v0.2.20 对 24 GB 的 4090 仍默认打开 VDH，还新加了默认 `ADAPT_LAG=2`，这两个都会关掉生产在用的自适应 overlap，所以两组 v0.2.20 都显式设为 VDH=0、LAG=1。

v0.2.20 已从 4090 的默认配置里去掉 `L2_PF` 和 `QFUSE`（启动日志列出 8 个默认开关）。所以上次对 v0.2.19 提出的"去掉这两个可能更快"的猜测，在 v0.2.20 上已经包含在内，结果仍然更慢。

**每窗口数据**（同 40 题，卡片采样的两臂）：

| 段 | 指标 | v0.2.19 VDH=0 | v0.2.20 卡片采样 |
|---|---|---|---|
| <4K | 接受率 / 每窗口 token | 0.643 / 1.89 | 0.643 / 1.86 |
| <4K | 每窗口 ms / GPU-reach ms | 14.13 / 7.88 | 15.76 / 8.41 |
| <4K | CPU 条目 / 命中率 | 1.15 / 94.8% | 0.90 / 95.9% |
| 4K–32K | 接受率 / 每窗口 token | 0.898 / 3.54 | 0.893 / 3.56 |
| 4K–32K | 每窗口 ms / GPU-reach ms | 23.32 / 8.02 | 24.24 / 9.41 |
| 4K–32K | CPU 条目 / 命中率 | 4.00 / 88.7% | 2.59 / 93.0% |

greedy 那一臂 <4K 段：接受率 0.775、每窗口 2.46 token、每窗口 17.85 ms，GPU-reach 8.96 ms。

## 过程

`upgrade_gate.py prepare` 跑了三次，每次都通过（单测 492 项 OK，`-j 4` 编译约 390–434 s）。三次的记录都保留在 [attempts/](../evidence/v0220-upgrade-gate-20261123/attempts/)。

1. **补丁。**
   - v0.2.19 补丁能原样打到 v0.2.20 上（`-F0`，只有行偏移）。
   - v0.2.20 让 `native_gu_fused_kernel` 多支持了 7 种 Split 格式（8、10、11、14、20、29、42），这些格式和原来的 12、13 一样没有 `DotG`。CUDA 12.3 编译时，同一处错误会扩大到 9 种格式。
   - 修复：给 9 种格式都补上永不执行的占位特化，每个都带 `static_assert(kSplit<T>)`，由编译器保证它们只出现在 Split 分支不会走到的位置。
   - PT0/#1536 的改动行与 v0.2.17 版相同。
2. **第一次（attempt1）：测速走了 greedy。** 加上 VDH=0、LAG=1 测 40 题，得到 +4.4%。随后发现 #6536 让请求改成了 greedy，这一结果作废，记录保留。
3. **加开关。**
   - 在补丁的 `server.py` 中加了 `STRATA_MTP_GREEDY_DEFAULT=0` 开关，恢复卡片采样（新增 `mtp_greedy_default()`，两处调用点各加一个条件），并在 `test_model_card_sampling.py` 中补了对应单测。
   - 第二次（attempt2）只从服务进程的环境变量读这个开关。冻结的 gate 驱动把 `--env` 只写进配置的 `env` 块（传给引擎），服务进程环境里没有它（`/proc/<pid>/environ` 已核对），所以跑了 1 题就中止。
   - 同一轮里，这条单测原先的一个预期写错了（显式 `temperature=0` 时 v0.2.17 的逻辑仍带上卡片里的 top_p/top_k），已改为与上游同款断言。
4. **第三次（最终补丁 [v0220-pt0-reply-reuse.patch](../patches/v0220-pt0-reply-reuse.patch)）。**
   - 开关先从引擎的启动环境读（配置 `env` 块，生产的其他 STRATA 开关也在这里），取不到再读服务进程环境。
   - `serve.test_model_card_sampling` 13 项 OK，在启动测速之前跑。
   - 测速服务起来后读 `/props`，默认参数为 `temperature 1.0, top_p 0.95, top_k 20`（[props-check](../evidence/v0220-upgrade-gate-20261123/props-check.txt)），确认开关生效。
5. 三次编译的内核源码相同，但引擎 sha256 各不相同（`72526772`、`e9c577ac`、`f9b2602c`），说明构建不可逐位复现。新树身份以最终的 [PREPARE.json](../evidence/v0220-upgrade-gate-20261123/PREPARE.json) 为准。

**停机**：生产共停三段，分别为 21:27–21:58（attempt1 测速）、22:13–22:14（attempt2 中止）、22:25–23:04（最终测速），时间均为美东。每段结束后自动恢复，health 200。11-22 11:29 之后 Pi 请求数为 0（[prod-idle](../evidence/v0220-upgrade-gate-20261123/prod-idle.txt)）。

## 局限

- 每臂只有 40 题，通过数不能用来判断质量；本轮也没跑 KL 门。
- **GPU-reach 上升归因于 #4870，只是推断。** 验证需要给 v0.2.20 加上命令行参数 `--adapt-every 4 --adapt-swaps 96 --adapt-decay 0.70` 再测一次。这些是命令行参数，一键过门的 `--env` 传不进去，需要改树里的配置；另外还要停机约 50 分钟。即使能回到持平，也没有收益，所以没做。
- 一键过门有两个漏洞：
  - **测速对比默认双方采样一致。** 上游改了采样默认值时，它会给出错误的加速，本轮就是靠接受率和 `/props` 才查出来的。
  - **`--env` 只能到达引擎，到不了服务进程。**

  这两点已写入[工具说明](../tools/upgrade_gate/README.md)。
