# 单会话长期追问 Phase：#1536 回复复用 + preserve_thinking 开关（2026-10-25）

**结论（#1536）：在你的实际用法（一个会话长期追问）下，#1536 消除了追问时整段重读上一轮回复的现象，off 14 轮中 4 轮重读 → on 16 轮中 0 轮；追问 TTFT 均值 4.87 s → 2.52 s。改动只在 Python 服务层，建议作为下一个生产候选，上线前先做一轮真实 Pi 会话复核。**

**结论（preserve_thinking）：关闭历史 thinking（PT=0）后，同一个 Java 会话在到达上下文上限前能问 12 轮，PT=1 只能问 5～7 轮，约 2 倍；质量链 6 条全部满分，没有测出差异，但题目有天花板效应。代价是每轮追问都要重读上一轮回答正文，TTFT 约 5 s；PT=1 + #1536 约 2.5 s。按你的用法（长期追问、尽量不切换），推荐 PT=0 作为生产候选，难题上的质量还需要用真实 Pi 会话确认。**

## 1. 用法画像与测试形态

- 用法（你的原话归纳）：同一时间只有一个会话，长期追问；不派子代理，不切换，无并发。
- 测试驱动 `session_bench.py`（实验包外，29 `/home/hhtele/strata-lab-4090/`），按 Pi 的请求格式构造：
  - 每轮追加一个约 3K token 的 Java 文件和一个分析问题；
  - `reasoning_effort` xhigh，temperature 1.0 / top_p 0.95 / top_k 20；
  - 历史 thinking 用 `reasoning_content` 回传；
  - 不设 thinking budget（Pi 不发）；
  - `max_tokens` 按 pi-ai 的 `clampMaxTokensToContext` 收缩：`min(32768, 131072 − 估算 − 4096)`。
- 环境：生产停机，GPU 独占，CFG-CSTATE 生效，公共基线 A0 + EXACT6。

## 2. 单会话的基本事实（A0 / PT 默认，已观察）

| 项 | 观察值 |
|---|---|
| 每轮生成 | 约 10～28K token，其中 thinking 约占 2/3 |
| 上下文增长 | 每轮约 15～30K；第 4～5 轮到约 100K |
| decode | 3K 时约 138～145 tok/s，100K 时约 124～137 tok/s |
| 正常追问 | 只读入新消息（约 3K），TTFT 2.3～2.9 s |
| 重读追问 | 回退到上一轮 prompt 末尾的 checkpoint，整段重读上一轮回复（20～31K），TTFT 9～12 s |
| 上限 | 约 5～7 轮后 prompt 超过 100K，Pi 收缩后的 max_tokens 已不够 xhigh 写完；真实 Pi 会在约 114.7K 触发 compaction |

**为什么会重读**：Qwen3.8-next 以线性注意力（GDN）为主，递归状态只能回退到 checkpoint，不能在回复中间截断。下一轮 prompt 由服务端重新渲染并按规范 BPE 编码；只要模型生成的 token 序列不是这段文本的规范编码，前缀就在回复内部分叉，只能回退到回复开头。

- 10 次没有重读的轮次，生成 token 数都等于规范编码长度。

## 4. #1536 的价值与风险

- 收益只在追问时体现：每次避免的重读约 7～9.5 s，按约 29% 的触发率，平均每轮省约 2.3 s。一轮完整回复通常需要 1.5～3.5 min，所以总耗时占比约 1～2%，但最差情况下的 TTFT 从约 12 s 降到约 2.5 s。上下文越长、回复越长，单次重读越贵。
- 输出不变：只改变历史回复的 token 化方式（复用模型自己生成的 id），渲染出的文本相同。
- 风险 / 未覆盖：
  - 客户端改写历史回复时（编辑、截断、Pi compaction 后的摘要），应退回规范编码。上游单测覆盖了这一点（`test_prompt_encoder` 11 项通过），但实机没有测这种情况。
  - 只测了服务端模拟的 Pi 请求格式，没有用真实 Pi 测过。
  - 带工具调用的 agent 会话没有测。
- 建议：真实 Pi 会话复核通过后，作为生产候选，以 `STRATA_REPLY_REUSE=1` 开关上线，回滚只需把它设为 0。

## 5. preserve_thinking 开关

### 5.1 背景与实现

- 29 上的 chat template 中 `preserve_thinking` 默认为 true，所以历史上每一轮的 thinking 都会重新进入 prompt。
- A0 frontend 的 `openai_to_messages` 只透传 `chat_template_kwargs` 里的 `enable_thinking` 和 `reasoning_effort`，`preserve_thinking` 被丢弃；Pi 也不发送这个字段。因此此前 `nobudget-pt-false` 那次运行实际上是默认行为（PT=1）的样本。
- 候选 `lab/cfg-pt@83a68423`，只改服务层 Python（3 个文件，+45 行）：
  - 请求里的 `chat_template_kwargs.preserve_thinking` 可以透传，优先级最高；
  - 请求未指定时，取 `STRATA_PRESERVE_THINKING=0|1` 作为服务端默认值；
  - `enable_thinking=false` 的请求不受影响。
- 单测：`test_frontend` 30 项**已运行并通过**；新增的 5 项中有 3 项在 A0 上**按预期失败**（red）。
- 用真实模板渲染核对过：PT=0 时，历史轮次的 thinking 不再进入 prompt。
- 回执：7 个运行进程的 server 日志都有 `LAB_CFG_PT preserve_thinking default=0|1`，与 arm 一致。

### 5.2 质量：8 轮递增编码链（`chain_bench.py`，PT=1 / PT=0 交替各 3 条）

题目：每轮给 Python `Ledger` 模块加一条需求，要求输出完整模块；用隐藏测试检查需求 1..t 是否全部通过。需求依次为余额、转账、历史、透支额度、快照恢复、手续费、撤销、线程安全。评分器已用参考实现校验：完整实现 8/8，只实现需求 1 的版本 1/8。

| arm | 第 t 轮累计通过 | 第 8 轮 prompt | 追问 TTFT | 追问重读 |
|---|---|---|---|---|
| PT=1 | 3 条全部 8 轮满分 | 54,370 / 94,219 / 56,842 | 正常 0.45～0.78 s | 21 轮中 3 轮，5.2～9.2K，3.2～5.3 s |
| PT=0 | 3 条全部 8 轮满分 | 4,903 / 4,375 / 4,337 | 0.77～2.14 s，随轮次上升 | 每轮读入上一轮回答，0.2～1.4K |

- **质量：没有测出差异。** 6 条链 48 个评分点全部通过，存在天花板效应，只能说明“在这个难度下 PT=0 没有掉分”，不能说明质量等价。
- 两个 arm 后几轮的生成长度都在 25K 左右，说明 PT=0 并没有让模型少想。
- PT=1 的 3 次重读与第 3 节的 BPE 原因相同，#1536 可以消除。

### 5.3 轮数与速度：Java 单会话（`pt0-java` vs PT=1 的 8 个会话）

| 项 | PT=1（`r1536-*` 6 个 + `nobudget-*` 2 个） | PT=0（`pt0-java`） |
|---|---|---|
| 到达上限前完成的轮数 | 5～7 | **12**（第 12 轮时 prompt 108,967，下一轮 max_tokens 不足 1024） |
| 每轮上下文增长 | 约 17～27K | 约 7.5～13K |
| 追问读入 | 正常约 3K；重读时 19～31K | 每轮 7.3～13.1K（新文件 + 上一轮回答正文） |
| 追问 TTFT | 正常 2.3～2.9 s，重读 8～12 s；均值：off 4.87 s，#1536 on 2.52 s | 3.4～6.4 s，均值 4.94 s |
| decode | 124～145 tok/s | 127～150 tok/s |

- **轮数**：PT=0 约是 PT=1 的 2 倍。Java 场景的回答正文本身较长（每轮 1.4～3.5 万字符），所以倍数远小于编码链上的 10 倍。
- **为什么 PT=0 每轮都要读**：引擎的实时状态里包含上一轮的 thinking，而下一轮 prompt 不含它，前缀在 thinking 开头分叉，只能回退到上一轮 prompt 末尾，再读入回答正文。所以在 PT=0 下 #1536 没有收益。
- **速度**：PT=0 的追问 TTFT 均值与 PT=1 off（含重读）基本相同，比 PT=1 + #1536 慢约 2.4 s，约占一轮总耗时（约 2 min）的 2%。decode 主要随生成内容波动，没有看到系统性差异。
- **观察（未解释）**：PT=0 后期 thinking 变短（约 1～2 万字符），回答正文变长（约 2.8～3.5 万字符）。这只是 1 个会话的现象，原因未验证。

### 5.4 DECISION

| 组合 | 能问多少轮（Java 场景） | 追问 TTFT | 质量 | 建议 |
|---|---|---|---|---|
| 现状（PT=1，无 #1536） | 5～7 轮后进入 Pi compaction | 均值约 4.9 s，最差约 12 s | 基准 | — |
| PT=1 + #1536 | 同上 | 约 2.5 s，稳定 | 不变 | 适合短会话和频繁换题 |
| **PT=0** | **约 12 轮** | 约 5 s，稳定 | 编码链未测出差异 | **推荐给你的用法**：长期追问时，推迟 compaction 的收益（避免约 20K 重读和细节丢失）大于每轮多出的 2.4 s |

两项都可以用环境变量开关、即时回滚，也可以同时部署：#1536 在 PT=0 下没有收益，但也没有害处，客户端按请求选择 PT=1 时就会生效。

## 6. 口径说明与更正（2026-10-26 补记）

- **TTFT 口径**：本报告所有“追问 TTFT”都是首个输出事件，开启 thinking 时就是 thinking 首 token，不是正文首 token。它衡量 prefill / 重读，不衡量用户看到正文的等待。v2 验证工具新增 `first_visible_s` 等字段后，后续报告分开记录（见 [测试协议](../docs/04_TEST_PROTOCOL.md)）。
- **评分隔离更正**：5.2 节的 6 条编码链当时在 29 宿主机上用 `python -I` 直接执行了模型生成的代码，违反本包“模型生成代码只在隔离容器内执行”的规则。2026-10-26 已把 `chain_bench.py` 改为 Docker 隔离评分（本地镜像 `python:3.12-slim`，无网络、只读、非 root、限内存 / CPU / PID），并用容器把 48 个评分点重评一遍，结果与原评分逐一相同，结论不变。
- 第 1 节提到的测试脚本已收编进包内 `tools/session/`（[单会话](../docs/11_SINGLE_SESSION.md) 第 4 节）。
