# C01 suffix 二级索引的离线反事实（2026-11-20）

接 [Pi 式负载模拟](V0217-PISIM-20261120.md)。只用 CPU，不启动模型。输入是那次模拟里两个会话的完整记录（公开 Exercism 题，没有用户内容，因此不需要 W09 的内容采集授权）。

## 结论

**NO_HEADROOM，C01 关闭。**

- 在当前 trigram 4-way 索引之外加一张 8-gram 索引，按最乐观的口径（ORACLE_UPPER_BOUND：proposal 总被采用、验证不额外花时间、不计 CPU 和内存开销）只能省 **0.19%** 的 decode 窗口。
  - write/edit 请求（复制和编辑最多）省 0.28%，其他请求省 0.01%。
  - 前进门槛是 max(4%, 2×AA)，差了一个数量级以上，所以不需要再算 CPU 开销和 policy 选择率。
- 原因：旧的长匹配源被挤出 4-way 桶以后，只要再生成一个 token，新的 trigram 就能区分开，又会直接命中那个旧位置。8-gram 只能多拿到最前面那一个 token。
  - 全部 75.7K 个生成 token 中，8-gram 额外找回的只有 134 个窗口、820 个 token（1.1%）。

## 数据

| 范围 | 生成 token | 窗口（现行 A） | 窗口（加 8-gram 的 B） | 节省上界 | 8-gram 找回（窗口 / token） |
|---|---|---|---|---|---|
| 全部 120 个请求 | 75,727 | 26,643.9 | 26,594.2 | 0.19% | 134 / 820 |
| write/edit 请求 | 49,904 | 17,348.2 | — | 0.28% | 116 / 761 |
| 其他请求 | 25,823 | 9,295.7 | — | 0.01% | 18 / 59 |

- **oracle 与实测的对照**：A 在 21.8% 的窗口上有至少接受 1 个 token 的 suffix proposal，覆盖 24.4% 的生成 token。引擎实测只在 7.4% 的窗口用了 suffix 草稿，覆盖 7.5% 的 token。也就是说，现有 policy 已经过滤掉了大部分短匹配（改用 MTP），实际可得的收益只会比上表更小。
- **生成 token 数校验**：按模板近似渲染得到 75,727 个，引擎日志记录 75,073 个，相差 0.9%。

## 方法

- **索引语义**：照 Strata v0.2.17 的 `engine/src/spec/suffix_drafter.cpp` 实现：
  - 历史中的每个 trigram 记录最近 4 个结束位置；
  - 向回匹配最长 64，最短 3，取最长的那个（相同时取最近的）。
  - B 另加一张 8-gram 索引（2 路，因为第 0 路通常就是当前后缀本身），作为额外候选，与 A 的候选一起比较。
- **渲染**：用引擎自己的 `strata_tokenizer` 和 Qwen 模板标记。按 PT0 规则，最后一条用户消息之前的 assistant thinking 不出现在 prompt 里。
  - 历史 = 本请求的 prompt + 本次回复中已生成的部分。生成 proposal 时只看当时已有的前缀；与已录输出逐 token 比较只用来给上界打分。
- **窗口模型**：
  - suffix proposal 至少接受 1 个时，窗口提交 1 + min(接受数, 8) 个 token；
  - 否则按 MTP 计，每窗口 2.475 个 token。这个值来自同一批日志中非 suffix 窗口的实测：(75,073 − 7,818) / (29,343 − 2,173)。
- **自检**：构造一个合成反例。旧源被同一 trigram 的 6 次新出现挤出时，A 先拿到 3 个 token，B 通过 8-gram 拿到 4 个，B 的逻辑按预期生效。
  - 自检最初发现 8-gram 只存 1 路时找回永远为 0（被当前后缀自身占住），改成 2 路后重跑，上表是改后的结果。

## 局限

- 只覆盖一种 agent 负载：两个会话、16 道题、60K 以内的上下文。没有覆盖长文档原样引用这类负载，不过[补遗](../../strata_data_first_rebase_20261120/docs/26_V0217_REBASE_ADDENDUM.md)中文档类负载的 lookup 本来就只占 3.9%～7.4% 的窗口。
- 渲染是近似的（token 数差 0.9%）。不影响量级结论。
