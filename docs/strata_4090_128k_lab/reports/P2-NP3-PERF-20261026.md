# NP-3 P01-02（第一步）：CPU pool 的 perf 与分阶段计时（2026-10-26）

> **更正（2026-10-26，第二步 [P2-NP3-TRACE](P2-NP3-TRACE-20261026.md)）：** 本报告把“引擎 rows 阶段只达 bench 的 72～74%”推断为“每阶段约 17 µs 的 pool 分发 / 同步 / 收尾固定开销”，**这个推断是错的**。
> - 分阶段 trace 实测，pool 的同步（publish、唤醒、claim、re-park、串行量化）合计约 2.5 µs/miss，尾部不均约 5 µs/miss。
> - 其余差距在任务内：gate/up 的 i-quant 点积受计算限制（25～27.5 GB/s），PCIe 同时读内存造成带宽争用。
> - NP-3 的 pool 代码方向因此 NO_BENEFIT。下面保留原文作记录，只有 P01-04 的结论仍然成立。

**结论（原文）：CPU 专家阶段约有 25～30% 的时间不在算，而是花在 pool 的分发、同步和收尾上，这是 NP-3 唯一值得做的部分。**（已被第二步更正，见上）
- **串行中间量化可以忽略：** 每窗口 0.06～0.07 ms，约占 pool 时间的 1%。所以 P01-04（并行中间量化）**不做**，计划里的停止条件已满足。（仍成立）
- **两个 rows 阶段（gate/up、down）偏慢：**
  - 引擎里这两个阶段合计读权重的带宽是 22.4～23.2 GB/s，即 36 GB/s 上限的 62～64%。
  - 同样格式在 bench 的 16 线程吞吐模式下，按层加权约 31 GB/s（nt≈1.15，每 expert 约 56 µs）。
  - 引擎只达到 bench 的 72～74%。~~按每层算，两个阶段合计约多出 34 µs，即每个阶段约 17 µs 的固定开销。~~ 多出的时间主要在任务内，不是固定开销（见更正）。
- **perf 看到的现象：**
  - CPU 专家阶段占窗口 28～37% 的时段里，worker 只有 74～84% 的时间在跑计算内核，其余在 `_mm_pause` 自旋。第二步显示这些自旋主要是尾部和 publish 后约 1.5 µs 的等待。
  - 每个 worker 在 decode 期间 94% 的时间都在 CPU 上（每秒约 1 次上下文切换），从不真正睡眠。
- **收益上限（原推论）：** 如果 CPU 阶段能达到 bench 的吞吐效率，每窗口可省 0.8～2.5 ms，约为窗口时间的 6～11%。第二步表明其中 pool 代码能碰到的只有同步与尾部，约为窗口的 2.5～4.5%。
- **下一步（已执行）：** 给 pool 加低扰动的分阶段计时（P01-02 第二步），结果见 [P2-NP3-TRACE](P2-NP3-TRACE-20261026.md)。

## 3. perf：线程在做什么

**线程级（`perf stat --per-thread`，60 s）**

| 线程 | task-clock | 上下文切换 | IPC | stalls_total / cycles | stalls_mem_any / cycles |
|---|---|---:|---:|---:|---:|
| worker（`strata-pool-0` / `-7`） | 0.943 CPU | 57 / 31 | 0.76 | 64% | 14% |
| host（`strata-host`） | 0.998 CPU | 5,003 | 0.92 | 58% | 17% |

**样本分类（`perf record`，按线程 × 符号）**

| 段 | 时段内的请求 | worker：自旋（`ExpertPool::worker`） | worker：计算内核 | host：计算内核 | host：其他（主要是 `Verifier::run` 等 GPU、MTP draft） |
|---|---|---:|---:|---:|---:|
| perf1（03:25:30～03:26:30） | 3K 思考 / 回答 / 思考 | 76.6% | 22.6% | 25.2% | 71% |
| perf2（03:28:34～03:29:35） | 40K 思考 / 回答 | 68.9% | 29.5% | 33.2% | 59% |

worker 的其余样本（`drain` 自身、内核态）合计不到 1.5%。计算内核按样本从多到少：
- `ggml_vec_dot_iq3_s_q8_K`
- `plain::rows_nt`（Q2_0 down）
- `ggml_vec_dot_iq2_xs_q8_K`
- `ggml_vec_dot_iq4_nl_q8_0`
- `ggml_vec_dot_iq2_s_q8_K`
- `ggml_vec_dot_iq2_xxs_q8_K`
- `ggml_vec_dot_iq3_xxs_q8_K`
- 以及 nt≥2 时的 `plain::row_dot<type, nt>`

**换算到 CPU 阶段（推论）：**
- 按请求的开始时间和各阶段的窗口数，把两个 perf 时段对齐到 decode 计时，CPU 专家阶段分别占墙钟的 27.9% 和 37.4%。
- worker 跑计算内核的时间占墙钟 21.3% 和 27.8%（计算样本比例 × 0.943 在 CPU 上）。
- 所以在 CPU 阶段内，worker 有 74～84% 的时间在算，16～26% 在自旋等待。
- 时段对齐是按请求时间估的，误差约几个百分点。

## 4. 分阶段计时（非 serve 模式汇总）

| 项 | 3K（seed 7） | 40K（seed 7） |
|---|---:|---:|
| verify：等 GPU / pool / host（ms/round） | 7.91 / 5.28 / 0.10 | 7.89 / 6.69 / 0.02 |
| pool multi：gate/up / quantize / down（ms/round） | 3.463 / **0.062** / 1.843 | 4.077 / **0.070** / 2.179 |
| rows 阶段的权重带宽 | 22.4 GB/s（62%） | 23.2 GB/s（64%） |
| CPU pool 调用（ms/round） | 5.171 | 6.662 |
| CPU 专家/层，路由条目/层 | 1.35 / 1.55 | 1.75 / 1.99 |

注意：
- 3K 的 prompt（3,033 token）低于分担门槛 3072，prefill 也用了 pool，所以它的 gate/up + down 被 prefill 时间稍微抬高：三项之和 5.37 ms，大于 pool 调用的 5.17 ms。
- 40K 的 prefill 全部走流式，不经过 pool，下面的换算用 40K。

40K 换算：
- **quantize：** 0.070 ms，占 pool 调用的 1.1%。
- **gate/up : down = 65 : 35：** 与读取字节比（gate + up 是 down 的两倍）一致，两个阶段都受读权重的速度支配。
- **每个 miss：** 6.662 ms ÷（1.75 × 48 = 84）= 79 µs。bench 下限按 nt=1.14 插值为 56 µs（[#3871 成本表](P2-PR3871-20261026.md)，10 种组合按层加权），引擎是下限的 1.41 倍。
- **按层：** 每层平均 139 µs，下限约 98 µs，多出约 41 µs；扣掉阶段外的约 7 µs（pool 调用比两个阶段之和多 0.33 ms/round），两个阶段合计多约 34 µs，各约 17 µs。用带宽算是同一个数：两个阶段每层 130 µs，按 bench 的 31 GB/s 应为 96 µs。（这是相对 bench 的差额，第二步显示它主要在任务内。）

两种方法（perf 的在阶段内计算占比、计时汇总和 bench 的带宽比）都指向 CPU 阶段比 bench 慢 25～30%。（第二步更正：慢的主要是任务内，不是“不在算”。）

附带观察（不在 NP-3 范围内）：
- 15 个 worker 在 decode 期间始终 100% 自旋，`kSpinBeforeSleep` 为 20 ms，而窗口间隔远小于它。
- 4216 是服务器 CPU，频率稳定在约 2.57 GHz，自旋没有观察到对 host 线程频率的影响。在功耗受限的平台上这会是个问题，本机不是。
