# 累计收益汇总与上限分析（2026-10-26）

**范围更正（2026-10-27）：** 本篇累计墙钟约 −9%、decode 约 +10%（从 10-12 算约 +23%）均为历史分项折算 / 相乘的推算，不是当前完整生产组合的实测。只比较 KVRES 在当前完整组合中增量的 [补充组合实验](P3-COMBINATION-KVRES-20261027.md) 已完成：6 对、276 请求中的 8 个定长性能主指标 CI 均未达 4% 门，正式采用门未通过，质量非劣未建立；64K / 100K 样本含前缀复用，不能称完整冷读。原正式回放失败与独立 4/4 同错保留；实际恢复有回执但两臂各六个长检索均未通过精确答案检查；Python 全链成功率关闭 2/2、开启 1/2，样本不足以因果归因。后续增量不能直接乘回本篇累计数字，旧历史部署决定也不替代本轮验收。

**结论：到 10-26 上线的配置为止，按你的用法（单会话长期追问），一轮追问的墙钟约快 6%（4～8%），几乎全部来自 decode。另外两项收益不体现在墙钟上：同一会话能问的轮数约 2 倍（PT=0）；最差的追问 TTFT 从 9～12 s 降到约 4～6 s。从 10-12 本轮优化开始算（含 0.1.43.1 的 overlap +12%），decode 累计约 +19%（推算，未在真实流量上复核）。**

**v2 复查补测后（第 4 节）：** 只有 CFG-KVRES 一项过门，10-26 21:38 已写入生产配置并冒烟通过（[DEPLOY-KVRES](DEPLOY-KVRES-20261026.md)），生产随后按要求重新停机。它让每轮再省约 2.5%～3.8%，累计约 −9%（−7%～−11%），decode 累计约 +10%（从 10-12 算起约 +23%），全部为推算。

收益不多，有三个原因：
1. 一轮追问 96～98% 的时间在 decode。prefill / TTFT 方向的改进相对幅度都很大（−12%～−48%），但乘上 2～4% 的权重后，对墙钟的贡献约 1%。
2. decode 窗口里没有可以单独拿下的大块：
   - GPU 约占一半以上，分散在每个窗口约 2,360 个 kernel 上，最大一项不到 GPU 时间的 9%；
   - CPU 专家约占 36%，时间花在专家计算本身和 2 通道 DDR（与 PCIe DMA 共用）上，调度层面没有可回收的开销。能减少它的办法只剩“让更多专家进显存”，这正是 CFG-KVRES 过门的原因；
   - CPU、PCIe、GPU 三者互相让渡：一边省下的时间，另一边多等回来。
3. 剩下杠杆最大的软件手段都会改变数值（更激进的 tail skip、低比特 KV / 权重、专家延后），与“Java 任务质量优先”冲突，没有进默认路线。

## 2. 折算到一轮追问

用 P1 实测的单会话形态：每轮生成 10～28K token（约 2/3 是 thinking），一轮 1.5～3.5 min；decode 3K 时 138～145 tok/s、100K 时 124～137 tok/s。

| 指标 | 本包开始时（10-23：0.1.43.1，PT 默认保留，无 #1536） | 现在（10-26 上线配置） | 性质 |
|---|---|---|---|
| decode 速度 | 基准 | 约 +6%（EXACT6 × CSTATE，两者叠加约 1.04～1.08） | 实测分项相乘，组合未单独测 |
| 追问 TTFT 均值 | 4.87 s（含 29% 概率的整段重读） | 约 4 s（PT=0 的 4.94 s 中，超过 8192 的读入按 0.73× 折算） | 推算 |
| 最差追问 TTFT | 9～12 s（重读 20～31K） | 约 4～6 s（PT=0 每轮只读 7～13K） | 实测区间 + 推算 |
| 一轮墙钟 | 基准 | 约 −6%（−4%～−8%）：decode 贡献约 5～6 个百分点，TTFT 约 0.5～1 个 | 推算 |
| 同一会话的轮数 | 5～7 轮到上下文上限 | 约 12 轮 | 实测（编码链） |
| 冷读 32K～123K | 基准 | −30% | 实测 |

- **不在墙钟里、但对你更重要的一项是会话轮数。** 轮数翻倍意味着 Pi 的 compaction 少一半：每次 compaction 要一次摘要轮，再加冷读摘要，并且会丢细节。
- PT=0 下上下文增长慢约 2/3，同一轮次的上下文更短，decode 也会略快（100K 比 3K 慢约 8%）。**推断**，没有单独测。
- 从 10-12 算起，decode 约 1.12 × 1.06 ≈ +19%。10-16 真实流量在 0.1.43.1 上是 129.0 tok/s，按此推算现在约 137 tok/s。真实流量还没有（新配置上线 20 分钟后就停机测试了），**未验证**。

## 3. 为什么 decode 只多了约 6%

### 3.1 一个 decode 窗口的构成（A0，实测）

| 来源 | 构成 |
|---|---|
| [DIAG](P0-T5-DIAG-20261025.md)（长上下文混合负载，18.5 ms / 窗口） | verify 90%：等 GPU 9.4 ms（51%）+ CPU 专家池 6.6 ms（36%）；MTP draft 1.6 ms（9%）；adaptive wait / join / commit / other 合计 <1.5% |
| 本次 base 臂（4K 上下文，greedy，13.06 ms / 窗口） | GPU-reach wait 8.20 ms + per-layer host 2.96 ms（其中 CPU 专家 2.47 ms）+ stage 0.15 ms；每窗口 9 次 adaptive swap |
| [nsys](P0-T7-NP0-20261025.md)（GPU 时间构成） | 每窗口约 2,360 个 kernel，窗口内 GPU 空闲约 1.2%。GPU 自旋等 CPU 专家结果（`wait_flag_ge_kernel`）17.5%；从映射内存取专家 11.1%；专家 gate/up 8.1%；dense 投影 8.1%；GR down 7.1%；其余每项 ≤5.5% |

### 3.2 每一块都测过什么、上限在哪

| 块 | 占比 | 已测的手段 | 结果 | 为什么到头 |
|---|---|---|---|---|
| GPU 计算 | 约 50～60% | EXACT6（6 个 exact kernel 开关）、IL 表、Ada MMVQ 表（#3453）、CFG-IL0 | EXACT6 −5%，其余 0 | 没有主导 kernel。单个 kernel 提速 20% 也只省窗口的 1～2%，而 kernel 开发是 XL 工作量（v2 O20～O32） |
| CPU 专家 | 约 36% | NP-3（pool 切分、任务数 16～192）、#3871 成本表、NP-1a、POOL8 | 都在 ±1.5% 内或变差 | 每个 miss 约 76 µs，基本都花在任务内（gate/up 受计算限制，并且与 PCIe DMA 争用 2 通道 DDR）。调度开销约 2.5 µs，无可回收的部分。即使吃满 36 GB/s，上限也只有约 −15%，而实际已在 20 GB/s 左右 |
| CPU / PCIe / GPU 分工 | — | `--pcie-frac 0.30`、`STRATA_PCIE_BALANCE=1`、O07 分析 | +0.3～4%（未过门）、0～2% | 最优点很平：CPU 少算的时间被 GPU 多等 PCIe 抵掉 |
| 每窗口提交 token | — | `--spec 3/4/5`、spec-min-p 0.3～0.9、#4040 lookup | spec5 +1.0～1.7%；0.5≈0.6≈0.7；lookup 可加速部分只占 decode 0.8% | 窗口越宽，CPU 专家越多，每 token 成本三档持平 |
| 主机 / 频率 | — | CSTATE、调频、GPU 时钟 | CSTATE +2.2%；GPU 已在出厂最高 2745 MHz、无降频 | 已到头 |

### 3.3 不碰的约束

- **硬件：** PCIe 3.0（实测 12.3 GB/s）、2 通道 DDR（36 GB/s）、24 GB 显存。24,576 个层内专家（48 层 × 512 个）里，显存只放得下约 9,420 个（38%），命中率 93～96% 靠的是路由偏斜。按要求不考虑硬件方案，这里只说明上限从哪来。
- **质量：** 能直接减少 CPU 专家计算的手段都改变输出，按“Java 任务质量优先”没有进默认路线。
  - route tail skip 已默认开在 rank 7。
  - 加深到 6、减少 top-k、低比特 KV / 权重、专家延后（v2 O46～O57）属于 Q 轨道。
