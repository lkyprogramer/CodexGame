# v0.2.17 B2 路由尾部跳过的 teacher-forced KL（2026-11-20）

接 [V0217-PRODUCTION-SWITCH](V0217-PRODUCTION-SWITCH-20261120.md)。生产服务停机期间在 4090 上启动 9 次引擎，没有发出 HTTP 请求。

## 结论

1. **测量可用，且完全确定。** 同一配置重复两次，4995 个位置的 KL 为 0、top-1 一致率 100%。不同 rank 之间的差异都是真实差异。这个方法可以作为数值级门：给定文本，比较每个位置的下一 token 分布。后续的开关和候选 A/B 都应先过这一关。
2. **生产的 rank 7：KL 0.047、top-1 一致率 93.4%（以同一放置下的精确路由为参照）。**
   - 约为上游标称值的 4 倍（UD-Q4_K_XL / RTX 5090 上为 0.0126）。
   - 约为"只改专家放置"的 2.2 倍：全 CPU 与生产放置之间、不跳过时，KL 0.021、top-1 95.4%。也就是说，即使不跳过，计算位置不同本身就带来 0.02 量级的差异。
   - agent 片段最高：KL 0.136，top-1 90.7%。而 Pi 的工作负载正是 agent 类。
3. **质量和速度之间没有明显拐点**，rank 每降一档约多 6% 速度、多 0.009 KL：

| rank | KL（全部） | top-1 | agent 片段 KL | PPL（参照 4.125） | 固定文本耗时 | 相对不跳过 |
|---|---|---|---|---|---|---|
| 关闭 | 0 | 100% | 0 | 4.125 | 65.4 s | 1.00× |
| 9 | 0.030 | 95.0% | 0.092 | 4.165 | 61.4 s | 1.07× |
| 8 | 0.039 | 94.1% | 0.115 | 4.103 | 58.2 s | 1.12× |

| 5 | 0.074 | 91.0% | 0.186 | 4.125 | 48.2 s | 1.36× |

   - 固定文本耗时 = 5 段 × 999 个强制 token 的读入时间之和。这次关闭了自适应换入、PCIe 份额、suffix 草稿和 prompt cache，又开着逐位置 logit 输出，所以只能作相对比较，不代表生产 tok/s。
   - 作为对照，生产形态的 c100k 实测是 rank 7 比关闭快 1.145×（[迁移报告](V0217-MIGRATION-TAILSKIP-20261120.md)），方向和量级一致。
   - PPL 的变化在 ±1% 内，对这类差异不敏感。
4. **建议：生产先保持 rank 7，不改。** 理由：
   - 自 0.2.3 起生产一直用 rank 7；
   - 质量筛查（corpus 21/23、ledger chain 8/8）开和关结果相同；
   - 没有任务级证据说明 0.047 的 KL 造成了可感知的退步。
   
   **风险标注**：agent 片段的 KL 是文档片段的 3～4 倍。若在 Pi 的 agent 任务中感到质量下降，第一个可调的就是这里：
   - rank 9：保留约 1/3 的加速，KL 减少 37%；
   - 关闭：放弃全部加速。
   
   rank 5 不建议：KL 增加 57%，只多约 15% 速度。是否改动由你决定；改法是修改 `/home/hhtele/strata-0.2.17/strata-iq3_xxs.json` 的 env 后重启服务。

   **后续（同日）**：[任务级配对质量门](V0217-AGENT-GATE-20261120.md) 在 305 道题上证实 rank 7 对精确路由非劣（损害上界 1.62%），所以 rank 7 保持，rank 9 不再测。

## 方法

- **工具**：上游 `terminal/tools/quant_quality.py`（v0.2.17，代码未改），在生产树中运行。
  - 文本：上游固定集，code / docs / english / multilingual / agent 五段，每段 1000 token。我们用自己 pack 的 tokenizer 重新生成 ids，与随包发的 ids 逐段完全相同。
  - 每段文本强制经 decode 窗口读入，引擎通过 `STRATA_LOGPOS` 输出每个位置的 top-64 log-probability。
  - KL 在参照分布的 top-64 上重新归一化后计算。
- **配置**：生产 `strata-iq3_xxs.json` 的副本，所有写路径（learned profile、slots、cwd）都改到实验目录，生产文件 hash 前后不变。
  - 工具固定：不自适应换入、`--pcie-frac 0`、无 suffix 草稿、无 prompt cache、`--kv fp16`。
  - "cpu" 臂：`--expert-cache 1`，专家全在 CPU，上游的默认口径。
  - "auto" 臂：`--gpu-experts auto`，与生产的专家缓存放置一致。
  - 只用 `--env STRATA_ROUTE_TAIL_SKIP=k` 区分各臂。
- **顺序**：cpu-ts0-a、cpu-ts7、cpu-ts0-b、auto-ts0-a、auto-ts7、auto-ts5、auto-ts0-b，之后补跑 auto-ts9、auto-ts8。参照固定为 auto-ts0-a。
- **全 CPU 口径**：rank 7 的 KL 为 0.088、top-1 89.9%。这是上限情形，生产不会落到这里。

## 附带观察：专家内存的大页

- cpu-ts0-b 臂（`--expert-cache 1`）运行时读取引擎的 `/proc/<pid>/smaps_rollup`：匿名内存 42.0 GiB，其中 33.3 GiB（79%）由透明大页支撑。本机 THP 为 always，`STRATA_ARENA_THP` 不起作用（日志已确认）。
- 结论：大部分专家 arena 已经是 2 MiB 页，不值得为显式大页预留 40 GiB 内存（且需要 root）。
- 同时看到引擎有 358 MiB 在 swap。若其中包含专家 arena，计算时会出现缺页。
- **生产复查**（2026-11-20 生产重启后约 40 s，health ok，还没有请求）：
  - 引擎匿名内存 43.8 GiB，其中 31.6 GiB（72%）是透明大页。
  - 引擎 swap 455 MiB，serve 进程 205 MiB。
  - 整机 SwapTotal 977 MiB，只剩 120 MiB 空闲；MemAvailable 8.3 GiB。
  - swap 很小，且刚启动就基本用满。这说明引擎启动时有冷的匿名页被换出；在使用过程中如果被访问，就会出现缺页延迟。
  - 待生产有真实请求后，用 `observe.sh` 看 swap 是否继续增长，以及 decode 窗口时间是否异常。目前不改动。
