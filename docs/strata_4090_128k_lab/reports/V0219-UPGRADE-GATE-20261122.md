# v0.2.19 升级评估与真实 Pi 流量（2026-11-22）

接 [新版本一键过门](../tools/upgrade_gate/README.md)。上游 11-21 发布 v0.2.18、11-22 发布 v0.2.19。Pi 空闲时段在 4090 上用 `upgrade_gate.py` 完整评估 v0.2.19。

## 结论

1. **不升级，生产保持 v0.2.17 B2。** v0.2.19 的任务质量不比 B2 差，但速度没有收益：
   - 按上游默认配置，decode 慢 13%（116.9 对 134.7 tok/s）；
   - 关掉新的 `STRATA_VERIFY_DEVICE_HITS` 后与 B2 持平：同样 40 题，端到端 129.9 对 130.6 tok/s。
2. **慢的原因是 CPU 专家条目变多，不是 GPU 变慢。**
   - v0.2.19 新增了 sm_89 默认开关表，其中 `VERIFY_DEVICE_HITS` 会把 `pcie_frac` 强制设为 0，并关掉生产开着的 `ADAPT_OVERLAP`。没命中的专家原来部分走 PCIe，现在全部回到 CPU。
   - GPU 部分（reach）确实快了 9%–10%，但抵不过 CPU 侧增加的时间。
   - release notes 说"4090 decode 快 20%–31%"，那是 IQ3_S、而且基线未说明。在我们的 IQ3_XXS + rank 7 配置上没有复现。
3. **v0.2.18 只新增 Hy4-Flash 模型**，与本机无关。
4. **真实 Pi 流量下生产正常**（11-20 21:15 至 11-21 21:23，共 63 个请求），见下文。
5. **v0.2.19 树保留在 `/home/hhtele/strata-0.2.19`**（已打补丁并编译，442 MB）。之后的版本如果改了 CPU 专家路径或缓存槽位，再用一键过门重测。

## 真实 Pi 流量（只读，[prodlog](../evidence/v0219-upgrade-gate-20261122/prod-traffic/real-pi-20261120-21.json)）

共 3 个会话、63 个请求，没有错误或取消，全部是正常结束（stop），没有因长度截断。最长的一个会话有 56 个请求，prompt 从 13.8K 增长到 114K，每一步只读入工具输出（几百到几千 token）。

| prompt 长度 | 请求数 | 复用率 | decode tok/s | 每窗口 ms | 每窗口 CPU 条目 |
|---|---|---|---|---|---|
| 4K–32K | 4 | 71.0% | 160.2 | 18.8 | 2.22 |
| 32K–64K | 23 | 90.9% | 137.1 | 17.0 | 1.57 |
| ≥64K | 36 | 99.2% | 129.5 | 18.0 | 1.80 |

- **时间构成**：decode 368.8 s，读入 89.9 s（占 20%）。
  - 冷读入 2 次，均为新会话首轮，共 53K token、14.7 s。
  - 其余是长上下文下的小段读入，每次约 0.2–2.5 s。
- **借回前缀**：1 次。一个新会话从驻留会话借回 13.8K 系统提示前缀，再读入 25K（7 s）。
- **PT0 的"新用户消息后重读"没有出现**。8K 以上的部分复用读入有 2 次，都不是重读：
  - 一次是上面那个借回前缀后读入 25K 的新会话；
  - 另一次复用了上一请求的全部内容，再读入 13.3K 新内容（一段大的工具输出）。
  
  重读的特征是复用长度小于上一请求的 prompt，这两次都不符合。因此"空闲时预读入"候选目前没有依据，不做。只有约 1 天的数据，后续继续用 `observe.sh` 看。
- **内存**：驻留 2 个会话（3.6 GB），没有驱逐；MemAvailable 7.4 GiB，引擎 swap 317 MB，保持稳定。

## v0.2.19 中与本机有关的变化（源码，`v0.2.17..v0.2.19`，282 个提交）

- **新增 sm_89 默认开关表**（`nv_defaults.cpp`）：
  - 开关：`HC_UPMIX L2_PF Q80_ROWS1 EXP_MODE=8 SIDE_MIXER=2 DEQUANT_SIDE QFUSE LFUSE PLE_COMPACT PLE_COPY_STREAM PF_FUSED_KQ PREFILL_CPU_SHARE_NT=32`。显存大于 16 GiB 的卡另加 `VERIFY_DEVICE_HITS=1`。
  - 启动日志称它们为 exact，但 sm_89 这一项在源码里没有附任何实测记录；其他架构的条目都附了 KL 或 greedy 对照。
  - 除 `VERIFY_DEVICE_HITS` 外，这些开关在 v0.2.17 中都已存在，只是默认关闭。lab 以前只筛过 `DEQUANT_SIDE`（[P10](P10-DEQUANT-SIDE-QUALIFICATION-20261028.md)：收益不到 4%）。
- **GPU kernel**：
  - 多 token verify 时，Split 格式的权重只解码一次；
  - INT8 Tensor Core 的 dense GEMM；
  - 两阶段 bit-plane LM head；
  - sm_120 的 FP4 prefill。
- **CPU 专家池**（`pool.cpp`）只改了 15 行。
- **serve**：`frontend.py` / `server.py` 增加了 Hy4 和 Inkling 的方言分支，Qwen 路径不变。

## 过门过程

`upgrade_gate.py` 运行了三次，前两次的记录都保留在 [attempts/](../evidence/v0219-upgrade-gate-20261122/attempts/)。

1. **补丁手工移植**：PT0/#1536 补丁在 `frontend.py` 处冲突。上游在同一段把 `reasoning_effort` 扩成了 `("reasoning_effort", "thinking_mode")`，插入位置和逻辑都没变。移植后，改动行与 v0.2.17 版逐行相同（新增 212 行，删除 0 行）。
2. **第一次：编译失败。**
   - 现象：CUDA 12.3 编译 `iq_kernels.cu` 时报 `DotG<TG,1>` 是不完整类型（Q4_K/Q5_K，TG=12/13）。
   - 原因（据源码推断）：
     - `native_gu_fused_kernel` 在泛型 lambda 中用 `if constexpr (kSplit<TG>)` 分支；
     - 被丢弃的 else 分支仍被 nvcc 12.3 实例化；
     - 上游用更新的 CUDA 编译，碰不到这个问题。
   - 修复：补两个永不执行的 `DotG<12/13>` 占位特化（内部 `__trap()`）。kSplit<12>、kSplit<13> 都为 true，这两条特化只用于通过编译，运行行为不变。修复已并入 [v0219 补丁](../patches/v0219-pt0-reply-reuse.patch)，所以补丁共 7 个文件。
3. **第二次：被脚本自己的内存守卫中止。** v0.2.19 的 CUDA 文件更大，生产在线时 8 路并行编译让 MemAvailable 跌到 2998 MiB，低于 3 GiB 的守卫。改用 `-j 4` 重编。
4. **第三次：成功。**
   - tag 对象 `8fffdbf4a`、commit `c6f6427d9`，与 API 一致。
   - 单测 `serve.test_prompt_encoder serve.test_frontend serve.test_server` 492 项全部 OK，与 v0.2.17 移植时相同。
   - 编译 368 s，引擎版本 0.1.65。

## 结果

**KL 门：PROCEED**（rank 7、auto 放置，ids 与 v0.2.17 的 KL 实验相同）。

| 对照 | KL（全部） | top-1 | agent 段 KL |
|---|---|---|---|
| 对 v0.2.17 rank 7 存档 | 0.0230 | 94.7% | — |
| 对精确路由存档 | 0.0462 | — | 0.1241 |
| v0.2.17 rank 7 的已接受水平 | 0.047 | 93.4% | 0.136 |

v0.2.19 的数值与 v0.2.17 并不逐位相同：漂移 0.023，与"只改专家放置"的 0.021 同一量级。不过它相对精确路由的距离略小于 v0.2.17。

**任务门：NONINFERIORITY_ESTABLISHED**（`quality_gate.py` 退出码 0）。

- 305 题，基线是存档的 b2 臂。
- 最终通过 296 对 296，首次通过 267 对 257。
- 只有一边通过的题 4 对 4，损害上界 2.97%，低于 margin 5%。

**速度**（同一负载，305 题；prodlog 的每窗口数据）：

| | B2（v0.2.17） | v0.2.19 默认 | 精确路由（参考） |
|---|---|---|---|
| decode tok/s | **134.7** | 116.9 | 115.7 |
| <4K：每窗口 ms / GPU-reach / CPU 条目 / 命中率 | 15.87 / 8.04 / 1.75 / 92.9% | 18.18 / 7.31 / 1.93 / 92.1% | 18.49 / 7.59 / 2.72 / 89.2% |
| 4K–32K：同上 | 27.04 / 8.44 / 4.90 / 86.2% | 31.77 / 7.55 / 6.44 / 82.3% | 32.70 / 8.11 / 7.39 / 80.1% |
| 专家缓存槽位 | 10126 | 9902 | — |

**确认原因**：在同一 v0.2.19 树上只加 `STRATA_VERIFY_DEVICE_HITS=0`，跑前 40 题（`gate --limit 40 --env`，[SMOKE](../evidence/v0219-upgrade-gate-20261122/upgrade-gate/SMOKE-v0219-verify_device_hits0.json)）。

- 启动日志显示 PCIe 分担和自适应 overlap 都恢复了。
- 同样 40 题的端到端 completion tok/s：

| B2 | v0.2.19 默认 | v0.2.19 + VDH=0 | 精确路由 |
|---|---|---|---|
| 130.6 | 115.7 | 129.9 | 115.0 |

- 这个代理指标可以替代整臂速度：前 40 题的比值（v0.2.19 默认 / B2 = 0.886）与整臂 305 题（0.874）相差约 1.5%。

## 局限

- **VDH=0 只跑了 40 题**，只能说明速度，不是质量结论。这 40 题最终通过 31 题，b2 同样 40 题是 34 题，n=40 时无法区分。
- **以后要测带 VDH=0 的 v0.2.19，需要整臂跑一次任务门**（`gate v0.2.19 --env STRATA_VERIFY_DEVICE_HITS=0`，约 2 小时）。但它速度只是持平，目前没有动机去测。
- **上游的 20%–31% 没有复现**，只说明在本机配置上不成立；没有在 IQ3_S 或默认关闭尾部跳过的配置上验证。
- **停机记录**：生产停了三段，分别是 KL 86 s、任务门 2 小时 3 分、40 题测速 36 分钟，每段结束后都自动恢复。当天没有 Pi 请求，没有影响任何用户。

## 一键过门的改进（本轮）

- 按版本优先使用 `pt0-reply-reuse.<tag>.patch`（手工移植件）。
- prepare 增加 serve 单测，失败即停。
- `gate --env K=V`：带额外 env 的一臂，臂名会带上开关名。`--limit N` 现在会给出同题的端到端速度对比。
- 已完整跑完的臂再次执行 `gate` 时只做判定，不再停生产。
- 修复读取 prodlog `--json` 嵌套 `summary` 时的 KeyError：第三次运行在最后一步因此中断，判定改为补跑完成。
