# CFG-SPEC-S：`--spec` 3 / 4 / 5 在 Pi 采样 + thinking 下的 decode（2026-10-26）

**结论：保持 `--spec 4`。**
- **spec 3 显著变慢，拒绝。** 按 decode tok/s 的成对比值中位数：长上下文贪心 0.911，回答段 0.964，思考段 0.986，三组 CI 都在 1 以下。
- **spec 5 只快 1.0～1.7%，不采用。**
  - 只有长上下文组的 CI 不跨 1，其余三组都跨 1。
  - 全部达不到正式采用门（≥3%）。
  - 整轮 wall_s 上没有显著差异。
- **spec 6 未测。** 依据是收益递减：spec 3→4 长上下文 +9.7%，4→5 只有 +1.1%。
- **机制（已观察）：** 每窗口耗时几乎和每窗口接受的 token 数成正比。窗口变宽时，同一窗口里要算的 CPU 专家也跟着变多，所以每 token 成本在三档之间基本持平，思考段约 7.5 ms/token。推测宽度不是本机的有效杠杆；要让更宽的窗口划算，得先降低 CPU 专家的单价（NP-3）。

（每档 spec4 行取自同一 campaign 的 base arm。）

已观察：
- **上限会改变整个 T 分布，不只是截尾。** spec4 时平均 T（思考 2.5、回答 3.45）远低于上限 6，但上限降到 5 后思考段平均 T 降到 2.19，升到 7 后升到 2.83。
- **窗口变宽，每窗口耗时几乎同比例上升。** spec5 回答段 token/窗口 +12.3%，ms/窗口 +10.8%。增量主要来自 CPU 专家（+1.27 ms）、draft（+0.35 ms）和 GPU 等待（+0.35 ms）。
- **spec3 在长上下文上掉得最多。** 原因是贪心长 prompt 的接受率最高（0.85），被截掉的长窗口最多。

推论：
- 一个窗口里多验证一个 token，新增的专家路由大多落到本来就没命中的专家上，CPU 专家时间按 token 增长，摊不薄。
- 所以 `--spec` 只能在约 ±1% 的范围里调。降低 CPU 专家单价（NP-3 / NP-RES）之后，宽窗口的收益可能变大，届时再测 spec 5/6。

## 5. 附带观察：思考预算收尾时的整段重读

- 服务端在思考触及预算时会强制收尾，再发一次引擎调用生成回答。正常情况下第二次调用只读入约 19 token（收尾句和 `</think>`）。
- 但在两个 campaign 里，320 次收尾调用中有 83 次（26%）把刚生成的思考整段重读了一遍：1,536 token 思考读 1,559 token，128 token 思考读 151 token，每次多花约 1.1～2.0 s。两个 arm 都有，不影响 decode 指标。
- 机制推测与 #1536 同类：前缀匹配在思考内部分叉，GDN 状态只能回退到 prompt 末尾的 checkpoint。
- 对实际用法的影响很小（已观察）：Pi 不发预算，`max_tokens` 32768 时思考上限 24,576。录制的 `r1536-*`、`pt0-java` 共 7 个真实形态会话，`thinking budget reached` 一次都没出现，所以不展开。如果以后真实会话里出现，最多会多读 24K token，约 9 s。

| `--spec 3` | **REJECT** | 四组 decode 都变慢，三组 CI 在 1 以下；长上下文 −8.7%；wall_s 三组显著变差 |
| `--spec 4`（现网） | **KEEP** | — |
