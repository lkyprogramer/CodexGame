# #4040：lookup 长窗口（最长 16 token）的适用性（Gate A，2026-10-26）

**结论：NO_BENEFIT，不移植。** 按 [PR 文档](../prs/12_PR4040.md) 自己的停止条件（目标负载的 lookup 份额低于 10% 直接记 NO_BENEFIT）在 Phase A 结束。

- **整体份额 4.6%（已观察）：** 29 上已有的 18 段会话 / 编码链、151 次引擎调用里，被接受的 lookup（suffix）草稿占生成 token 的 4.6%。各段在 1.7～7.9% 之间。
- **份额高的调用很少，时间也短（已观察）：**
  - lookup ≥20% 的调用有 14 次，平均 39%，全部是编码链里“思考之后写代码”的回答段：回答照抄思考里起草的代码。
  - 这 14 次只占全部 decode 时间的 0.8%；即使只看编码链，也只占每条链的 1.1～3.7%。单会话追问（`session/*`，含 Java 会话）一次也没有。
- **上限（推论）：** 这些调用的窗口已经平均提交 3.7～4.8 个 token（上限 6 = `--spec 4` + 2）。
  - 即使 #4040 让它们整体快一倍，端到端也只省 0.4%；在编码链里最多 1.8%。
  - 都低于组级噪声（约 ±2%）和 3% 采用门。
- **本机机制不利（已观察，[CFG-SPEC-S](P2-CFG-SPEC-S-20261026.md)）：** 29 上每窗口耗时随窗口提交的 token 数近似同比增长，因为窗口越宽，要算的 CPU 专家越多。窗口从 6 放到 16，每 token 成本的下降会比作者的 RTX 2060 SUPER（`--spec 3`，+19%）小得多。
- **之前的估计偏高：** 包内文档原写“端到端上限约 2～3%”，那是按整体份额套 Amdahl 得出的。按调用拆开后，真正能被长窗口加速的部分只有 0.8% 的 decode 时间，已在文档中更正。

## 1. 数据与方法

- **来源：** 29 `workspace/reports/{chain,session}/*/engine.log`，即单会话 Phase（#1536、CFG-PT）和编码链质量测试时的 serve 引擎日志。负载是 Pi 采样 + thinking，A0 + EXACT6，`--spec 4`。
- **每次引擎调用的日志顺序：**
  1. `strata decode timing: …`
  2. `strata serve: prompt … N generated in M ms`
  3. 有 suffix 窗口时，`strata serve: suffix drafts: W windows, A of D drafts accepted`

  第 3 行是**本次调用**的数，不是累计数。
- **份额：** 本次调用的 lookup 份额 = A / N。
- **工具：** `tools/analysis/lookup_share.py`。跳过 ≤4 token 的计数探针。

一个典型编码链（chain/pt0-1）的一轮：
- 思考段生成 24,576 token、约 188 s，lookup 2.3～5.7%。
- 回答段生成 693～1,441 token、5～10 s，lookup 23～59%，平均 T 3.95～4.85。

长窗口能帮的只有回答段，而回答段只占这一轮 decode 时间的 2.5～5%。

## 2. 什么情况下值得重测

Pi 有一类回合是改文件 / 整段重写，模型直接输出完整模块，几乎全是照抄。只有这类回合在用户真实流量里占相当的时间时才值得重测，前提条件有两个：
- 真实流量里出现 lookup 份额 ≥20% 的调用。
- 这些调用占 decode 时间 ≥10%。

用法是对新的生产日志跑 `tools/analysis/lookup_share.py`。按目前已知的用法（单会话长期追问，思考占 decode 的绝大部分），不满足。
