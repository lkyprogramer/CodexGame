# CFG-ADAPT（v2 O09）：自适应层三种模式对照（2026-10-26）

**结论：两种替代模式都不采用，保持现网的 `STRATA_ADAPT_OVERLAP=1`。**

| 对照 | 结果 | 判定 |
|---|---|---|
| lag2nw | overlap 关，开 `STRATA_ADAPT_LAG=2` + `STRATA_ADAPT_NOWAIT=1`（上游 sm_86 / sm_60 的默认） | **略慢**：回答段配对中位 0.981 [0.968, 0.997]，短 greedy 0.981 [0.942, 1.000]，长 decode 与思考段持平。窗口里 CPU 专家条目多了 7.5% |
| async | overlap 关，开 `--adapt-async 1` + LAG=2（Reddit 帖子的配置） | **持平**：思考段 1.015 [0.993, 1.031]，回答段 1.000，长 decode 1.009 [0.997, 1.025]，短 greedy 1.049 [0.980, 1.105]，都没到 3% 门，CI 都跨 1。异步层确实在工作（每轮约 77 个专家，命中率与 overlap 相同） |

为什么没有空间：overlap 下自适应层留在关键路径上的只有等待 0.07 ms 加 join 0.17 ms，约占 17.6 ms 窗口的 1.4%。这是任何换模式手段的收益上限。
- lag2nw 省掉了等待，但窗口开始时还没落地的专家要由 CPU 算，CPU 专家条目从每层每窗口 2.02 增加到 2.17，得不偿失。
- async 把交换放到后台线程，等待反而变成 0.17 ms，窗口净变化 −0.6%，在噪声内。

Reddit 帖子的配置（Windows、0.1.43、IQ3_S）在 29（Linux、A0、IQ3_XXS、overlap 已开）上没有收益。这与上游源码注释一致：overlap 在 Linux CUDA 上原本就是更好的那一档。

## 2. 结果

### 2.1 配对 decode tok/s（cfg / base，中位与 bootstrap 95% CI）

| 组 | n | lag2nw | async |
|---|---:|---|---|
| decode（短，greedy） | 15 | 0.981 [0.942, 1.000] | 1.049 [0.980, 1.105] |
| long-decode | 20 | 0.996 [0.984, 1.035] | 1.009 [0.997, 1.025] |
| spec-answer | 40 | **0.981 [0.968, 0.997]** | 1.000 [0.989, 1.014] |
| spec-think | 40 | 0.995 [0.973, 1.020] | 1.015 [0.993, 1.031] |

### 2.2 组内总 token / 总 decode 时间（tok/s）

| 组 | lag2nw：base → cfg | async：base → cfg |
|---|---|---|
| decode | 145.85 → 141.90 | 140.47 → 147.63 |
| long-decode | 187.84 → 189.77 | 187.08 → 189.96 |
| spec-answer | 148.51 → 145.59 | 145.09 → 146.02 |
| spec-think | 135.45 → 135.63 | 135.17 → 136.28 |

两个 campaign 的 base 在短 greedy 组上差 3.7%（145.85 对 140.47）。这是跨 campaign 的进程间噪声，所以只看同一 campaign 内的配对。async 在短 greedy 组上的 +4.9% 主要来自这组 base 偏低，CI 也跨 1。

### 2.3 引擎窗口构成（按窗口数加权，≥20 窗口的调用）

| campaign / arm | ms / 窗口 | CPU 专家条目 / 层窗口 | adapt wait | join | swap / 窗口 | 命中率 |
|---|---:|---:|---:|---:|---:|---:|
| lag2nw base（overlap） | 17.587 | 2.018 | 0.069 | 0.173 | 18.7 | 96.58% |
| lag2nw cfg | 17.710 | 2.170 | 0.010 | 0.147 | 18.9 | 96.33% |
| async base（overlap） | 17.765 | 2.115 | 0.070 | 0.173 | 18.7 | 96.49% |
| async cfg | 17.652 | 2.154 | 0.173 | 0.000 | 18.8 | 96.30% |

分组看（spec_analyze 引擎表）：
- lag2nw 短 greedy 组：窗口 16.40 → 17.07 ms，CPU 时间 5.16 → 6.10 ms。
- lag2nw 思考段：15.26 → 15.43 ms。
- async 各组：窗口变化在 −1.0%～−0.1% 之间（短 greedy 组 −6.9% 除外，原因见 2.2）。
- 两个 cfg 的专家槽都与 base 相同（9420），verify 窗口上限都是 6。

异步层的活动：每个 cfg 进程约 3,550 轮、约 27 万个专家换入，每轮从开始到切换约 19.9 ms。

## 3. 判定与影响

- 两项都是 NO_BENEFIT，生产不变，不需要回滚。
- O09 的其余部分（overlap 的成本治理）没有可做的空间：overlap 下自适应层在关键路径上只剩约 0.24 ms / 窗口。
- 之前分析 Reddit 帖子时提出的 “O09 先测、再测 `--kv-resident`”，前一半已完成；`--kv-resident` 见 CFG-KVRES 报告。
