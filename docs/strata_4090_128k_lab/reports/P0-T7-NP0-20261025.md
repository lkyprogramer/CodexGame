# P0-T7 报告：NP-0 测量与 CPU 专家路径（2026-10-25）

**结论（Gate NP-0）：**

1. **CPU 专家在关键路径上，而且是线性的。**
   - DIAG 的 4,052 个稳态窗口里，verify 耗时 ≈ 10.8 ms + 77 µs × CPU miss 数（r = 0.96）。CPU 池耗时对 miss 数的斜率是 80.6 µs（r = 0.99）。
   - 等 GPU 不随 miss 数增加：r = −0.28，各档都在 8.7～9.8 ms。CPU 工作没有被 GPU 掩盖，每省 1 µs CPU 就省 1 µs 窗口。
   - GPU 侧印证（nsys）：17.5% 的 GPU kernel 时间是 `wait_flag_ge_kernel` 自旋，即 GPU 在等主机侧结果。
2. **内存带宽上限是 36 GB/s。** 29 只插了 2 条 DIMM（每个内存控制器 1 条，Xeon 4216 支持 6 通道），只读带宽 4 线程就饱和。
   - CPU 专家路径的折算有效带宽约 20 GB/s，大约是上限的 55%。这是推断，按平均 blob 1.59 MB 计算。
   - 这一项是硬件事实，按你的要求不考虑硬件方案，只作为软件优化的天花板。
3. **GPU 窗口内几乎不空闲。** 小于 1 ms 的间隙合计约 1.2%，CUDA graph 已经把发射间隙压到可忽略。
   - NP-5 “消除小 kernel 发射间隙”空间很小；GPU 侧只能靠减少实际工作量。
4. **NP-1a（Q2_0 down 改走 128 位 kernel）NO_BENEFIT**：整机 A/B 引擎耗时 +0.4%，CPU 专家 +0.05 ms，没有改善。
   - 原因是 `kq_cpu_bench` 直接调用 `native_down_rows`，而引擎 pool 对 Q2_0 down 走的是 `q2_rows_any`（AVX2 kernel）。微基准测到的是引擎不走的标量分支。
   - 这条线索是工具假象，已撤回。
5. **CFG-THP / NP-2 关闭**：引擎匿名内存 43.0 GiB，其中 `AnonHugePages` 36.7 GiB（85%）。
6. **未完成**：`perf` 不可用（未安装，且 `perf_event_paranoid=3`，需要 sudo 或装包），CPU 侧“计算、同步、TLB 各占多少”无法拆。所以 NP-1 / NP-3 谁更值得做暂时无法定论，标 BLOCKED，见第 6 节。

## 1. CPU 是否在关键路径上（DIAG 窗口 trace 回归）

数据：P0-T5 的 `window-trace-20261025-022254.bin`，稳态 4,052 窗口（A0 + #1864 + #3631）。

| 模型 | 斜率 | 截距 | r |
|---|---|---|---|
| CPU 池耗时 ~ CPU miss | 80.6 µs/miss | 0.47 ms | 0.99 |
| verify ~ CPU miss | 77.0 µs/miss | 10.78 ms | 0.96 |
| 等 GPU ~ CPU miss | −4.2 µs/miss | 9.71 ms | −0.28 |

| CPU miss/窗口 | 窗口数 | verify | 等 GPU | CPU 池 |
|---|---|---|---|---|
| 0～40 | 1,723 | 12.57 | 9.77 | 2.17 |
| 40～80 | 981 | 15.17 | 9.49 | 5.06 |
| 80～120 | 505 | 17.84 | 8.91 | 8.24 |
| 120～200 | 516 | 21.99 | 8.74 | 12.64 |
| ≥ 200 | 327 | 32.38 | 8.86 | 22.79 |

verify 的增量和 CPU 池的增量几乎一一对应，等 GPU 基本不变。可以排除“CPU 与 GPU 专家同层并行、只有超出部分才计入”的情况：

- 在 0～40 档，CPU 池只有 2.2 ms，远小于 GPU 的 9.8 ms。
- 如果两者并行，CPU 时间应该完全被掩盖；实际上 CPU 每多一个 miss，窗口仍然线性变长。

推断：每层的 CPU 专家结果是该层后续计算的前置依赖，即串行（`wait_flag` 自旋印证了这一点）。所以第 3 节（CPU 专家路径）的收益是线性的。

平均每窗口 CPU miss 76.4 个（CPU 条目 100.4 个，即每个 miss 平均 1.31 个 token），按 80.6 µs 计约 6.2 ms，占窗口 18.5 ms 的约 33%。

## 2. 内存带宽（只读，未改配置）

| 项 | 结果 |
|---|---|
| DIMM | EDAC：`mc0/dimm0` 32 GB、`mc1/dimm0` 32 GB，Unbuffered DDR4；每个内存控制器只有 Chan#0 有条 |
| 读带宽（自写 STREAM 类求和，4 GiB，`OMP_PROC_BIND=spread`，5 次取最好） | 1 线程 15.4 GB/s；2 线程 27.1；4 线程 36.4；8 线程 36.8；16 线程 35.5；32 线程 34.5 |
| 引擎 K-quant 专家行（`kq_cpu_bench`，nt=1） | q4_K/q5_1：8 线程 35.9 GB/s；q8_0/q8_0：8 线程 36.0（都到了 100%） |

所以 CPU 专家路径的上限是 36 GB/s，pool 的 16 线程远超饱和所需的 4～8 线程。

对 CPU 路径的推算（推断）：

- 每窗口 76 个 miss × 平均 1.59 MB（偶数层 IQ2_XS + IQ4_NL 1.87 MB，奇数层 IQ2_XXS + Q2_0 1.31 MB，按各半估）≈ 121 MB。
- 用 6.2 ms 完成，折合约 20 GB/s，约为上限的 55%。
- 理论空间：如果完全吃满带宽，CPU 部分能省约 45%（约 2.7 ms/窗口，约 15%）。这是上限，不是预期。

## 4. CPU 专家内核微基准（`kq_cpu_bench`）

引擎自带的 `kq_cpu_bench` 用随机权重量化 i-quant 时会段错误（K-quant 正常）。在 DIAG 树里给它加了 i-quant 生成路径：随机索引字节，每个 block 设正常的 fp16 scale，避免非规格化数。只改测试工具，不改引擎。

| 格式（gate+up / down） | nt=1，16 线程 | nt=2，16 线程 | nt=4，16 线程 | 单线程 nt=1 |
|---|---|---|---|---|
| IQ2_XS / IQ4_NL（偶数层，1.87 MB） | 35.3 GB/s（98%） | 27.8（77%） | 20.2（56%） | 3.2 |
| IQ2_XXS / IQ4_NL（拆分对照） | 35.0（97%） | 28.7（80%） | — | 3.2 |
| IQ2_XXS / Q2_0（奇数层，1.31 MB） | 13.2（37%） | 7.5（21%） | 3.9（11%） | 1.0 |
| IQ2_XS / Q2_0（拆分对照） | 13.9（38%） | 7.9（22%） | — | 1.0 |

**注意：Q2_0 那两行不代表引擎。**

- `kq_cpu_bench` 的 down 行调用 `native_down_rows`。它在 AVX2 且无 AVX1 tier 的 CPU 上，对 Q2_0 落到 ggml-cpu 的标量 `vec_dot`。
- 引擎 pool（`src/kernels/cpu/pool.cpp` 约 1226～1239 行）对 Q2_0 down 调用的是 `q2_rows_any` → `q2_0_gguf_rows_multi_avx2`，根本不经过那个分支。

IQ4_NL 这两行可信：pool 走 `native_gu_rows` / `native_down_rows`，与微基准同一入口。在 nt=1 / 2 时它已接近带宽上限，说明偶数层的 CPU 专家基本是带宽受限，NP-1（VNNI 内核）对偶数层的空间很小。奇数层（Q2_0 down 走 AVX2 kernel）的真实成本还没有正确测过。

## 5. NP-1a：Q2_0 down 走 `iq128_down_rows`（已证伪）

| 项 | 值 |
|---|---|
| 改动 | `trees/np1a`（分支 `lab/np1a`，A0 + 1 处改动）：`STRATA_LAB_Q2_128=1` 时，AVX2 CPU 上 `native_down_rows` 对 Q2_0 改走 `iq128_down_rows`；不设则与 A0 相同 |
| 正确性 | `iq_avx1_parity` 全部通过（相对误差 ≤ 1e-5，对标量 ggml） |
| 微基准 | 16 线程 IQ2_XXS / Q2_0：nt=1 13.2 → 25.8 GB/s，nt=2 7.5 → 16.2，nt=4 3.9 → 9.5；IQ4_NL 对照不变 |
| 整机 A/B | `results/pr-0-20261025-053728`，5 轮，EXACT6 公共基线：ms/窗口 16.44 → 16.51（+0.4%），CPU 专家 4.53 → 4.58，decode 各组中位 0.990～1.020（CI 覆盖 1） |

教训：用微基准做立项依据前，先对照 pool 的实际调用点核对入口。本报告第 4 节的 IQ4_NL 结论已经做过这个核对。

## 6. 方向决策（Gate NP-0 之后）

| 方向 | 决定 | 依据 |
|---|---|---|
| NP-1（VNNI 无 VBMI 内核） | **暂缓** | 偶数层 IQ4_NL 路径在 nt ≤ 2 时已接近 36 GB/s 上限。奇数层 Q2_0 的真实路径（`q2_rows_any` AVX2）还没测；要先修 `kq_cpu_bench`，让 Q2_0 down 调用 `q2_rows_any`（需要按 pool 的方式准备 `ActQ` 激活），再定 |
| NP-3（pool 任务切分 / 同步） | **候选，排在 NP-1 之前** | 回归斜率 80.6 µs/miss，按带宽折算只用到约 55%；每层平均只有 1.6 个 miss，却要 16 线程分发和汇合。没有 `perf` 拆同步占比，只能用代码实验验证：例如把 pool 线程数从 16 降到 8，或按 expert 而不是按行切分，用窗口 trace 直接比较 |
| CFG-THP / NP-2 | **关闭** | 85% 已是大页 |
| NP-5（小 kernel 融合） | **降级** | 窗口内 GPU 空闲约 1.2%，graph 已经消除发射间隙 |
| NP-4（跨层预测 + PCIe 预取） | 不变（研究级） | adaptive tier 已在每窗口搬约 18 个专家；预取会和它争 PCIe 与槽位 |
| CFG-CSTATE | 需要你批准 | 每层 CPU 任务很短；C6 唤醒（133 µs）可能落在关键路径上，而本节已证明关键路径是线性的，所以这一项的预期价值比文档写的更高 |
| perf 采样 | **BLOCKED** | 需要安装 `linux-perf` 并调低 `perf_event_paranoid`（root）。没有授权，不做 |

POOL8 对 NP-3 的含义（推断）：

- worker 从 15 减到 8，CPU 专家时间只增加 21%，远低于纯计算受限时的接近翻倍。
- 另一方面，`kq_cpu_bench` 里 8 线程已能吃满 36 GB/s；如果是纯带宽受限，减半 worker 应该几乎不变。
- 两头都不符合，说明每层的分发、汇合和小任务开销占了可观的一块。这把 NP-3（任务切分 / 同步）放到 NP-1 之前。

CFG-MTPQ4 的配套项 CFG-DVOCAB（自定义 draft 词表）需要先从 Pi 真实输出统计 token 频率，本轮没有这份数据，未做。
