## 1. 证据、收益与适用性

**来源报告：** 4070TiSUPER16GB+128GB RAM、NVFP4 target的短代码decode+29.05%，2.4K+11.15%，cache例+0.21%；256K单次decode+14.84%但完整请求反而慢0.72%。256K只是历史证据，本机严禁复现超限窗口。 [来源](https://github.com/Niko1221/Strata/pull/3322)

**本机判断：** 投入最大、排名靠后。v0.2.3 已带 DFlash2 drafter（`--draft dflash2 --draft-model PACK`，drafter 为 `incoai/Qwen3.8-Flash-Next-DFlash2`，用 `tools/dflash2_pack.py` 打包），但**只在单卡命令行运行时生效**：`--serve`、`--batch`、多卡切分下引擎自动退回 MTP（`src/program/generate.cpp:5478`），Control 的 `ENGINE_SERVES_DFLASH2 = False`（`strata_control/drafting.py:146`）。29 以 `--serve` 为 Pi 提供服务，所以发布说明里的 `strata launch --drafting dflash2` 在 29 上不会生效。

维护者实测表（`drafting.py`）：没有任何显卡类别在所有 prompt 上都快于 MTP——RTX 3060（sm_86）每个 prompt 都更慢，RTX 5070（sm_120）代码更快、聊天慢 1%，R9700 全部更慢，Strix Halo 工具调用慢 6%；sm_89 未测，`auto` 选 MTP。

29 上的不利因素（**推断**，未实测）：
- DFlash2 需要约 1.2 GiB 显存（pack 0.76、缓冲与 K/V ring 0.25、draft head 0.2），引擎建议 `--vram-reserve-mib 1900`，且 MTP 层（950 MiB）仍作为后备常驻。1.2 GiB 约合 700 个专家槽（现有 9434 个的 7% 以上），未命中转给 CPU，而 CPU 专家已占每窗口约 24%。
- 窗口更宽时验证要读的专家并集更大，在部分专家放 CPU 的配置下验证成本随宽度上升。
- MTP draft 每窗口只有 1.88 ms（约 11%），DFlash2 只能靠把每窗口 token 数从 2.33 明显提高来获益。
- Pi 请求是 temperature 1.0 采样、`xhigh` thinking；drafter 按原始权重训练，target 是 IQ3_XXS 量化模型，接受率可能打折。

因此先做 Phase A0 的命令行上限测试；不过门槛就不做服务集成，等上游打开 `ENGINE_SERVES_DFLASH2` 再重新评估。查明缺失的是 checkpoint 契约、服务状态还是性能选项，不直接合并722文件旧分支。

收益数字不是本包作者4090实测，也不作为验收预设答案。先证明瓶颈存在，然后决定是否继续。

## 3. Phase / Task

### Phase A0：命令行上限测试（服务集成前的门槛）

在不改任何代码的前提下，用 A0（v0.2.3）的引擎做单卡命令行运行，比较 MTP 与 DFlash2：

- 准备：从 hf-mirror 下载 drafter（约 1.2 GB），用 `tools/dflash2_pack.py` 打包到 `workspace/` 下；**下载与占用 29 GPU 都需要用户批准**，hf-mirror 不可用就立即报告、不反复试。
- 运行：同一引擎、同一 target、同一 `--vram-reserve-mib`（两边都按 1900 设，保证专家槽数相同），`--tokens-file` 喂入 Pi 风格的预分词 prompt（4K / 32K 代码与工具调用各若干），`--max-new 512`；greedy 一组，`--seed S --temperature 1.0 --top-p 0.95 --top-k 20` 一组。一边 `--draft dflash2 --draft-model PACK`，另一边不加。
- 记录：decode tok/s、每窗口 token、draft ms、verify ms、专家命中率、额外显存，各 5 轮。
- **门槛**：采样组 decode tok/s 稳定比 MTP 快约 10% 以上（超过 A/A 噪声），且 greedy 组不回退，才进入 Phase A；否则结论 NO_BENEFIT，本项停在这里。

### Phase A：机制资格与最小设计

A1：运行doctor与qualify；保存模型、KV、MTP、缓存、CPU/PCIe和内存证据。A2：构造能反映该机制的最小样本，确认不是不相关瓶颈。A3：冻结主指标、off/on语义和资源状态图。**Review Gate A**：条件不成立就NOT_APPLICABLE，不先写大改。

### Phase B：最小移植

- B1：出差量表：upstream已有、PR特有、两者冲突、需要重新实现。若主线已有等效功能且可安全serve，则将任务改为qualification，不制造重复实现。
- B2：保持同一target GGUF/量化/head/tokenizer，不为满足作者checkpoint换成NVFP4；验证当前 IQ3_XXS GSQ-RCO 的draft契约，兼容未知就停止。
- B3：明确MTP与DFlash互斥，分别核算draft权重、KV、scratch，比较固定actual expert slots与各自最优容量两套实验，不能混淆。
- B4：实现服务端prefill/continuation/checkpoint/cancel/snapshot完整状态；CLI可答一次不等于Pi可长期使用。
- B5：通用runner禁止偷偷改--mtp：在worktree内增加受审查的专用drafter配置适配器和测试，输出相同结果schema；包本身不含未验证的flag拼接或自动模型下载。

**Review Gate B**：至少检查主线程/worker、异步copy、缓存身份、取消错误恢复和默认关闭路径。可以并行进行文档/CPU测试审查，但GPU实验只能串行。

### Phase C：失败测试与正确性

- C1：checkpoint几何/shape/tokenizer/head/dtype/hash错误要fail closed。
- C2：BF16参考与native的stage parity、selector predecessor条件、local-window边界。
- C3：快照含draft状态，重启/取消/预算/compaction后不能复用旧draft KV。

要求在未修改A0或关闭路径上看到机制测试失败（对于纯性能优化使用已固定的性能断言/dispatch断言），在候选中通过。不能把缺失测试数据导致的skip计为pass。

### Phase D：实机A/B

- D1：先4K/32K通路与MTP同target基线，通过后64K/96K/120K；每轮固定512/1024输出。
- D2：分别测冷prefill+decode和hot follow-up，保存acceptance、tokens/window、draft_ms、verify_ms、extraVRAM。
- D3：至少5轮而非一次长上下文；完整请求/Java任务净收益才可采用。禁止宣传1.5～2倍普遍收益。

**必须观察到的机制回执：** 在不更换target的前提下，更多有效accepted tokens抵消draft成本和expert显存挤压；不是单纯输出缩短。

**停止条件：** Phase A0 未过门槛、draft契约未对齐、62GiB RAM/24GB显存装不下、只能CLI不能serve、main已有等价差量为零，或只有decode快而完整任务不收益时停止。

### Phase E：留出与结论

E1：同一Java mini-agent题集与真实Pi留出任务。E2：按统计协议产出CI、质量、资源与回退报告。E3：写DECISION.md并保留最小补丁。**Review Gate E**：只有经过独立留出验证才能推荐生产，脚本不会自动切换。
