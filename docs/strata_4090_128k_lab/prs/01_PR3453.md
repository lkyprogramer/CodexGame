## 1. 证据、收益与适用性

**来源报告：** RTX4070 上 IQ4_XS 2560×10240、4列微内核54.4→35.2µs，8列71.8→46.5µs；但作者的Coder IQ1_M完整decode没有可辨提升。不能把约1.5×微内核速度说成4090整体收益。 [来源](https://github.com/Niko1221/Strata/pull/3453)

**本机判断：** 最适合先投入小规模实机校准：你的4090是sm_89，但128SM与作者4070的46SM不同。29 实际是 IQ3_XXS GSQ-RCO，dense投影占比必须先测；CPU专家瓶颈很强时可能没有收益。29 真实流量 decode 占引擎时间 75～80%，decode 窗口约 17.2 ms 中等待 GPU 约 9.65 ms，是本项排第一的依据。冻结 main 中 `kIlRows_89` 只出现在注释和 `docs/MMVQ_IL_TABLE.md` 的操作说明里，`kIlArch` 未注册 sm_89 表，需要本机 `--emit-table` 生成。

**直接证据（Issue [#1842](https://github.com/Niko1221/Strata/issues/1842)）：** Windows RTX 4090、Qwen3.8-Flash-Next IQ3_S、`--spec 4 --spec-min-p 0.5`：0.1.41 的 128K decode 73.2～78.4 tok/s，0.1.40.3 为 90.3～95.4；同一 0.1.41 二进制设 `STRATA_MMVQ_IL=0` 回到 90.7～91.9，每步 14.6 → 12.9 ms，prefill 不变；8K 时开 IL 反而更快；A30（sm_80）上同一 A/B 无差别。该 issue 按“超过三天”统一关闭，没有修复记录；v0.2.3 的 `native_mmvq.cu`（约第 2994 行）仍写“sm_89 (Ada) has none yet”。**推断**：29 的 0.1.43.1 同样走共享表且默认开 IL（未在 29 源码树核对）。因此 P0-T6 的零代码对照 CFG-IL0 是本项的前置对照。

收益数字不是本包作者4090实测，也不作为验收预设答案。先证明瓶颈存在，然后决定是否继续。

## 3. Phase / Task

### Phase A：机制资格与最小设计

A1：运行doctor与qualify；保存模型、KV、MTP、缓存、CPU/PCIe和内存证据。A2：用 DIAG 构建（START_HERE P0-T5：冻结 main + #1864 + #3631）拆清 29 每窗口约 17.2 ms 的构成；只有 verify 窗口里 GPU dense 投影（MMVQ）占比足以支撑 ≥5% 的端到端收益时才继续，否则 NO_BENEFIT。A3：读取 P0-T6 的 CFG-IL0 结论：IL=0 在长上下文已追平或反超默认值时，本项目标改为“sm_89 表在长短上下文都不劣于 IL=0、且短上下文保留 IL 的收益”，A0 与 B 都以通过的公共基线为准；IL=0 与默认无差别时，按原目标继续。A4：冻结主指标、off/on语义和资源状态图。**Review Gate A**：条件不成立就NOT_APPLICABLE，不先写大改。

### Phase B：最小移植

- B1：先不改源码，检查冻结main的sm_89是否已有独立表。若已有相同覆盖，比较cell差异和实际dispatch，不重复注册。
- B2：在本机用相同nvcc、sm_89、锁定电源/后台负载，扫T=1…8与rows=1/2/4；每个shape重复，生成4090表，保留原始样本。同一窗口内用 main 自带的 `b6_mmvq_bench` 测 `STRATA_B6_MMVQ_ROWS`=0/1/2/4（B6 跨行复用片段，逐位一致；#3230 在 gfx1201 上 Q6_K head T=4 −29.6%、MTP head T=5 −19.2%）。29 是 `--spec 4`，重点看 T=5。#3230 新增的 Q6_K/Q4_K/Q5_K 等 B6X traits 是否在 CUDA 编译路径生效需先审计，不默认移植。
- B3：新表只匹配sm_89及经过验证的shape；没有证据的cell保持原表或0，不把4070整表当作4090最优。
- B4：加实验master gate STRATA_LAB_PR3453（本包新增），off选冻结main表，on选候选表；分别记录实际命中次数。

**Review Gate B**：至少检查主线程/worker、异步copy、缓存身份、取消错误恢复和默认关闭路径。可以并行进行文档/CPU测试审查，但GPU实验只能串行。

### Phase C：失败测试与正确性

- C1：表索引、格式编号、shape class和T边界检查；未覆盖架构必须保持原路径。
- C2：同一shape的普通/IL输出bitwise parity；T1/2/3/4/5/6/7/8与尾行。

要求在未修改A0或关闭路径上看到机制测试失败（对于纯性能优化使用已固定的性能断言/dispatch断言），在候选中通过。不能把缺失测试数据导致的skip计为pass。

### Phase D：实机A/B

- D1：运行并保存 mmvq_il_parity --bench --emit-table 的完整输出。只改变表，不改变MTP深度。
- D2：固定512输出，4K/32K/64K/96K/120K；报告verify窗口耗时、decode_ms、MTP接受率。
- D3：若微内核快但API整体<5%或与A/A噪声重叠，结论NO_BENEFIT；不继续大规模调参。另跑一个只作参照的 CFG-IL0 arm（不进入配对统计），候选在 ≥64K 上不得慢于它。
- D4：A0 是否带 CFG-EXACT 由 P0-T6 先定；B6 行复用若 CFG-EXACT 已开启（`STRATA_B6_MMVQ_ROWS=1`），本项只比较 IL 表本身，不重复计入。追加一组使用 Pi 采样参数的抽查（见测试协议）。

**必须观察到的机制回执：** 独立sm_89表实际命中；每shape时间与端到端窗口时间均有记录。

**停止条件：** 端到端没有增益、只有不相关quant快、寄存器溢出或parity失败时停止。

### Phase E：留出与结论

E1：同一Java mini-agent题集与真实Pi留出任务。E2：按统计协议产出CI、质量、资源与回退报告。E3：写DECISION.md并保留最小补丁。**Review Gate E**：只有经过独立留出验证才能推荐生产，脚本不会自动切换。
