## 1. 证据与本机上限

**来源报告（作者，RTX 2060 SUPER，同款 GSQ-RCO IQ3_XXS，`--spec 3`）**：改文件类回合几乎所有 lookup 草稿都被接受，decode 受 `--spec`+2 的窗口上限限制；`--lookup-max-t 16 --lookup-sizes 8,16` 后 edit / rename 类 decode +19%，needle 10K +12%，默认路径与开关路径 greedy 输出逐字节一致。

**本机实测上限（已观察，2026-10-26）**：单会话采样 + thinking 负载里，被接受的 lookup 草稿只占生成 token 的 3.6～5.6%（`session/r1536-on-1`、`session/pt0-java`、`chain/pt1-*`、`chain/pt0-1` 引擎日志 `suffix drafts` 行）。thinking 是新文本，lookup 只在照抄代码时命中。按 Amdahl，问答型会话端到端上限约 2～3%，低于组级 A/A 噪声（约 ±2%）的分辨力。

**推断**：只有 Pi 的改文件 / 整段重写回合（例如每轮输出完整模块）占比高时才可能有可见收益。

## 2. 审计入口

- `kVerifyLongT=16` 只用于单会话串行 decode；超过 8 的窗口拆成两组各 ≤8 行，CPU 专家、drafter、各层 kernel 仍是 8 行。
- 每个窗口尺寸一张 CUDA graph（约 20～35 MiB）；`--lookup-sizes` 控制捕获集合；捕获失败时 `DraftPolicy::disable` 并回退小尺寸。**本机风险**：额外 graph 显存会挤掉驻留专家，增加 CPU miss，可能抵消收益。
- A0 与 PR base（main `7dd5cf18`）之间的 verify / mtp / generate 差异先列 PORT_AUDIT。

- **D A/B**：base / off / on，重写型会话为主场景，问答会话为非目标场景（时间 ratio 上界 ≤1.03）；记录额外 graph MiB、驻留专家数变化、CPU miss / 窗口。

**停止条件**：问答会话退步；额外 graph 让 expert cache 减少导致每窗口 CPU miss 上升而抵消收益；目标负载 lookup 份额过低。
