## 1. 证据、收益与适用性

**来源报告：** 独立2060SUPER8GB报告4K/16K/32K Prefill约+17/+17/+23%；作者另一多卡Q8配置没有时间收益。重要负例是每个小续写也搬两次约675MiB导致约0.2s额外开销。 [来源](https://github.com/Niko1221/Strata/pull/3307)

**本机判断：** 4090是否受ring约束要看现有布局，不能用8GB卡幅度外推。29 上 expert cache 占 9434 slots / 15.29 GiB、`--vram-reserve-mib 974`、`--prefill auto`，128K int8 KV 的驻留方式未验证，机制值得测，但可能已有足够ring。优先于更侵入式3281。**主指标收窄为未读 ≥8K token 请求的 TTFT**：29 上 prefix reuse 89～94%，多数请求未读很短，不应期待全量平均收益；67 个请求中 6 个冷启动占 prompt 时间约一半，是本项的主要目标样本。

收益数字不是本包作者4090实测，也不作为验收预设答案。先证明瓶颈存在，然后决定是否继续。

## 3. Phase / Task

### Phase A：机制资格与最小设计

A1：运行doctor与qualify；保存模型、KV、MTP、缓存、CPU/PCIe和内存证据。A2：构造能反映该机制的最小样本，确认不是不相关瓶颈。A3：冻结主指标、off/on语义和资源状态图。**Review Gate A**：条件不成立就NOT_APPLICABLE，不先写大改。

### Phase B：最小移植

- B1：保持MTP专家block地址不变，原位用作prefill ring；不能free/reallocate使已捕获decode graph失效。
- B2：阈值按本轮未读token，不能按总prompt。默认尝试4096或16384，先测转折点，再锁定留出验证参数。
- B3：回收必须在第一个decode窗口之前；取消、NaN重试、prefill失败、request结束都走明确回收状态机。
- B4：禁止batch，与3281互斥；保留main新的draft类型检查，不能在DFlash2配置上假装有MTP专家block。

**Review Gate B**：至少检查主线程/worker、异步copy、缓存身份、取消错误恢复和默认关闭路径。可以并行进行文档/CPU测试审查，但GPU实验只能串行。

### Phase C：失败测试与正确性

- C1：资源状态idle→loaned→restored与重复关闭幂等；失败注入不能双重恢复。
- C2：未读7/128/512token不借用；总历史120K也不能改变这点。
- C3：draft不是MTP、batch模式、block尺寸变化时明确拒绝或回退。

要求在未修改A0或关闭路径上看到机制测试失败（对于纯性能优化使用已固定的性能断言/dispatch断言），在候选中通过。不能把缺失测试数据导致的skip计为pass。

### Phase D：实机A/B

- D1：4K/32K/64K/96K/120K fresh prompt，记录ring/chunk、lend/reclaim DMA时间、TTFT和decode。
- D2：长输入之后马上做20轮短追加，确认没有每轮大DMA；执行取消/重试后的第一窗口。
- D3：对比固定geometry与auto geometry：区分资源事务开销和planner获益。

**必须观察到的机制回执：** 确实扩大ring/geometry且未读小于阈值时不发生借用。

**停止条件：** ring不受限、reclaim成本吞没收益、取消后状态不正确，或需与3281同时开才有收益时停止并另立组合实验。

### Phase E：留出与结论

E1：同一Java mini-agent题集与真实Pi留出任务。E2：按统计协议产出CI、质量、资源与回退报告。E3：写DECISION.md并保留最小补丁。**Review Gate E**：只有经过独立留出验证才能推荐生产，脚本不会自动切换。
