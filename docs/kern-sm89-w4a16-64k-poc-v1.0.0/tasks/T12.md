## 实施与测试步骤

- [ ] **Step 1 — 写失败测试。** 在本任务test文件中把以下行为做成断言，至少包含一个故意破坏数据/元信息的负例，不用“空数组也通过”的fixture。

- usage与输入ID数组长度65536一致，无truncation。
- 2K生成结束前保持≥512MiB余量或报告内存未达标。
- 声明64K却实际只送短prompt的负例被判FAIL。

- [ ] **Step 2 — 验证RED。** 在固定源树中执行：

```bash
python3 -m unittest discover -s tests/sm89 -p 'test_T12.py' -v
```

首次应因本任务尚未实现的合同而失败。若失败来自拼写/导入环境，先修测试基础；缺GPU应BLOCKED，不把错误日志当数值失败。T00/T01没有GPUtest时先运行`bash scripts/self_check.sh`和文档中的只读命令，并保存actual findings。

- [ ] **Step 3 — 最小实现。** 先4K→32K→64K阶梯。记录weight、scratch、activation、KV、所有slot和CUDA graph。超过预算先收紧workspace/生命周期，不改数学。明确只引用language权重。内存计量包括first-run transient而不是仅空载nvidia-smi。

- [ ] **Step 4 — 验证GREEN与GPU Gate。** 重跑单测；涉及GPU的任务在授权维护窗口中执行固定接口：

```bash
python3 tests/sm89/run_gate.py --gate T12 --config work/poc.local.json \
  --out work/records/T12/gate.json
```

此命令由T03统一runner驱动各任务真实实现。它不能仅返回预设JSON；必须记录实际子命令、退出码、device和输出文件hash。T00–T02只运行对应CPU工具，不要求尚未创建的runner。

- [ ] **Step 5 — 审阅并提交。** 检查改动没有触碰production路径、没有在runtime硬编码模型名、没有放宽数值阈值。保存`git diff --stat`和原始日志，再提交单一任务：

```bash

git commit -m 'feat(sm89): T12 64K容量与峰值内存实现'
```
