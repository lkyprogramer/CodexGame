## 接口与不可变约束
- 批准包含host、容器、镜像digest、时间窗口、允许停机和回滚触发；不从“可直接部署测试”推断无限生产改动权限。

全局约束：固定 source-lock；生产 profile 沿用 P0；计数/计时不进入 identity；不删失败测试；同一阶段源文件锁不能被两个 worker 同时持有。详见 `../00-master-plan.md`。

## Red → Green → Review 执行步骤

- [ ] **1. 建立可失败断言。** 新增/迁移测试按下列命名与行为验证；源码导入/取证类任务运行已有 fail-closed 检查，不为制造失败故意破坏生产。
- ApprovalRequired：未明确批准生产目标时仅test执行，final release状态PENDING而非伪PASS。
- CanaryHealth：从受控少量Java会话起步，监测error/toolcorrectness/TTFT/cache/memory，不仅health200。

- [ ] **2. 记录 RED。** 新增功能的测试应在缺失实现或错误旧行为下失败。失败原因必须是预期断言，不是路径/依赖缺失；已有上游实现使测试本来通过时，明确记录继承既有测试及新增回归负例，不伪造 RED。

- [ ] **3. 实施改造。**
- 排空旧实例并确认旧镜像三件套保留；候选作为唯一驻留模型启动。
- 先合成smoke再受控实际会话；因单GPU不可做双模型百分比分流，按时段和会话白名单逐步放量。
- 采用P0预先冻结观察量：至少一个有代表性的业务窗口且≥100次已完成请求；不足时不完成最终生产资格。
- 任何状态污染/OOM/工具错误或持续超过门槛立即停止放量并执行T05回滚路径。

- [ ] **4. 运行 GREEN 与负例。**
- 按 deploy/merge-runbook.md 的已批准target执行；命令和退出码写入canary-report，不在本包预填成功。

命令中的新增target必须先在本任务创建并由Integrator注册。涉及未核实的现有target，先从 `ctest --show-only=json-v1` 展开精确名称并写入required-tests；不能凭空假设目标存在。任何匹配零项均失败。

- [ ] **5. 提交独立任务成果。** 仅 stage 本任务文件，写明实现、测试、适用模型/codec、未执行项；记录实际提交SHA与raw evidence SHA256。不得推送/部署到生产目标。使用有意义的 `merge:` / `fix:` / `test:` / `perf:` commit message。

- [ ] **6. 任务自审并提交统一 gate。** 自审不是 phase review 的替代；与其他 worker 集成到一个固定提交后重新跑阶段必测。若 gate review 修改源码，必须重新生成相关证据。
