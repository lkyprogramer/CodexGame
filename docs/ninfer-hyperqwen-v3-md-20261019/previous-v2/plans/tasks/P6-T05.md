## Red → Green → Review 执行步骤

- [ ] **1. 建立可失败断言。** 新增/迁移测试按下列命名与行为验证；源码导入/取证类任务运行已有 fail-closed 检查，不为制造失败故意破坏生产。
- RollbackUsable：旧实例实际恢复health、一次正常生成和完整tool-call回路；旧cache可用或合法coldmiss。
- VersionIsolation：候选payload未写进旧namespace；旧启动参数不混入rk4v4新格式。
- ReleaseTruth：源码完成、chat生产资格、optional资格和实际发布状态分别列出。

- [ ] **2. 记录 RED。** 新增功能的测试应在缺失实现或错误旧行为下失败。失败原因必须是预期断言，不是路径/依赖缺失；已有上游实现使测试本来通过时，明确记录继承既有测试及新增回归负例，不伪造 RED。

- [ ] **3. 实施改造。**
- 在批准测试/维护窗口执行候选→旧版本切换并跑真实smallprobe；不只检查命令存在。
- 记录排空/停机/恢复时间和失败请求处理；进行中的写工具不得自动重试。
- 保存finalsource/images/profiles/gates/quality/perf/caveats；按已批准release决定最终驻留旧版或新版。
- 输出统一最终review与gate；保留旧镜像/cache至约定观察期结束，清理另行批准。

- [ ] **4. 运行 GREEN 与负例。**
- 按 deploy/merge-runbook.md 回滚三件套并运行标准Chat+tool smoke；保存真实log与manifestSHA。

命令中的新增target必须先在本任务创建并由Integrator注册。涉及未核实的现有target，先从 `ctest --show-only=json-v1` 展开精确名称并写入required-tests；不能凭空假设目标存在。任何匹配零项均失败。

- [ ] **5. 提交独立任务成果。** 仅 stage 本任务文件，写明实现、测试、适用模型/codec、未执行项；记录实际提交SHA与raw evidence SHA256。不得推送/部署到生产目标。使用有意义的 `merge:` / `fix:` / `test:` / `perf:` commit message。

- [ ] **6. 任务自审并提交统一 gate。** 自审不是 phase review 的替代；与其他 worker 集成到一个固定提交后重新跑阶段必测。若 gate review 修改源码，必须重新生成相关证据。
