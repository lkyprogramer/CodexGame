## 2. 推荐的合入策略

采用“固定 O 建集成分支 → 按上游祖先链做里程碑 merge → 每阶段保留项核对、review、测试 → 最终验证 U 是祖先”的方式。不 rebase 已部署公共分支，不在生产目录直接 `git pull`，也不把 34 个提交随意挑选 cherry-pick。

第一段先合入最直接改善编码 Agent 的变更：缓存断点、分段编码、工具解析、请求级错误隔离、预填充调度、异步 continuation 导出及 small-T CUDA 内核。第二段再引入新的 KV 格式、决策执行、日志与视觉能力，并按现有生产用途控制启用范围。

最终的源代码集成检查是：`git merge-base --is-ancestor <OURS> <CANDIDATE>` 与 `git merge-base --is-ancestor <UPSTREAM> <CANDIDATE>` 都成功。**这只是历史包含性检查，不是实现正确性证明。** 还必须检查定制保留账本、源码差异、独立 oracle、实机测试。

## 3. 不能简单“选 ours / theirs”的六个地方

### 3.1 B0/B1 与上游分段编码重复解决同一个热点

你的 B0 按首字节桶进行单调扫描，B1 从最后一个已选中 added token 的结束点重新编码边界局部，并记录请求级工作量。上游 `94cdb5a` 保存完整编码的分段信息，支持任意字节断点的最长公共 token 前缀。这两个实现不能直接堆叠：会造成重复编码、重复状态与语义不一致。

推荐保留 B0 扫描后端，输出上游 `SegmentedEncoding` 所需的段描述；B1 的 memo、计数和 restart trace 作为同一遍扫描的附加结果。生产边界模型统一到上游，旧结构只留在测试适配层。[S04—S08]

### 3.2 “边界必须精确”与“显式边界向前吸附”不是同一规则

模板生成的隐式边界必须是精确 token 前缀；客户端显式字节切点允许落在 token 内，此时要返回与全量编码一致的最长前缀。重复、归零、越过重写前沿的边界还要按上游规则过滤。把旧 B1 的“不是完整精确前缀就抛异常”直接套给显式断点，会破坏新协议。[S06—S08]

### 3.3 两边都曾叫 schema 20，但不是同一份日志协议

你的 schema 20 是 prepare_detail 和 size 扩展；上游的 schema 20 是流式工具调用变更。最终上游已到 schema 24。选择上游 schema 24 主体，保留你的字段，另用命名扩展标识 `lkyprogramer.prepare_detail`。不能把最终常量改回 20，也不能只根据旧数字 20 推断字段一定存在。[S09、S14、S16]

### 3.4 `rk4v4-e8` 已被上游删除，不是默认参数的小改动

`772b881` 删除旧 4-bit E8 lattice 路径，统一采用 midrise 4-bit 平面。连原有 `rk4v4` 的编码语义也变了。快照/continuation 格式随之升级，最新图像状态又继续升级。不能把旧参数当成新参数的别名，更不能复用旧目录中的旧状态镜像。[S12、S16]

建议采用上游新实现，用独立配置和新缓存目录做长上下文 A/B/A。保留旧镜像、旧参数和旧缓存作为回滚三件套，而不是默认在新运行时再维护一套 E8 内核。新编码不通过质量或容量验收时，P4 不放行；P3 可作为阶段性交付，但不得宣称最终上游已生产验收。

### 3.5 异步导出把“正确性”从函数返回值扩展到了生命周期

新导出线程允许请求提交与大 continuation 导出重叠。被导出的 lane、device buffer、pinned host buffer 必须存活到完成事件；重置、取消、逐出、复用和 adapter 切换都要守住 fence。文本无冲突的 executor 改动也可能在真实并发下产生跨请求污染。[S13]

### 3.6 当前生产物与分支 HEAD 不能画等号

仓库中的 2026-09-28 审计记录显示：当时生产镜像是 `prepare-detail`，来源为共同祖先加计时 overlay，生产源码目录不是 Git checkout。该记录不证明你今天仍运行同一个镜像，也不证明 b0-scanner HEAD 已部署。P0 必须重新采集实际镜像 digest、模型指纹、完整参数和代理的 reasoning 设置。[S02]

## 4. 预期收益与不能承诺的部分

| 改动 | 预期改善 | 本次不能直接保证 |
|---|---|---|
| 分段编码 + B0 + memo | 多轮、长工具历史的准备耗时和重复 tokenizer 工作 | 你的机器一定比现有 B1 更快 |
| 显式断点、alias kind、payload 去重 | 路由缓存复用正确性、减少 L2/L3 重复导出 | 旧缓存无缝沿用、所有请求命中率都上升 |
| 准入与异步导出 | 冷请求与热请求混跑时的等待与尾延迟 | 增加单卡总 KV 容量、保证公平 QoS |
| small-T MMA | 解码/MTP 验证的小批次投影成本 | 100K+ 下整体速度按短上下文比例提升 |
| 新 KV codec | 保留压缩容量，改善部分量化偏差 | 量化前后逐 token 或概率完全相同 |
| 流式工具调用 | Agent 更早拿到结构化参数，减少输出解释偏差 | 客户端可以在工具闭合前安全执行 |
| 决策与视觉 API | 增加独立能力 | 无干扰地提高现有编码服务吞吐、无需训练就有视觉决策精度 |

上游公布过 `rk4v4` 相对旧 E8 的长预填充约 +2.3%、类似的长上下文 decode 速度；这只是对应提交中的 4090、CUDA 13.2、指定负载记录。不能把它写成你的收益承诺。对你高缓存复用的编码场景，CPU prepare、恢复和排队变化可能比冷 prefill 峰值更重要。[S12]

## 5. 最终交付判定

本计划的核心完成标准是：最新上游历史包含、14 个生产源码定制的行为保留、旧与新 oracle 角色清晰、100K—248K 场景通过、三套生成 HTTP 协议正常、恢复/并发/取消无污染、单卡容量可控、可回滚、原有 reasoning 模式不降级。

可选择的附加完成标准是决策/视觉决策实模型验收。缺少决策 adapter 时，可以交付“源码全量合入、Chat 生产资格通过、决策未资格化”；不得把 adapter 测试的 skip 写成通过，也不得在生产模型发现中暗示已验证它的业务精度。
