# 29 单卡 RTX 4090 · Qwen3.8-27B 的 130K 多会话选型

2026-11-18，北京时间。目标是让同一张卡完成更多有效的编程或推理任务，同时让正在交互的用户及时收到输出。本文把 130K 解释为每条会话 **131,072 个总 token**，包含模板、历史、工具、思考和输出。如果业务要求的是 130,000 个输入再生成 8,192 个输出，单会话就要约 138,192，双会话也要重新算容量。

## 开启 medium thinking 后，长主会话该用哪套

**按“一条长主会话为主，偶尔派一两个短搜索代理”，29 上首选 HyperQwen 0.33 single、DFlash2-7、6 GiB KV、medium thinking。给同一主会话派出的短子代理共用一个模型请求名额。** 主工具始终可用。这样既保留单主续写速度，也在两次 12 万 token 的双子汇报中保住了长前缀。主要收益来自取消一次约 65 秒的重读。若编排层必须允许两个子代理同时占 GPU，优先 HyperQwen MTP3；如果确定整条对话只会独立续写，默认 5.2 GiB 的 DFlash2 实测略快，显存余量也更大。 [逐配置实测摘要](../output/qwen38-130k-multisession-20261118/thinking-summary.json)

前一轮的 NInfer 和 HyperQwen single 已经开了 MTP3，HyperQwen batch 关闭了投机解码，三者都关闭了 thinking。当时得到的纯短请求 C3 交叉点、以及主会话等两子的 7–9 秒，只适用于对应的短答设置。本轮在 29 的同一张卡上明确请求 `medium`，比较 NInfer MTP3、HyperQwen MTP3 和 DFlash2-7。以下时间均为秒。

NInfer 保持工具可用时，两条纯轨迹分别合格 **0/8 和 5/8**。十一轮失败中，八轮擅自调用派工工具，两轮给出残缺的工具标记，一轮只有解释、缺少要求的结构化结果。测试器回填了真实拒绝回执，未执行额外搜索。这些失败让“全部热轮完成”降到 3.73 秒，14 个热轮中只有 7 轮出现可见正文。仅取答对的 5 个热轮，完整交付中位数为 **8.88 秒**。NInfer 未提供可比较的逐请求思考 token 数，证据保留了全部实际生成 token 及思考首段时间。

为 NInfer 另跑了两条相同纯会话，只从第一轮起固定 `tool_choice=none`，请求仍携带相同工具定义。16/16 轮都返回正确的结构化答案，完整解释为 **14/16**，热轮首正文 **6.69 秒**，完整回答 **10.16 秒**。一处把被更正的旧事件 ID 当成当前更正事件的去重键，另一处把“先预留后发货”说成唯一能保持非负的顺序。此选项适用于确定整段无需工具的会话。会话中途切换会改变 NInfer 渲染的长前缀，后文有该代价的独立实测。

DFlash2 的 5.2 GiB 与 6 GiB 实报共享 KV 池分别为 **133,883、154,615 token**。两种配置同时让两名子代理推理时，约 12.2 万 token 的主汇总在 **4/4 次**都命中 0。四次完整汇总分别为 65.93、67.22、66.02、66.92 秒，vLLM 的抢占计数均为 0。空闲历史的可复用前缀会丢失，即使当时没有运行中的请求被抢占。扩池期间计时最低空闲显存由 **1,235 MiB** 降至 **415 MiB**。同一深度只派一子时，两种配置都能保住长前缀。

HyperQwen MTP3 在两条深轨迹的双子轮分别用 **3.56、2.81 秒**完成最终汇总。NInfer 两次汇总复用 **120,573、120,644 token**，用时 **2.56、3.28 秒**；用户等到最终答案仍需约 26 秒。四份 NInfer 子报告的服务端排队为 **13.69–16.10 秒**，各自 prefill 约 1.21–1.27 秒。若继续优化 NInfer，这组数据把优先级指向子请求入队后等待调度的时间。

三种基础配置各有 12 项真实源码搜索。每个子报告和主汇总的事实、所属文件与回执均逐项核对通过。HyperQwen MTP3 的两轮失败都在主会话独立题，一轮误调空任务工具且未作答，一轮先给出错误 JSON，随后在同一条公开回复中更正；按首个结构化答案判失败。另有一轮在正确答案后的附加说明触及 2,048-token 上限，已单独标记。

**客户端调度改变了 DFlash2 的结果。** 主会话收到两项任务后同时提交两个独立 worker，保留各自的原生工具和回执。在客户端给短子代理的模型请求共用一个容量为 1 的信号量：生成搜索调用和生成子报告时占一个名额，执行 `rg` 时释放；主会话的请求不占这个名额。两个子任务的外部工作仍可独立进行，实测两份搜索都完成。各 worker 的模型区间逐一通过时间戳互斥检查。6 GiB 的两次深主汇总均复用 **120,960 token**，分别用 **1.93、2.58 秒**。两子整轮分别 **9.42、11.12 秒**，十轮轨迹从 **193.78／194.37 秒**降至 **131.27／136.37 秒**。两种调度在这 20 轮都完整答对。

相同的错峰策略放回 **5.2 GiB**，两条轨迹的主汇总再次命中 0，分别耗时 **65.98、66.71 秒**，整轮 **73.57、75.24 秒**。在这组 2×2 配对中，**6 GiB 加子推理错峰**才在两个编号上同时保住了主前缀。只改显存或只改调度都复现了停顿。这个结果支持在这台 29 上部署这一组合，不能推出所有 130K 提示都有相同的容量临界点。

- **请求。** 主、子都开 `reasoning_effort=medium` 和 `preserve_thinking=true`。HyperQwen 同时传入模板的 `enable_thinking=true` 和 `reasoning_effort=medium`。温度 1.0，top_p 0.95，top_k 20，seed 42，presence/frequency penalty 均为 0。独立题与子报告的思考和输出共用 2,048 token，派发上限 1,024，代码上限 4,096，允许模型自然结束。

- **适用边界。** 混合组的 80%／10%／10% 是设计比例。题目用英文编程审计、冻结源码和合成库存长历史，搜索在 29 本地执行。没有采集个人生产流量，两次配对不足以给出 p95 或泛化质量排名。保留历史思考、工具策略、模型转换与真实输出长度都会影响数值。本轮没有同权重关闭投机的 medium 消融，接受计数验证了各投机路径实际工作，端到端差值反映整套配置。关闭 thinking 时的双独立长会话和短并发扫描保留在后文。

**验证与现场。** 本轮 412 次正式流式模型请求均出现了思考事件，覆盖 180 轮混合对话、80 轮纯单对话、8 次独立代码实现或修订。54 项真实源码搜索逐项核对了子报告及主汇总。四组独立代码样本的执行回执合计 52/52。北京时间 **16:53:49** 复核，29 的实验容器已移除，GPU 无计算进程，显存占用 1 MiB，实验端口与 Strata 端口均无监听。原 Strata 单元 `openclaw-qwen38-next.service` 保持 **inactive / disabled**。

## 关闭 thinking 的对照 · 一条长主会话派发 1–2 个短搜索子代理

**在关闭 thinking 的短答测试中，主会话派工后等待并汇报，29 上自己的 NInfer 三槽最快。** 主会话如果经常在搜索期间继续做一段实质推理，**HyperQwen 0.33 的 single MTP 三槽**更合适。两者的真实工具链都完成了 12/12 轮，各自的 18 项子结论均正确进入最终汇报。前一轮测到的纯短请求 C3 交叉点，不能直接用来给一长两短选后端。[结构化实测摘要](../output/qwen38-130k-multisession-20261118/fanout-summary.json)

- **NInfer 三槽。** 保持主会话使用同一 `prompt_cache_key`，从第一轮起固定主工具列表和排序。子代理使用独立会话，只带自己的问题和搜索片段。测试使用 131,072 单会话上限、163,840 共享池、3 个活跃槽。这份容量服务于一长两短。29 运行 B0+B1 镜像 `e753e228` 和 E8/MTP3。本地 `f4089901` 分支没有参加本轮。
- **HyperQwen 三槽。** 使用 `single`、`SPEC=mtp CTX=long PTH_FA=1 MAX_LEN=131072 MAX_SEQS=3`，使用准备好的 W4A16 AutoRound 基础权重、3 枚草稿 token 和前缀缓存。29 的该配置报告 GPU KV 池为 173,542 token。主会话反复切换工具开关时，可直接对照下文，或先调整编排以保住 NInfer 长前缀。
- **主会话的工作决定选型。** 有独立工作就与搜索重叠。如果它的下一步依赖搜索结果，直接等两份报告再汇总。保留每个任务的 ID、文件和回执，便于检测提前结束的汇报。计时中一子和两子完成的题数不同，二者用于估算各自用户等待时间。

### 在 29 上怎样复现这个工作流

主会话从 11 条消息开始，六段长记录之间夹有五条历史回复。私有标记埋在长文中间。每套配置用三个不同前缀分别冷读。流式组每条轨迹连续五轮，固定工具组每条轨迹连续四轮。主会话回填本引擎实际生成的派发指令、独立工作和子报告。相同编号的轨迹在各引擎上使用同一组问题，三条轨迹轮换场景顺序。冷读首字单列，整轮耗时从已建立的主会话收到派发请求计至用户收到最终汇报。

子代理独立执行真实的本地 `rg`，读取当前项目 `d7fd182f` 冻结的五个源码文件。12 道题覆盖调度、超时、状态持久化和重连。例如，调度子代理要找到覆盖间隔的环境变量，持久化子代理要找到原子写入函数。每次检索都验证结果 SHA256。子模型只收到自己的任务和命中片段。主模型最后看到子模型实际写出的报告。审计逐题核对源码事实、归属文件和检索回执，并另外核对原长会话标记。

流式对照包含「等待」和「继续工作」。等待时，派发后主会话空闲，收齐报告便汇总。继续工作时，客户端在主会话首次输出非空正文后放行子代理，让同一张卡同时处理长会话续写和新到的短请求。同轨迹另跑主会话独立工作的对照。派发、子报告、主工作、汇总的输出上限分别为 128、192、384、320 token，允许提早结束。两种模式的主会话工作量不同。每种形状只有三个样本，表中报告中位数，不估计生产 p95。

流式计时组使用正文 JSON 派发和 SSE，以测到正文停顿。派发格式错误时，计时客户端按原定题目放行，保留该轮耗时并单列回退。原生对照通过 API 的 `tool_calls`、实际 `tool_call_id` 和 `role=tool` 回填结果，遇到非法调用就记录该次失败。初次试跑曾给汇总 128 token，观察到两个子代理都查到了，主会话却只交付第一份。该试跑从正式比较中剔除。

搜索使用 29 的本地回环和冻结仓库。报告中的墙钟包含调度、分词、检索、模型推理和生成汇总。公网搜索的网络等待、子代理继承整段主历史、开放式任务质量，以及真实用户历史的命中分布仍需各自的流量验证。

**验收与机器状态。** 固定工具组完成 60/60 轮，模型实际返回 375 次。流式组 300 次正式请求全部正常结束。另有五套配置各一次的工具开关对照与一组独立的 MTP 预试。北京时间 **14:34:44** 复核，测试容器已移除，测试端口和原 Strata 端口均无监听，GPU 无计算进程，显存占用 **1 MiB**。原 Strata 服务 `openclaw-qwen38-next.service` 保持 **inactive / disabled**，等待明确恢复指令。[结构化结果](../output/qwen38-130k-multisession-20261118/fanout-summary.json)

### 只保留一套配置时怎么选

**如果主要工作是两位用户反复读写长历史，NInfer 双槽更合适。** `--max-context 131072 --kv-capacity 262144 --max-concurrency 2` 启动后尚有约 **1.18 GiB** 显存。也实测了保留 262,144 总池、只把槽数增加为 4 的配置。双冷、双热、追加一、追加二整批分别用 **117.67 / 7.19 / 4.28 / 4.33 s**，标记全部通过，但启动后显存余量降至 **584.5 MiB**。四个槽适合调度若干较浅请求，整池仍只够约两份 130K 私有历史。短请求专用的 NInfer 八槽则使用 **131,072** 总池。三档均使用同一份 B0+B1 镜像和模型。当前本地 `f4089901` 的新调度仍待独立对照。

### 复现条件与边界

**怎么测。** 两条会话分别使用库存预留和网关重连记录，私有标记放在各自长文中间。先用 NInfer 的计数接口冻结文本，再把完全相同的首轮消息送给两个引擎。每个新容器先用无关的 4-token 请求预热。冷读指两个业务前缀都未出现过，计时不含装载模型和编译算子。热读精确重放首轮。随后每条会话连续两次提交完整消息历史，带回本引擎刚生成的真实 assistant 和一个新用户问题。第二次追加带五条消息。测试逐轮检查旧标记、新标记和对方的标记。首轮要从文档中间找回标记。追加时上一轮回答也可能含该标记，因此续轮检验的是会话连续性。两种权重可能生成不同的回答，续轮输入长度以各自 usage 为准。

两端均关闭 thinking，使用贪心、`top_k=1`、`top_p=1`、presence/frequency penalty 均为 0、seed 42，输出预算 256。NInfer 用公开的 `prompt_cache_key` 为 A、B 分别保持稳定路由。HyperQwen 使用默认内容前缀缓存。短请求从正文开头就带独立标记，各并发档按升序、降序各发一波，波内从屏障同时放行。表中吞吐按两波总实际输出除以两波总墙钟，包含排队、分词、prefill 和流式交付。首 token 计到客户端收到第一个非空正文。所有客户端与服务都在 29 的回环上运行。

29 上 NInfer 使用 B0+B1 镜像 `e753e228…`、18,210,531,328 字节的 Dense 27B 制品、E8 KV 和 MTP3。HyperQwen 使用 `3d6c9543` 的固定镜像 `926ebaaf…`，镜像内版本为 **vLLM 0.33.0**。AutoRound 权重固定为 `1f05c441`，8 个源 safetensors 通过 SHA256。按上游 CPU 准备流程保留 W4 主体，量化输出头、embedding、MTP 并生成草稿词表。实际 `batch` 路径使用 Marlin MLP INT8 激活、FP16 GDN 和前缀缓存，关闭投机。两套服务的模型转换和加速路径不同。上述标记只验证这两份合成记录的检索和会话隔离。源码搜索的原生工具链见上文的 medium 与关闭 thinking 两组测试。Java 改错和开放式长文推理的任务通过率仍需真实回放。

**验收与现场状态。** 正式对照及交叉点复测有 **32 个长请求、1,116 个短请求**，全部收到正常 SSE 结束、实际输出 256 个 token 并通过各自标记检查。每个长会话配置只测了一对独立会话，每条连续三轮。两端按配置先后独占 GPU，主机保留原有的 CPU 服务，复测数字反映这台机器在该时段的表现。首次 NInfer 预检因 `repetition_penalty` 未受支持而返回 HTTP 400，删除该参数、在新容器中重新冻结相同文本后重测。两次从 HyperQwen 换回 NInfer 时，原回环端口绑定失败，改用独立端口后完成。上述失败均保留原日志，未计入吞吐。北京时间 **12:48:48** 复核，测试容器已移除，测试与 Strata 端口均无监听，GPU 占用 **1 MiB**。按最新指示，原 `openclaw-qwen38-next.service` 为 **inactive / disabled**，等待明确恢复。29 本机保留已准备的模型、镜像和编译缓存，后续复跑可直接复用。[实测摘要](../output/qwen38-130k-multisession-20261118/ab-summary.json)

## 单条窗口和整卡 KV 池如何分配

Dense 27B 的 64 层里，16 层用全注意力，每层 4 个 KV head、head dimension 256；另外 48 层用 Gated DeltaNet。模型权重只加载一次。注意力 KV 随各活跃会话的实际长度增长，GDN 状态按活跃槽、状态精度和检查点数量计费。把两份 130K 文本放在不同会话中，仍要为约 260K 的私有历史付费。以下均按互不共享前缀计算。[模型布局与状态数组][nmodel] · [原始模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)

| 单条 131,072 token，注意力部分 | 每 token / 每条的需求 | 还需留出的空间 |
|---|---:|---|
| BF16 K/V | 16 × 2 × 4 × 256 × 2 B = 64 KiB / 8 GiB | 权重、GDN、图、工作区、草稿 |
| FP8 K/V 理论载荷 | 32 KiB / 4 GiB | 比例参数、实际混合分组、页碎片和固定状态 |
| HyperQwen INT8 per-token-head | 16 × 2 × 4 × (256+4) B = 32.5 KiB / 4.0625 GiB | 仅 target。DFlash2-long 的名义总 KV 预算为 5.2 GiB，光两条 target 已需 8.125 GiB |
| 此次 NInfer E8 完整规划的增量 | 每 64 token 增 1,183,744 B，折合每条约 **2.258 GiB** | 从启动日志相邻页组的 reservation 差额计算，含布局开销。额外槽位还增加 GDN 和其他状态 |

本次机器实际加载权重 **16.672 GiB**，双槽配置 KV payload **4.516 GiB**，完整 runtime reservation **5.456 GiB**（已含 KV，不应重复相加）。启动后的可用显存 **1.178 GiB**。同一引擎、制品和 codec 下，从两条满窗增加到三条，仅额外历史就要约 2.258 GiB，已经超过余量。当前源码按每槽两份 FP32 recurrent state 及 BF16 卷积历史计算，另需约 **293.625 MiB/槽**，尚有图与工作区等成本。[本次启动记录](../output/qwen38-130k-multisession-20261118/observations.json) · [NInfer 容量规划][nlayout] · [GDN 布局][nmodel]

NInfer 的 `--max-context` 限制每条，`--kv-capacity` 决定整个引擎共享的主 KV 池；省略后者时默认跟随前者。若把两项都减半，只剩一份满窗容量。当前源码对新请求先预留 prompt 和至多 4,096 个待提交输出位置，按 64-token 页取整，后续按需扩展；最终可生成量另受窗口约束。NInfer 有“最后曝光的 token 可不写回 KV”的边界，产品预算用 `输入 + 输出 ≤ 131072` 更容易跨引擎保持一致。两条各 122,880 输入、各留 8,192 输出，比两条各 130,000 输入还承诺 8,192 输出更符合这份合同。[CLI 容量说明][nserv] · [实际准入计算][nadmit]

原生 4090 的 0.33 结果还给出默认 single 池 71,218、报告中 `CTX=huge` 档 198,485、`alternative.sh` 的 INT4 池 302,735。后者默认只开一个槽；改到 `MAX_SEQS=4` 加 8 GB CPU 缓存层后，两条长对话追问的命中率 99.1%、TTFT 0.8 秒。名义池、两轮可恢复和两个 130K 请求同时在 GPU 上 decode 是三个指标。对混合的全注意力/GDN 模型，还要看每活跃序列的 recurrent state、草稿 lookahead、页组与运行期峰值。上游的 “C64 约 1,035 tok/s” 来自 3090 的 128 入/512 出短请求，不能作为 29 上长会话的容量或任务承诺。[原生 4090 版本实测][h033] · [4090/WSL2 对照][hwsl] · [压缩 KV 对照][hlong] · [不同深度席位计算][hseat]

另一台 4090 的独立研究在 `6ab9bd0`、MTP/FP8 上做了 149 个串行请求，128K 冷 prefill 约 72.5 秒，精确重复约 1.3 秒，改写后的多轮追问则有 18/40 报零缓存命中。它说明 exact-repeat 和真实多轮应分开测。当前 0.33 也有 MTP 缓存命中率变高但因抢占而整组耗时持平的案例。[独立 4090 测量](https://github.com/piotrmasior/hyperqwen-results) · [0.33 的抢占案例][h033]

## 哪些优化值得投入

1. **先减少独立冷 prefill 和排队。** 为每个 Agent 使用稳定独立的会话键，保持系统提示、工具定义及消息序列化稳定，变化的工具返回放在尾部。分别回放独立前缀、公共前缀、真实 append、分叉和压缩后的首轮。NInfer 的 L1 是 GPU 上保留的槽，L2 是 RAM 里的完整映像。当前 NInfer 通过私有槽恢复，公共前缀能省 prefill 时间，不能直接从每个活跃槽的容量预算中扣掉。两用户轮流打一个槽，历史 120K–130K 的 L2 restore+preflight 曾需 5.5–7.3 秒。HyperQwen 的 prefix cache 要同时找回 attention blocks 和 GDN 边界。29 是 PCIe Gen3 ×16，CPU tier 有助于停放会话；活跃 decode 所需的 GPU 状态仍须计入显存。[NInfer 缓存机制][ncache] · [HyperQwen batch 缓存说明][hbatch]
2. **解决长请求挡住短请求的问题。** 在已经生成的会话旁插入一条冷长 prompt，再反向测试长 prompt 先到、短 prompt 后到。NInfer 当前分支在 prefill 单元边界接纳其他请求，多个活跃请求可交错，单个 prefill 单元处理一个槽；HyperQwen/vLLM 可把分块 prefill 和 decode 放进同批。先试原配置；有短流饥饿再对 HyperQwen 的 `max_num_batched_tokens` 做 2048→1024→512 对照。4090/WSL2 的 72.6K + 三条 4K 混合输入，2048→1024 时短流 TTFT 从 63–70 秒降到 4.2–7.2 秒，整批略慢。调小这个值服务于交互延迟。[NInfer 调度结果][nperf] · [HyperQwen 混合负载][hwsl] · [vLLM chunked prefill 原理](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill)
3. **用空出的实际容量重新评估 `rk8v4`。** 对“一条 130K + 一条 8K–32K”有价值。29 的 200,192 上限、单流历史记录在 4K/64K/120K/184K 有 145.2/129.0/116.7/103.7 tok/s，四个长度均取回标记；120K 与旧 E8 medium 对照仅差约 1.3 tok/s。若两条都要近 130K，先计算增大的 KV 开销和可用池，再决定是否安排运行。按两种长度混合分别验证，避免拿浅档提升估算深档。[原始 rk8v4 阶梯](../output/qwen38-4090-compare/results/rewrite/ninfer-rk8/http_bench.json) · [同机 E8 对照](../output/qwen38-4090-compare/results/medium/ninfer/http_bench.json)
4. **投机宽度跟着正式产出与批量成本走。** NInfer 以 MTP3 为基线，记录每轮耗时、每轮正式提交数、实际总输出和完整任务墙钟。29 的 medium 实测表明，DFlash2 在纯长会话续写上也有收益。长主会话偶尔派工时，要把搜索后的前缀命中与整轮交付一起核对，详见本文首节。对于大量短流，先用 batch 默认 MLP INT8 activation；上游扩到全部线性层虽提高短流吞吐，也报告约 +3.7% 困惑度且压缩显存余量。要测 Java/中文/工具任务通过率和长检索。对 NInfer 11 月 D1 来源定位、H2 草稿头粗筛，只有真实输出存在复制片段或 head 成本足够时再做。[HyperQwen 两条执行路径][hbatch] · [11 月 D1/H2 研究](ninfer_strata_source_delta_exploration_20261115/docs/00_DECISION_SUMMARY.md)
5. **用真实瓶颈决定是否改 CUDA 或硬件参数。** 在双热 steady decode 采样权重 GEMM、KV attention、GDN、draft/verify 时间及接受率；双冷则拆 queue、prepare、prefill、restore、publish。能量按完成任务和有效输出计，同时记录频率、板功率、温度。29 当前 450 W，上游 115K INT8 prefill 的 2,496 tok/s 来自 480 W、CUDA 13.2；该分支已经为六个 dense GEMM 做了 INT8 路径，重复实现或单凭 GPU 利用率无法说明提速空间。保留默认功耗；若持续负载有降频，再做同温、同功耗条件的对照。[NInfer SM89 实测和条件][nperf]

在冷读接近 100K–130K 已经主导任务墙钟，且缓存和调度的收益都量过后，才值得考虑 HyperQwen 的 **LSA 稀疏注意力**。它在 single、MTP-long 下只改变 16 个全注意力层。3090 的单次冷读对照中，98.7K TTFT 为 126.1→121.2 秒，31.3K 反而为 30.7→36.4 秒，136.7K 的 13% 改善又超过本次窗口。两臂 GPU 内存设置不同。pthfa 后端的能力检查允许 SM89，仍取决于扩展是否可用。4090 上这条 LSA 路径的启动、29 的 130K 收益和长文推理质量均未实测，优先级低于命中前缀。[LSA 实现、适用面与实测](https://github.com/syv-ai/HyperQwen/blob/3d6c9543292efc17372b824071ef8d9f33366b21/lsa/README.md)

### 哪些旧实验可以省掉

| 已试方向 | 已有结果 | 对本次决策的影响 |
|---|---|---|
| 固定 W6、更深 MTP、请求内 n-gram lookup | W6 两个短样本单位 token 快约 20%–23%，Java 后半反慢 13.75%；H1 lookup 的三组单位 token 慢 4.28%–8.11%；旧 n=5 在 184K 约 76.4 tok/s | 130K 上限没有消除 proposal 和 verify 成本。优先利用不同会话共享权重前向。 |
| 卷积、GQA tile、CPU 哈希、导出 | 卷积局部省 36.48%，完整 prefill 仅省 0.314%；GQA Bc64 在 32K 有利、128K 慢 0.156%；P4 四次 Chat 完整耗时合计上升 34.95%。后续导出/发布解耦有 CPU 验证，29 的同合同整机收益未验 | 跨请求导出若真实挡住下一槽，再对照已有修复。单算子的百分比不能累加到服务吞吐。 |
| 更低比特 E8、重写整套引擎、移植 Strata 专家优化 | 29 的 rk2 在 184K 冷首字约 110 s、Java 仅 2/3；Strata 实机是 Flash-Next IQ3_XXS MoE，曾有 CPU 专家、PCIe 及专家缓存瓶颈；研究中的 Kern 起点是 64K、无投机 | 压缩 KV 只有确实多容纳一个目标请求才有容量收益。Dense 27B 没有这些 MoE 专家。llama.cpp WORK 可作交叉质量/协议对照。 |

## 从本次跑分到上线验收

下表是原定的验收矩阵。现已完成 B0+B1 与 HyperQwen 0.33 的双深会话、连续追加、短请求阶梯，以及一条长主会话派发一至两个短搜索子代理的原生工具和流式对照。后续仍可沿用同一口径比较新版 NInfer、不同输出预算和真实业务任务。先用同一套前端到达轨迹、相同输入文本、各引擎实报 token 数、相同 thinking/采样/输出预算；记录有效配置与模型哈希。两引擎权重转换不同，比较的是实际服务组合。先单次淘汰不能驻留或答错的配置，再对有机会胜出的组合交错运行并重复。短波次给原值，样本足够再报 p95。

| 次序 | 负载与配置 | 怎样作决定 |
|---|---|---|
| 1 | B0+B1 vs `f4089901`，同旧权重 + E8 + MTP3；C1/C2/C3，8K、2×64K、2×(约 130K)，以及 120K+8K。每组区分冷、精确重复、真实追加和 A→B→A | 看正式 decode 的双活区间、每用户首/末 token、有效任务/小时；量化新调度是否减少慢请求对短请求的阻塞。 |
| 2 | HyperQwen batch FP8 与上述 NInfer，C2/4/8/16；只有短请求吞吐继续增长且延迟可接受才扩到 32/64；长流同时测独立前缀和预热的共享前缀 | 算 `全部成功输出 token / 从首请求提交到末请求完成的墙钟`，另报所有请求数、失败率、TTFT/ITL 和排队。独立前缀超池时转压缩 KV。 |
| 3 | 只保留两个深并发对手。HyperQwen batch KVarN，必要时换 int4pth；小并发另测 single MTP-long。相同 130K 总窗，预留 1K、4K、8K 输出，依次缩短输入 | 读启动时各长度的 resident requests、实际 running、preemption/recompute、页池和运行期显存峰值。两路各自生成且无抢占，才算双深驻留。跨请求命中高但中途长时间停顿要记为退化。 |
| 4 | 回放原 Pi Java 三题、两条基线失败题、中文长检索、跨会话专属标记、流式工具参数、正常取消后的下一轮。至少加入一段持续到达的真实多轮轨迹 | 先看功能和质量，再在可接受的首字、输出间隔和失败率内比较每小时正确任务数。固定长度输出的 tok/s 用于归因；自然输出按完整任务计费。 |

实操配置起点是 NInfer 的 `--max-context 131072 --kv-capacity 262144 --max-concurrency 2 --kv-dtype rk4v4-e8 --spec mtp --draft-tokens 3 --lm-head-draft --prefill-chunk 1024`。沿用足够的队列超时以完成容量验证；生产应按用户能接受的最长等待设准入和超时。HyperQwen 可先核对 `MAX_LEN=131072 MAX_SEQS=4 KV=kvarn PRINT_ARGV=1 bash batch/start_qwen.sh`；本次本地 dry-run 确认生成 `kvarn_k4v2_g128`、FP16 GDN、2048 批 token、prefix caching + align。本次同机实测沿用相同 KV 与前缀策略，每次只运行一个推理引擎，实测槽数和资源见上方记录。[NInfer 启动合同][nserv] · [HyperQwen 实际 launcher][hstart]
