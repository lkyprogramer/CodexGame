## 执行链与计时边界

```mermaid
flowchart LR
    A[Chat Completions] --> B[GenerationService / Frontend]
    B --> C[ConcurrentExecutor / cache selection]
    C --> D[Prefill / existing Graph]
    D --> E[MTP draft / Target verify]
    E --> F[Existing permit / GDN fold / output]
    D --> G[Background export job]
    F --> G
    G --> H[GPU to CPU copy / release source]
    H --> I[Canonical image SHA256]
    I --> J[L2 alias publication]
    J -. cache readiness .-> C
```

`PreparedPrompt`和request/lane由原Engine所有；正式KV/GDN state、RNG/采样、许可和commit不转移给新哈希后端。publication worker拥有导出的`ContinuationImage`，canonical bytes→SHA256→ContentId；hash在cache mutex之前执行，alias/CAS原子发布仍在原锁内。**哈希已经在锁外**，不能再以“搬到锁外”充当新优化。

代码见本轮固定[源码见证清单](../output/ninfer-v4-k0-20261023/source-witnesses.json)：`http_server.cpp:1289`→`generation_service.cpp:385/483`→`engine.cpp:435/534`→`concurrent_executor.h:296`。publication路径为该executor的`publication_loop:1161`→`run_publication:1062`→`continuation_cache.cpp:723 store_impl`→`:227 hash_serialized`→`artifact/sha256.cpp:203 process_blocks`（行号以本轮见证为准）。

GPU内部attention/GEMM/GDN/norm的耗时占比没有现成trace，本轮将其作为有明确接口的未测部分保留，不逐个展开为新测试任务。已有P3 Op/Graph结果明确写的是host-resolved route而非GPU profiler时间，因此只能复用正确性，不能推导谁最慢。

## CPU热点的最小验证

29为Xeon Silver4216，AVX2可用但SHA指令不可用。P4的`Sha256::process_blocks`已有SHA-NI快速路径；本机不命中，走portable标量压缩。不要重复开发已有SHA-NI，也不要另写cache专用SHA实现。

在`/home/hhtele/ninfer-v4-k0-20261023`中，将未修改的P4 `sha256.cpp`和`continuation_cache.cpp`与新合成探针编译。无CUDA/model链接；L3关闭，cache在内存中。3种buffer（64KiB/16MiB/320MiB）各2次，另测原`content_id`和原L2发布各1次。整个probe运行9.21秒，编译9.59秒。没有执行旧测试二进制。

| 320MiB，2次中位数 | 时间 |
|---|---:|
| 原P4 SHA256 | 1.72961s |
| OpenSSL EVP参考 | 0.81487s |
| 原P4 canonical content_id（独立单次） | 1.73097s |
| 原P4 L2 publish（独立单次） | 1.72975s |

大块哈希参考速度约 **2.12×**，时间降低约52.9%；6次原SHA与EVP摘要比较逐字节一致，只有3种不同输入，不冒称完整密码学回归。首次64KiB EVP包含provider启动，约1.50ms，比原0.38ms慢，启动/小buffer成本必须在候选中保留验证。

这将P4的秒级发布尾部明确定位到大块内容指纹这一CPU函数族；没有证明全部1.7秒都可在原BO构建中消除。探针使用host GCC12.2，而BO为GCC13.3，尚未构建EVP产品后端。[原始probe](../output/ninfer-v4-k0-20261023/probe.jsonl)、[命令/耗时回执](../output/ninfer-v4-k0-20261023/cpu-probe-receipt.json)。

## 为什么首选这一项

C0有同机函数级时间、真实发布事件和成熟参考实现三种相互支持的证据；实现边界集中，保持所有摘要、ContentId和GPU数值/采样合同，不增加KV/Graph显存。它适合先完成无需GPU服务的可构建补丁。

其余候选保留但当前不优先：

- 冷prefill：历史占比大，尚无P4 GPU关键路径，不能由总prefill时间猜GEMM或attention瓶颈。
- Lookup/W8/W16：可能提高每轮提交量，但尚无真实Lookup命中与完整round成本；涉及新的Target前缀/分布/状态资格。
- correction/norm/small-T：有源码机制，缺实际op份额；correction还增加记录store和空间。
- workspace：短场景峰值不能证明长场景生命期及容量收益。
- DFlash2/检索/utility：条件性实验继续保留，资产/命中/合格可选路线与成本合同尚未齐备。
- 完整U34合并：剩余主要为决策/媒体/UI，当前无纯text直接收益证据。

这不是声称CPU SHA是所有请求的最大瓶颈。当前Chat lookup非等待，publication在后台；原两个Chat并未观察到等待该完整1.7秒。因此不能许诺每请求节省0.9秒，也不能把CPU微基准2.12×写成decode或整机2.12×。
