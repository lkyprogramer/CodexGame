# NInfer 29 优化改造复盘：完成了什么，哪些有收益，为什么还没有整体提速交付

截至北京时间2026-10-25，已完成精简Baseline、BO/G1构建与前端证据补全、P1—P4隔离整合，以及**9个性能方向的实测探索**。已经得到真实的局部加速、两个短样本的完整decode单位token成本改善，以及一批可复用的正确性和运行能力；**尚未取得相对原生产版本、可归因且稳定的整体Chat提速结论，也没有发布这些候选。**

这个落差同时来自计划和执行。早期目标混入了完整上游功能整合，后续又在缺少真实关键路径占比的情况下连续做局部kernel；实验驱动和夹具的缺陷反复增加接续成本。这些问题不能由测试数量、文档数量或“还有很多方向没做”来抵消。

本复盘只读取并交叉核对已有报告、最终回执和结构化结果，没有SSH、构建、测试、GPU、模型或HTTP请求，没有修改原始资料、生产配置或既定关闭状态。下面的服务状态来自最后一次实测清理证据，不是本轮实时探测。旧复盘中“W6只完成准备/部分数值”等描述已被后续结果覆盖，以本文引用的最终接续报告为准。

## 收获最大的四个判断

**第一，局部加速必须乘上关键路径份额。** 卷积段减少36.48%，完整Prefill只改善0.314%，是本轮最直接的教训。若某段只占串行关键路径1%，即便该段减少一半，也只能减少整体约0.5%；这是条件算术，不是当前NInfer热点占比。K0当时的GPU算子占比和关键路径均为null，之后仍连续优先局部kernel，说明选型依据不足。也不能由两个不同层级的实验百分比反推精确热点占比。[K0原始缺口](../output/ninfer-v4-k0-20261023/metrics.json)

**第二，W6证明了“每轮正式产出”比单看kernel快慢更关键。** W6单轮本身慢约9.4%～9.6%，但Java正式token/轮从3.0增至4.25，中文从3.8125增至5.25，摊薄后得到约20%的短样本净收益。Java后半正式产出优势消失，单位token耗时随即反向。两路生成文本也发生分歧，因此这是真实短样本观察，仍不是同token轨迹下的因果估计或长期稳定收益。它为后续研究提供方向，但不授予重新开启W6、动态宽度或utility的预算。

**第三，缓存能力有价值，后台发布加速却未必改善当前请求。** C0最后两侧均真实L2恢复55,293 token，只重算81 token；TTFT为943.552→959.943ms，原对照条件未成立，不能判断稳定加速或退化。源码和事件还揭示boundary alias可能先于整个publication job就绪。缓存命中带来的大幅少算早已存在，不能记成C0新创造的收益；C0可以证明的是哈希与合成发布成本下降。

**第四，接受率、单位token耗时和任务完成时间必须同时看。** Lookup命中仍保留mandatory MTP工作，且原正例已接近每轮4 token上限，单靠接受率提高的条件空间只有约3.01%/1.39%。随机MTP工具题接受率92.64%→97.10%、每token快3.11%，但输出649→808 token，完整请求反而更久。算法正确、接受率更高和用户更早拿到答案，是三个不同结论。

资源指标也应按这个原则解释：Q4压缩shared没有跨过驻留档位；GQA新增spill也不意味着所有长度必慢，32K实测就是反例。之前把“新增spill”当绝对性能否决条件过强，已明确纠正；最终应由完整测量段的净收益和原数值标准决定，而不是事后修改标准让某个配置通过。

## 计划和执行哪里浪费了时间

| 问题 | 本轮已发生的事实 | 应改变的做法 |
|---|---|---|
| 性能目标与上游功能耦合 | 完整上游整合把API、图像、Playground等推到性能路径前面 | 共享正确性依赖可以整合；与纯Chat无直接依赖的功能不成为性能开发前置 |
| 先做局部方案，再找整轮收益 | norm、correction、卷积缺当前关键路径份额；P1—P4也缺组合AB | 先回答“省哪段、该段花多少、增加什么成本”，再决定是否值得接入整链 |
| CPU验证没有贴近实际消费边界 | Graph函数地址取错TU、宏未到模型TU、零workspace、Fold layers=1不受支持 | 复用真实消费入口与注册几何，CPU只补直接风险；不以场景数量代替覆盖 |
| 控制器/采集重复出错 | 响应ID关联、PID登记、代理端口、HTTP400终态、容器UID/0600读回 | 固定复用已有owner/ID/终态/清理实现，只加必要的候选输入和输出 |
| 资源预算推导不完整 | 随机MTP遗漏Graph memset节点×replay；部分早期失败缺最终audit | 从完整窗口调用链推导有限预算，失败出口保存已用成本；不靠多开窗口弥补 |
| 夹具不能回答预定问题 | H1重复保护截断、C0两侧alias/control不一致、随机输出长度不同 | GPU前核对真实输入/保护/可比性；质量和归因测量分开解释，不放宽断言 |
| 状态汇报太散且存在过时结论 | 长注册表中累积多段“当前”；W6一度被写成未跑，后续已有净收益 | 复盘按最终结果归并；明确“未测”“局部有效”“稳定性未过”“已关闭” |

这些是计划和执行需要承担的问题，不能归咎于用户限制预算、不允许重跑或要求保留失败。保全失败和修复采集是必要支撑，不应列作推理性能成果。本轮没有统一实际工程工时账本，不能可靠报告总投入小时或“多少比例花在工具上”；各窗口耗时与工程预估也不能相加当作真实总工时。

## 哪些资产保留，哪些停止投入

**保留为后续开发基点：** BO依赖闭合、P1—P4隔离代码与实际缓存/故障证据、small-T数值/Graph参考、请求和导出job关联、已修正的owner/终态/清理工具。它们降低下一轮开发成本，但不自动成为可发布版本。B29与P4 codec/源码身份不同，不能直接跨版本拼出一个单因素收益数字。

**保留为有价值的性能观察：** C0的大块CPU收益，T1024卷积段收益，W6的短样本完整轮产出收益，GQA 32K的局部收益。保留补丁和原始数据，不挑有利shape自动启用，也不把多个不同基点、工作负载和计时口径的百分比相加。

**继续保持关闭：** 本次9个具名实验的已消费窗口均不重开；尤其不追加Bc64 32K、W6、随机MTP或其它已明确收尾方向的补测。没有宣布所有相似算法永久无效，关闭的是本轮固定设计和验证目标。

**尚未实施，不应误判无效：** H2进一步proposal head裁剪/稀疏投影、K3工作区生命周期和有限fork/join、W8/W16、27B DFlash2适配、全局草稿检索、utility规则。现有131072行optimized proposal head、greedy proposal＋Target sampling、CUDA Graph、统一GDN Fold已经存在，不能作为下一轮新成果重复开发。这些方向仍缺各自关键成本或适配证据；此复盘不新建待办、不排序为“确定最大收益”，也不启动它们。[最近候选复核](ninfer-v4-post-w6-selection-20261024.md)

后续若继续，最值得改变的是选型方法：复用已有完整round驱动，以一个窄的真实负载成本归因补齐Target主体、head、MTP、host/提交等份额；同时明确组合候选相对哪个同身份基点。无需重跑旧Baseline，更不应把完整发布验收再次挡在开发前。进入下一项实现前，应能写出一个可被证伪的整轮收益假设，而不是只写“更少shared”“更少循环”或“提高接受率”。这是复盘建议，尚未执行，也不是重新授权测试。

## 仍然不能抹去的缺口

- 严格G1的18处checkpoint_hints差异仍保留；没有改golden消除FAIL。
- C1末次telemetry HTTP附件缺失，不能由排空日志替代原附件。旧Baseline的3个损坏raw、本机CLI/部分patch/grader附件缺失仍在。
- Baseline的97fc7be6是reasoning-only输出耗尽，Gson为8/10 FAIL，RE003为trim断言FAIL。后续性能实验没有证明修复这些质量问题，随机MTP控制题也仍有reasoning-only输出耗尽。
- Baseline没有真实token IDs/逐token ITL/可靠reasoning token拆分/round wall/allocator高水位。W6后来取得了特定驱动范围的完整round wall，但Target/MTP分段仍未公开；不能说所有阶段“已有完整归因”，也不能反过来把W6已测的round wall抹成null。
- GQA Graph仅query0，query1只direct；大状态、probe、arena等部分原始payload仍仅在远端持久目录，不能把本地SHA/摘要称为完整payload备份。
- 各性能首筛不提供总体p95或置信区间，`optimization_qualification=false`。最近2026-10-25凌晨GQA清理记录显示原服务保持停止；本轮没有实时连接核查或恢复服务。
