Diagnosing a local HTTP 502 Bad Gateway error requires a systematic approach that isolates the failure point between the client, the reverse proxy or load balancer, and the upstream application server. A 502 status code specifically indicates that the server acting as a gateway or proxy received an invalid response from the upstream server. In a local development environment, this often manifests when running Docker containers, using Nginx or Apache as a front-end for Node.js, Python, Go, or Java backends, or when utilizing service mesh sidecars like Istio or Linkerd. The following checklist provides concrete commands and verification steps to identify the root cause, ensuring that each stage of the request lifecycle is validated before proceeding to the next.

1. Verify the current state of the local service mesh or reverse proxy configuration. Begin by identifying which process is listening on port 80 or 443. Use the command `lsof -i :80` or `ss -tlnp | grep :80` to determine if Nginx, Apache, Caddy, or a Docker port mapping is handling the incoming traffic. If you are using Docker Compose, run `docker-compose ps` to ensure that both the proxy container and the application container are in a "running" state. If any container shows an exit code other than 0, inspect its logs immediately with `docker logs <container_name> --tail 100`. This initial step confirms that the infrastructure layer is active and not silently crashing due to configuration syntax errors or missing volume mounts.

2. Inspect the reverse proxy error logs for specific upstream failure details. If Nginx is your front-end, locate the error log file, typically found at `/var/log/nginx/error.log` on the host or inside the container via `docker exec <nginx_container> tail -f /var/log/nginx/error.log`. Look for messages such as "connect() failed (111: Connection refused) while connecting to upstream" or "upstream prematurely closed connection". The specific error code in parentheses is critical. Error 111 indicates the upstream port is not listening, suggesting the application has not started or crashed. Error 104 indicates a connection reset, which may point to a protocol mismatch or an application timeout. If you are using Apache, check `/var/log/apache2/error.log` for similar mod_proxy errors. These logs provide the first concrete evidence of why the proxy cannot communicate with the backend.

3. Test network connectivity from the proxy context to the upstream service. Since containers operate in isolated network namespaces, a direct `curl` from the host may not reflect the view from the proxy container. Execute `docker exec <nginx_container> curl -v http://<upstream_host>:<port>/health` to test the connection from within the same network segment as the application. If this command fails with "Connection refused," the issue is definitely between the proxy and the app, not the client and the proxy. If it succeeds but returns a non-200 status code, the problem lies in the application logic or health check endpoint definition. Ensure that the hostname used in the curl command matches exactly what is defined in your Nginx `proxy_pass` directive. You can verify the active listening sockets from within the application container using `netstat -tlnp | grep <port>` or `ss -tlnp | grep <port>`. If the output shows `127.0.0.1:3000`, you must change the bind address to `0.0.0.0` and restart the service. This is a frequent oversight when migrating from native host execution to containerized environments.

5. Check for application startup delays or readiness probes. If the proxy starts before the application has fully initialized, requests sent during the boot sequence will result in 502 errors. This is particularly common with Java Spring Boot applications or Python services that perform heavy initialization tasks like database migrations or schema checks. Implement a readiness probe in your Docker Compose configuration or Kubernetes manifest to delay traffic routing until the app is ready. For immediate diagnosis, manually wait for the application log to output "Server started" or "Listening on port X" before sending test requests. You can automate this check by running `until curl -s http://<upstream_host>:<port>/health > /dev/null; do echo waiting; sleep 1; done` in a shell script that runs after the container starts. This ensures that you are not diagnosing a transient startup failure as a permanent configuration error.

6. Investigate protocol mismatches between the proxy and upstream. Ensure that if your reverse proxy is configured to use HTTP/2 or HTTPS for upstream communication, the application actually supports those protocols. For instance, if Nginx is configured with `proxy_pass https://backend:443`, the backend must be serving TLS. If it is only serving plain HTTP, the handshake will fail, resulting in a 502. Conversely, if you are using gRPC or WebSocket upgrades, ensure that the proxy configuration includes the necessary headers such as `Upgrade` and `Connection`. Check your Nginx configuration for `proxy_set_header Upgrade $http_upgrade;` and `proxy_set_header Connection "upgrade";` if dealing with WebSockets. A mismatch here often manifests as a 502 even though basic TCP connectivity exists.

Check for Out Of Memory (OOM) events using `dmesg | grep -i oom` on the host system or `docker inspect <container_id> | grep OOMKilled`. If `OOMKilled` is true, you need to increase the memory limits in your Docker Compose file or adjust the JVM heap size for Java applications. Additionally, check CPU throttling if using cgroups; high load can cause request timeouts that the proxy interprets as invalid responses.
